## Topics

A topic is a thread in the human's chat with agents (spec 4.5, decision #7): an id, a title, a status, a `standing` flag, at most one bound item, creation and activity times. Every message belongs to one, and the `deliver` frame carries it as `"topic":{"id":…,"title":…,"item":…}` (`item` only when bound; the spoke shows them as `topic`, `topic_title` and `topic_item` on the channel event).

- **General** (`general`) and **Agents** (`agents`) are created at the project's first hub start and are standing: renaming, deleting or closing them is refused. The system creates no other topic.
- **Automatic run reports.** Periodic dev T3, nightly soak, culprit probes/search summaries, skip/blocked notices, merge-batch notices and quarantine proposals go to Agents. Suite log and coverage chips follow the report topic. Verify and executor prepare default to Agents, addressed to the Coordinator; explicit `--report` chooses another topic. General retains human/Coordinator dialogue and the automatic Coordinator harness-exit and ten-minute vacancy/recovery notices: those rare notices require the human to restore a Coordinator.
- **Creation.** The human creates a topic from the UI (`topic.create`) or shell (`cland topic create <title> [--item T-n]`), an agent with that CLI command or the `topic.create` tool (the Coordinator any topic, an Implementer only one bound to its own item: the permission table below); a title is required (at most 200 characters). The id is `topic-<n>`. `item` binds the topic to a unit of work: the item must exist and be open, and has one topic at most, so a second `topic.create` for it is refused with the topic it has (`T-1 already has a topic: "…" (topic-1); one topic per unit of work: write there`). The binding is written into the item's file (`topic: topic-1`) through the tracker. A hub with no project has no tracker and refuses a binding; a blank `item` is refused, not taken as none. `task.link --topic` (the CLI's `cland task link`, the `task.link` tool) and `task.create` with a `topic` bind through the same rule: the topic must exist and not be standing, an item already bound elsewhere is refused (`T-1 already has a topic: …`), and so is a topic bound to another item (`topic-2 is already bound to T-1; one item per topic`); the item's file and the topic's `item` change together, and `--topic ""` (null) unbinds both. At start the hub reconciles the bindings with the tracker: a bound item closed while no hub ran (a hand edit, a pull) closes its topic and cancels its asks. A topic with no message yet is listed last (a task's topic appears with its first message).
- **Status** follows the direction of the messages (`src/hub/topics.ts`): a human Question makes the topic `waiting for agent`; Message and Decision start no wait; an agent's message to the human makes it `open` (a topic `waiting for human` stays so: an ask is answered by the human); a message from an agent the human's latest Question addressed, to other sessions in the topic, answers that wait too (`open`); any message reopens a `closed` topic to the status its direction implies. `resolve` clears a wait back to `open` and withdraws the topic's open asks: the `resolve` tool (the Coordinator's, by the permission table) and the UI's `topic.resolve`; a closed topic has nothing to clear and is refused. The human closes a topic (`topic.close`), and closing its bound item (`task.close`, `task.edit --state closed`, a hand edit to `state: closed`) closes it; a message reopens the topic, never the item. An `ask` (#33) makes it `waiting for human`, and while any ask in it is open it stays so whatever else is written (below); closing cancels its open asks. Agents keeps `open`.
- **The warning.** While a message in a topic waits for a role nobody holds (a delivery queued under `@coordinator`), the topic carries `"warning":"no coordinator"` (`no reviewer`, … for another role). It clears when a session takes the role (its hello, or the human's `role.set`) and the queued delivery moves to it.
- **History pages.** Each `TopicMessage` carries `seq`, its durable number in the hub-wide monotonic message sequence, in history, live `message` events and `topic.send` results. Numbers are never reused after retention or topic deletion; gaps between a topic's numbers are normal. `topic.history {topic:"general", after:0, limit:200}` starts a forward traversal; use the last returned `seq` as the next `after`. To walk backwards, start with the latest page and pass its first `seq` as `before`. Numeric cursors are exclusive non-negative safe integers; supply only one of `before` and `after`. Every page is oldest first and contains at most 200 messages (default 50): `after` selects the earliest matching rows above the cursor, `before` the latest below it. Empty pages end the traversal; a message inserted between reads is available on a later forward page. Agents filters apply before the page limit. With neither cursor, the existing latest-message selection and ordering are unchanged. String `before` still accepts a message id in the same topic for the Neovim archive reader; an unknown id returns an empty page. `events.list` retains its independent cursor. This uses the existing `messages.seq` and `(topic, seq)` index: upgrading an already numbered store needs no new schema migration, backfill or whole-table rewrite.
- **Agents history filters** (T-56). `topic.history {topic:"agents", item:"T-12", session:"impl-12", limit:200}` searches the whole retained record before taking the latest matches (oldest first, at most 200). Either filter may be omitted; together they intersect. An item matches exact values in notice `detail` naming the item or its currently bound topic (claims, releases, worktrees, merges, agent-message references). A session matches the sender, resolved addressees, or session-bearing notice facts (`session`, `from`, `to`, `by`, `pair`), including arrays such as a mute's pair; harness, role and rule metadata do not name sessions. Message text is not searched; `T-1` does not match `T-12`. The spoke's `history {topic:"agents", item:"T-12", session:"impl-12"}` accepts the same filters (default 50 matches); other topics refuse these filters.
- **Unread.** The human's unread count per topic is the messages from others since the human last read it: the UI sends `topic.read` when the thread is in view, and a message the human writes reads what came before it. It never moves back. The watermark is a message's place in one monotonic sequence the store keeps (`counters.message_seq`, `messages.seq`), never a rowid: retention emptying the table does not make new messages read. The sequence starts above every stored seq and every watermark, so a file an older hub left (watermarks migrated from rowids, its messages pruned) hides no new message. Every `message` delta carries the authoritative `topic.unread` and `topic.lastMessageAt` alongside its topic reference, including human messages (which read the preceding messages). Replace these values rather than incrementing a local counter. `topic.read` publishes a `topic` delta with the new count and retained last message time; snapshots and `topic.list` provide the initial values. Agents have no unread concept.
- **Human kinds and withdrawal.** `topic.send` accepts `kind: "message" | "decision" | "question"` (default `message`), recorded on the message, its history and message delta. Only a Question starts a topic wait for its addressee, named in `Topic.waitingFor`. Message and Decision preserve an existing Question wait; otherwise they leave the topic open. Answering an ask settles that ask without starting a new human Question wait. The latest Question's addressee can settle its wait even after a later Message names somebody else.

  `topic.withdraw {topic, message}` is human-only on the local and authenticated web edges. It returns `{text, message}` for restoring the composer's draft, and publishes `delivery {topic, message, stage:"withdrawn"}`. It accepts the human's ordinary message only while every recipient is still queued or accepted without an adapter submission. Human messages to busy sessions remain queued until idle; an acknowledgement arriving after the session becomes busy waits for idle before injection. Withdrawal releases attached progress/events for the next input and survives reconnect/restart; late acknowledgements cannot revive it. It also clears the withdrawn latest Question's wait. Once any recipient was injected, became uncertain, expired, or began adapter submission, the entire withdrawal is refused with that recipient's stage. The submission fence is durable, including after a failed attempt or hub restart. A bare spoke has no retractable adapter boundary, so its named deliveries are refused conservatively. Ask answers cannot be withdrawn. Neovim renders the terminal stage with the dropped glyph and colour; the composer action is supplied by the web client.

  `TopicMessage.withdrawable` and `delivery.withdrawable` are optional additive
  facts computed from the same per-recipient check as `topic.withdraw`. History,
  message and delivery deltas carry them. An injection-started fence publishes
  false even if the aggregate stage is still queued because another recipient
  waits; aggregate stage semantics are unchanged. Older clients ignore the field.
  Visibility refresh rows recompute eligibility; clients retain newer delivery
  facts when a held refresh crosses a submission delta.
  Ordinary human input publishes a delivery update at submission even if its
  aggregate stage remains delivered; eligibility changes from true to false.
  Non-human and ask-answer inputs add no submission-only delivery update.

  The web message header offers Withdraw for eligible human messages,
  disables it while pending or offline, and removes it after injection. Only a
  successful withdrawal receipt restores the returned text before the topic's
  newer draft; a refusal preserves it and exposes the hub reason in a tooltip.
  If an older hub omits eligibility, the web offers it only for aggregate queued
  messages and lets the hub refuse races. A newer pending send retains its place
  after withdrawn older text on refusal/reload; success keeps the withdrawn draft.

  The web thread composer sends the human's kind, a Coordinator role or chosen
  session chip, and same-topic available artifact ids through `topic.send`.
  Removing the addressee chip omits `to`, retaining hub addressing. Browser drafts
  persist per topic; pending sends await a receipt and a refusal restores text and
  artifacts ahead of newer typing. Offline writes and reconnect replay are
  disabled. A successful human send already marks the topic read through its
  message. See `web/README.md` for keys and browser storage.

- **The human** writes through the UI (`topic.send`), into any topic but Agents: Agents is read-only, a record of what agents send each other, and a `topic.send` there is refused unless it is a reply: with `replyTo` naming an agent's message in Agents, the reply is recorded there and addresses that message's sender, found by the session id it wrote from, so a sender renamed since is still reached (a hub notice has no sender to answer). The message addresses `to` when given, else its mentions: `@coordinator`, `@implementer`, `@reviewer`, `@qa` reach the role's live holders, `@<session-name>` that session (a session the hub knows); with no mention, the Coordinator. `@all` and globs stay text for the human; a mention that names no session and no role is reported as `unknown` and addresses nobody. Each address counts once, with or without its `@`. The addressed party answers with `send` and the topic's id, so the reply lands in the same topic. A party other than the Coordinator may answer the human there (no `to`) while the human's latest message in that topic was delivered to it, by its name or its role (see Permissions); elsewhere it writes to the Coordinator.
- **A role, for the human**, reaches its live holders only: a holder that went offline is not an addressee (it was replaced, or will take the role again on its hello). With no live holder the message is queued under the role, and the first session to take the role (its hello) gets it, also a session that was already addressed by name in the same message (one delivery, one ack). The stage stays `queued` until that session acks. One role may have several holders: all of them are reached. The sender is `human`, a reserved name.
- **A session** writes with `send`: `to` accepts `string | string[]`, such as `"coordinator"` or `["coordinator"]`; a string becomes a one-element array. For a caller with send-tool availability, other shapes (including null and arrays with non-string entries) fail with `to must be a string or an array of strings` before argument-dependent permission routing. With no `to` or `to: []` the message is for the human, in the given topic or General; with `to` it goes to sessions and is recorded in the given topic or Agents. A role reaches its live holders, or, with none connected, the offline holders the hub remembers (queued for them); a role nobody ever held answers `empty`.

The process view (`session.list`, `hub.status.harnesses` and `session.process`) carries `holds`: the claim (`role: "item"`) first, followed by verifier holds (`role: "review"` or `"qa"`) newest first. Each verifier hold includes its durable ISO `heldAt` timestamp; claims have no hold timestamp. Connected presence carries the same work facts. The view can also carry `pending: { item, kind: "review" | "qa" }`, captured when the session accepts a message whose first line starts with `review request <id>` or `qa request <id>` (including epic stage requests; text after the id is detail). IDs resolve by number with any kind prefix. Unknown, ready or closed items are ignored, including late delivery acknowledgements. Moving an item to ready, closing, landing or removing it clears every reservation for it, including disconnected verifiers; stale stored reservations for ready, closed or missing items never block assignment or appear in work views. A newer request replaces pending work; a hold on that item or stop/death clears it. Same-kind verdicts and newer accepted requests retire reservations as described below. Pending work survives hub restart, is stored at delivery acceptance, and is never reconstructed by reading message history. Hold and pending changes publish a changed process view at most once per tick.

The sessions snapshot also supplies `rows`: one hub-merged `SessionRow` per process or connected unmanaged session. `session.list` adds the same `rows` projection alongside its unchanged compatibility fields. Its default read includes unarchived processes and connected unmanaged sessions; `{archived: true}` returns only archived rows, excluding unrelated connected presence. The authenticated web edge permits both reads. `shared/wire` exposes this row portion as `SessionListRows`. Each row has a stable `key` (session id, or `name:<name>` for an unknown identity), the process facts, current `presence` or null, hub-held role, `launched` and `live`, account and usage. `item` selects the first claim/hold, then an accepted pending request, then the launch item. `itemKind` is `item`, `review`, `qa` or null; `additionalHolds` is the +N count, and `itemRequested` distinguishes a request from held work. Verifier holds are newest first. `stateSince` is the ISO transition time for computing the state's age without timer-only deltas (null when unknown); `approvalCommand` carries the command it waits on and clears when the state changes.

Clients negotiating `snapshot`, `numbered-deltas` or `slim-frames` receive `session.row {key, row}` replacements after subscribing. A burst of presence/process/work changes publishes each changed complete row once; unchanged rows consume no additional delta. A null `row` removes that key when it leaves the projection. Snapshots and row deltas use the same composition. Existing `session.list`, `hub.status` and their process/presence events remain available; clients using merged rows ignore those compatibility events for their row model. Numbered row deltas participate in the normal epoch, sequence and resume ring.

A lead's `review request T-n` addressed to `reviewer`, or `qa request T-n` addressed to `qa`, in Agents or the item's topic resolves to one live verifier. Text after the item on that first line is detail: `review request T-<n> — branch, head and scope` resolves exactly like the bare form, and only the item id decides routing. The hub prefers the item's current holder or latest request/authenticated verdict writer, then a free live holder. Verdict affinity follows durable hub write order and identity, independent of copied or reordered item comments. Free holders have no item holds, pending delivery or pool handoff and are idle (or have no adapter state). A bare spoke has no adapter to confirm injection, so its accepted deliveries count as complete for staffing; managed sessions still wait for adapter confirmation. The outcome includes `resolvedTo` with the selected session name.

With no eligible verifier, the outcome is `queued`, its reason says it is waiting for the next free live verifier, and `resolvedTo` is absent. The request and its attachments stay in the topic's durable history, and its topic warns `waiting for free reviewer` or `waiting for free qa`. The hub retries in request order when holds release, delivery acceptance/injection completes, a session becomes idle or reconnects, and during queue maintenance. Selection retains the same affinity rules and reaches one session; a busy earlier request does not block unrelated eligible work. Selection and its sender notice commit together. The sender receives a `verifier-request` notice in the request topic naming the selected session. The queue and sender identity survive hub restarts and renames. Wait for the notice instead of resending; if no verifier is live, report the staffing blocker to the supervising lead so one can be launched.

### Verifier reservation retirement and queue diagnostics

Authorized request admission is persisted privately on its message before native
delivery. Trusted human input through topic.send, CLI, web or remote ingress records
the same receipt without a sender session; legacy human rows retain that authority
from their stored human producer. Owned launch and pool-reuse brief producers also
record admission before native delivery or first-turn acceptance. A legacy NULL
launch receipt migrates only when the stored message/recipient delivery retains an
accepted, uncancelled launch token bound to that durable session credential.
Ordinary hub text, another owner and explicit denied0 remain unadmitted. Authorized named
requests keep updating local pending even across request kinds. Only global
supersession across verifiers requires the matching recipient role; unrelated
agent messages cannot supersede verification work. Older queued role
requests receive the receipt only after the normal authority recheck. Legacy
named agent deliveries with a NULL receipt reauthorize through the stored durable sender
identity, current send permission and item-lead authority at acceptance. New
messages persist explicit 0/1 decisions; a rejected decision is never reauthorized.
Missing durable agent sender identity leaves an ordinary delivery without a reservation.
Accepted reservations project `{item,kind,head?}`, with
`{messageId,admittedAt,head?}` persisted separately. An unpinned reservation retires
on a durable same-kind verdict recorded after admission, whoever wrote it.
Pinned reservations require the same commit or proven descendant (see Pinned
verifier request heads). Another
verifier accepting a newer same-kind request supersedes older reservations and
queued requests subject to that same pinned-head check. Late acceptance cannot recreate already-served work. Old stored
reservations without provenance begin at hub load time and retire on the next
later verdict. Ordering uses durable message identities and verdict timestamps;
legacy unpinned requests do not infer heads from prose. Explicit Head fields
use the shared asynchronous ancestry cache.

Eligibility changes retry immediately; the hub also retries at most every 1000 ms
while its maintenance clock runs, independently of held asynchronous heartbeat
warning reads. Diagnostic deduplication is separate from the lifecycle journal
checkpoint and survives Store reopen. An unassigned request past 1000 ms posts one
report-only `verifier-request` notice in Agents, naming the request and each idle
connected verifier's exclusions (holds, pending work/delivery or pool handoff).
Retired stale pending diagnostics name admission time and the superseding verifier
and receipt. The notice survives restart without duplication and changes no gate,
exit status or permissions. An idle process with live work remains reserved.

Selection rechecks the sender's role, send permission and item ownership. A closed/removed item, closed topic, lost authority, hygiene refusal or expired queue (24 hours by default) drops the pending delivery and sends an explicit refusal notice with the reason and retry rule. Named recipients and ordinary role messages keep their usual addressing behavior.

`send` accepts `kind: "progress" | "report" | "question" | "decision" | "request"`; an omitted kind is `report`, and other values are refused. Reports, questions and decisions use the normal turn-starting delivery path. Progress notes stay `queued`, start no turn, and reach each recipient as one ordered digest with its next ordinary delivery. A reconnect's role clause leaves progress held. The digest carries each note's sender, message id, topic and attachments, followed by the triggering delivery, in one harness input on Claude Code, Codex and OpenCode. A message to the human is recorded immediately, whatever its kind.

A `request` is addressed only to the human: omit `to` or give `[]`, set `request` to `review`, `qa` or `handover`, and set `subject` to a known item (`T-n`), artifact (`A-n`) or session name. Any session, whatever its role and without a human mention, may send one. Other message kinds retain their permission rules. A request defaults to General or the named `topic`. Addressees, missing/unknown subjects, invalid request values, and `request`/`subject` on another kind are refused with the fix. Request first lines are never parsed; `review request T-n` addressed to a verifier retains the separate crew routing convention.

```json
{"kind":"request","request":"review","subject":"T-12","text":"Please review the build","topic":"topic-12"}
```

Held notes and their digest membership live in the existing SQLite delivery queue and survive a hub restart. A batch's membership is fixed when its triggering delivery is recorded; notes arriving afterwards wait for a later delivery. The spoke acknowledgement and the adapter confirmation advance the whole batch together, while history and the journal retain each original message and its stage. The journal's `send` record includes the kind. Unconfirmed injections retry the same batch; an uncertain outcome holds the whole batch for the existing manual retry path.

Unbound progress keeps the existing queue TTL: expired notes are dropped and journalled before binding. Once bound, a note follows its trigger's TTL, and the batch expires together. Retention preserves every member of a pending batch. If a trigger is deleted, surviving pending notes are released to the same queue with their original TTL and the release is journalled. Injected or dropped notes lose their binding and stay settled. Renaming onto a name with any queued, delivered, uncertain or injected delivery is refused with the target and its unacknowledged count before any mutation. A rename also refuses any duplicate message delivery row between the source and target, regardless of state, naming the target and collision count. Other renames follow the existing behavior.
