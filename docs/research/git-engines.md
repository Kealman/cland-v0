# Self-hostable git engines for an agents-only territory

Research for wayfinder ticket "Research: self-hostable git engines for an agents-only territory" (issue 5), made on 2026-10-07 for cland. Versions, features and install stories were checked against each project's own documentation, source and release metadata; GitHub claims cite docs.github.com and github.blog. Things run on this machine (macOS 27.0.1, Apple Silicon, Apple Git 2.39.5) are tagged [M] and described in Appendix A.

Tags on bullets: [V] stated by the cited source; [M] measured here; [I] inferred (basis given); [U] could not be verified. Links are pinned to a tag, commit or dated docs page where the host allows; "checked directly" means the quoted text was re-read from the primary page after the first pass.

## Bottom line

As of 2026-10-07 no mature, locally runnable, agent-first git engine exists. The realistic options are plain Git, a general forge run as a local process, or a peer-to-peer forge.

- **Plain Git** gives a territory with no server and no accounts. Policy and agent identity can be enforced with hooks and SSH-signed commits (shown on Apple Git 2.39.5), but Git has no review, comment, approval or check object, so cland would own those (section 9).
- **Gitea 28.1** is the one forge run end to end here: one Go binary with SQLite, 170 to 256 MB of RAM, bot accounts, PRs, reviews by a different account, required approvals and checks, auto-merge, AGit push-to-PR and webhooks, all scriptable over REST (section 2). **Forgejo 16** has the same loop but no official macOS binary and was not run (section 1). Gerrit and OneDev have richer review but are JVM servers (not run); soft-serve has a true no-accounts mode but no review objects; Radicle worked locally but is mid-transition after a 2026-09-23 protocol vulnerability disclosure (sections 4, 5, 8, 10).
- Every forge needs accounts, and a reviewer's approval must come from an identity different from the author's.
- Merging slows with the number of open PRs on one base branch: on Gitea the median was 14 s per merge at about 250 open PRs and 1.7 s at 10 or fewer, and GitHub documents the same effect (Appendix A, section 15).
- No engine lands one commit per release by itself; squash-and-push to GitHub is a separate step. Push mirrors and replication copy every branch unless filtered.
- GitHub alone does not remove the need for a territory on a personal account: merge queue is organization-only, rulesets and auto-merge need Pro for private repos, content creation is capped at about 500 requests per hour, and stacked PRs (generally available 2026-10-06) still create N PRs and land n commits (section 15).

Sections: 1 Forgejo, 2 Gitea, 3 Gogs, 4 Gerrit, 5 OneDev, 6 Gitness (Harness Open Source), 7 GitLab CE, 8 soft-serve, 9 bare Git plus review layers (git-appraise, git-bug, Sourcehut, Tangled), 10 Radicle, 11 jj, 12 Sapling, 13 other clients (GitButler, git-spice, git-branchless), 14 agent-oriented layers, 15 GitHub itself, 16 comparison tables, 17 implications for the git strategy, Appendix A smoke tests, Appendix B unverified. Main candidates follow the ticket's six points: (1) what it is, maturity, license, version and cadence; (2) install footprint; (3) API, CLI and auth for non-human actors; (4) change and review primitives; (5) fit for an agents-only territory; (6) flow to GitHub.


## 1. Forgejo

Forgejo and Gitea share a code base back to Gogs and still share most behaviour; this section records Forgejo's facts, and section 2 records Gitea's, with the differences listed at the end of section 2. [V] "Forgejo and Gitea are now effectively different codebases although they share the same history back from the early days of Gogs" ([first-party blog, 2024-12-18](https://codeberg.org/forgejo/website/src/commit/be393fe6325e3aa81eb3be1b2d8acaba0e2308f8/src/content/blog/2024-12-gitea-compatibility.md)).

**1. What it is, maturity, license, version, cadence**
- [V] Self-hosted forge in Go; governed by its contributors, with the domains held by the non-profit Codeberg e.V. ([FAQ source](https://codeberg.org/forgejo/website/src/commit/be393fe6325e3aa81eb3be1b2d8acaba0e2308f8/src/pages/faq.md)).
- [V] Current stable: v16.0.5 (non-LTS) and v15.0.9 (LTS), both 2026-09-17 ([release API](https://codeberg.org/api/v1/repos/forgejo/forgejo/releases)). [M] Recent releases: v16.0.4 2026-09-10, v15.0.8 2026-09-10, v16.0.3 2026-08-20, v16.0.0 2026-07-16, v15.0.0 2026-04-16 (same API, 2026-10-07): the two lines ship patch releases together every one to three weeks.
- [V] Quarterly majors on a fixed schedule: 16.0 released 2026-07-16 and end of life 2026-10-29; 17.0 planned 2026-10-15; 15.0 is the LTS (released 2026-04-16, end of life 2027-07-15); 18.0 planned 2027-01-14 ([release-schedule.json](https://codeberg.org/forgejo/docs/raw/branch/next/release-schedule.json), checked directly; [policy](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/release-schedule.md)). [I] An install made on v16 today would be on a line whose support ends three weeks after this research, with v17 due in eight days; v15 is the LTS line. Since 7.0.0 "there is no breaking change unless the first number changes" ([upgrade doc](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/upgrade/index.md)).
- [V] License GPL-3.0-or-later since v9.0; earlier versions MIT ([README v16.0.5](https://codeberg.org/forgejo/forgejo/raw/tag/v16.0.5/README.md), checked directly).
- [V] API compatibility promise: "As of Forgejo 7.0.0, tools designed to work with Gitea 1.22.0 and below are compatible"; the baseline is still `GITEA_COMPATIBILITY ?= gitea-1.22.0` at v16.0.5 ([versions doc](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/user/api/versions.md), [Makefile](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/Makefile)). Later Gitea API additions are not promised in Forgejo.

**2. Install footprint**
- [M] Official release assets for v16.0.5: `forgejo-16.0.5-linux-amd64` 122,204,040 bytes, `linux-arm64` 113,875,936, `linux-arm-6` 113,422,480, source tarball 55,640,773; Linux only (release API, 2026-10-07).
- [V] There is no official macOS binary: the release workflow builds `platforms: linux/amd64,linux/arm64,linux/arm/v6` ([build-release.yml](https://codeberg.org/forgejo/forgejo/raw/tag/v16.0.5/.forgejo/workflows/build-release.yml), checked directly), and the docs offer only binary (Linux) and Docker, calling other packaging "third-party" ([installation doc](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/installation/index.md)). A third-party Homebrew formula `forgejo` 16.0.5 has arm64_tahoe and arm64_sequoia bottles ([formula API](https://formulae.brew.sh/api/formula/forgejo.json)); building from source needs Go, Node and a C toolchain because the SQLite driver is CGO ([from-source](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/contributor/from-source.md), [go.mod](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/go.mod)). [U] Not run here: with no macOS binary and no running Docker daemon on the test machine, Forgejo's memory and behaviour were not measured.
- [M] Container images from the Codeberg registry, compressed: `forgejo:16.0.5` 82,373,985 bytes (amd64) and 78,665,856 (arm64); `16.0.5-rootless` 75,698,574 (arm64) (manifest sums, 2026-10-07).
- [V] Minimum git 2.34.1 ([git.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/modules/git/git.go)); databases mysql, postgres, sqlite3 (SQLite default journal WAL); SQLite "becomes a poor choice once you see a lot of concurrent activity" ([recommendations](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/setup/recommendations.md)). [U] The docs give no CPU or RAM figure.
- [V] Runs from a work directory as an unprivileged user (`--work-path`, `--custom-path`, `--config`), though the docs say `RUN_USER` "should be a dedicated system (non-user) account" ([command-line](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/command-line.md), [config cheat sheet](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/config-cheat-sheet.md)). [I] Running as the human's own user needs `SSH_CREATE_AUTHORIZED_KEYS_FILE = false`: the writer checks only `StartBuiltinServer` and `CreateAuthorizedKeysFile`, not `DISABLE_SSH` ([ssh_key_authorized_keys.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/models/asymkey/ssh_key_authorized_keys.go)). The same effect was measured on Gitea (section 2).
- [V] Headless bootstrap is documented for the CLI: `forgejo migrate` "so that you can run 'forgejo admin user create' before starting the server", `admin user create --admin --random-password --must-change-password=false --access-token --access-token-scopes ...`, and `admin user generate-access-token --raw` ([command-line](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/command-line.md)). Every key of the minimal local-only `app.ini` listed in Appendix A (`INSTALL_LOCK`, `HTTP_ADDR=127.0.0.1`, `DISABLE_SSH`, `DB_TYPE=sqlite3`, `DISABLE_REGISTRATION`, `REQUIRE_SIGNIN_VIEW`, `[actions] ENABLED=false`) is documented in the Forgejo [config cheat sheet](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/config-cheat-sheet.md); the webhook allow-list key is `[webhook] ALLOWED_HOST_LIST` here (Gitea 28 moved it). Gotcha: users created by CLI after the first must change their password by default, and the API then refuses even a valid token ("You must change your password.") ([admin_user_create.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/cmd/admin_user_create.go), [middleware.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/routers/api/shared/middleware.go)).
- [V] No account-free mode: anonymous users can at most read; the nearest is reverse-proxy header auth (`ENABLE_REVERSE_PROXY_AUTHENTICATION_API`), which still creates accounts and "Verification of header data is not performed", so on a loopback instance any local process could act as any user by setting a header ([reverseproxy.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/auth/method/reverseproxy.go)) [I].

**3. API and CLI surfaces, auth for non-human actors**
- [V] REST `/api/v1` with Swagger 2.0 at `/swagger.v1.json`; auth by Basic, `Authorization: token ...` or Bearer; token scopes are `read|write` over activitypub, admin, issue, misc, notification, organization, package, repository, user, and v16 can restrict a token to specific repositories ([api usage](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/user/api/usage.md), [token-scope](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/user/authentication/token-scope.md)). v16 lets instance admins list, issue and delete users' tokens through the API and adds "Authorized Integrations" (externally signed JWTs, no long-lived credentials) ([v16 release post](https://codeberg.org/forgejo/website/src/commit/be393fe6325e3aa81eb3be1b2d8acaba0e2308f8/src/content/blog/2026-07-release-v16-0.md), [authorized-integrations](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/user/api/authorized-integrations.md)).
- [V] `Sudo`: "The API allows admin users to sudo API requests as another user" via a `sudo=` parameter or `Sudo:` header; non-admins get 403 ([api usage](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/user/api/usage.md), [api.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/routers/api/v1/api.go)). [I] One admin token can therefore act as N bot users on the API; git pushes still need each user's own credential. The same behaviour was measured on Gitea.
- [V] Endpoints (from the Swagger template): create PR `POST /repos/{o}/{r}/pulls`; reviews `POST .../pulls/{n}/reviews` with `event` APPROVED, REQUEST_CHANGES, COMMENT and inline `comments`; dismiss and undismiss; `requested_reviewers`; merge `POST .../pulls/{n}/merge` with `Do` in merge, rebase, rebase-merge, squash, fast-forward-only, manually-merged, plus `merge_when_checks_succeed`, `force_merge`, `delete_branch_after_merge`; update branch; commit statuses; branch-protection CRUD; issue dependencies; labels; Actions runs and dispatch ([swagger template](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/templates/swagger/v1_json.tmpl)). Resolving a review conversation is web-only (no API write) ([web.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/routers/web/web.go)).
- [V] No first-party user CLI: the `forgejo` binary is admin-only. `fj` (forgejo-cli) is a community project in `forgejo-contrib`, v0.6.0 (2026-07-19), with Linux and Windows binaries only; the old `berg` is archived; there is no official SDK or MCP server ([command-line](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/command-line.md), [forgejo-cli releases](https://codeberg.org/api/v1/repos/forgejo-contrib/forgejo-cli/releases), [berg](https://codeberg.org/api/v1/repos/Aviac/codeberg-cli)). Gitea's `tea` makes no Forgejo claim.
- [V] Webhooks: HMAC-SHA256 in `X-Forgejo-Signature`; events include `pull_request`, `pull_request_review_approved`, `pull_request_review_rejected`, `pull_request_sync`, `push` and Actions run events, but no commit-status event; delivery to localhost needs `[webhook] ALLOWED_HOST_LIST = loopback` (default `external`) ([type.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/modules/webhook/type.go), [cheat sheet](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/config-cheat-sheet.md)). No API rate limiting exists; the docs point to a reverse proxy [I].

**4. Change and review primitives**
- [V] AGit: "Forgejo ships with limited support for AGit-Flow": `git push <remote> HEAD:refs/for/<branch>/<topic> -o title=... -o description=...`; `draft` and `for-review` "are currently silently ignored"; "Forgejo does not support Gerrit's Change-Ids" ([agit-support, v16.0](https://forgejo.org/docs/v16.0/user/git-cli/agit-support/), checked directly). Always on: Forgejo sets `receive.procReceiveRefs refs/for` at startup ([git.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/modules/git/git.go)).
- [V] Self-approval: the PR author cannot approve or reject; the API returns 422 "approve your own pull is not allowed" ([pull_review.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/routers/api/v1/repo/pull_review.go)). Approvals counted are official, non-dismissed ones ([review.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/models/issues/review.go)); the UI text says "Without approval whitelist, reviews from anyone with write access count to the required approvals." ([locale_en-US.ini](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/options/locale/locale_en-US.ini)). So reviewer and author must be different accounts [I].
- [V] Branch protection: required approvals, approvals whitelist, dismiss stale approvals, block on rejected reviews, block on outdated branch, required status checks (glob contexts), protected file patterns, signed commits, push and merge whitelists, `apply_to_admins` ([swagger template](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/templates/swagger/v1_json.tmpl)). An instance admin can always `force_merge` past failed protection; a repo admin can unless the rule applies to admins ([check.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/pull/check.go)).
- [V] Merge styles per repository (merge, rebase, rebase-merge, squash, fast-forward-only, manually-merged), auto-merge on checks, draft only by title prefix (`WIP:`), CODEOWNERS (regex), merge blocked by open issue dependencies ([check.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/pull/check.go), [cheat sheet](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/config-cheat-sheet.md)).
- [V] Stacked PRs: `RETARGET_CHILDREN_ON_MERGE = true` retargets child PRs when the parent merges, but in code only on the delete-branch-after-merge paths; a plain branch deletion closes unmerged PRs whose head or base is that branch ([branch.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/repository/branch.go), [push.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/repository/push.go)). [I] Agents must merge parents with `delete_branch_after_merge: true` or the children are closed.
- [V] CI: Forgejo Actions with `forgejo-runner` v13.2.0 (2026-09-18), Linux binaries only; host mode runs jobs "without any container isolation" ("There is no isolation at all and a single job can permanently destroy the host"); "designed to be familiar to users of GitHub Actions, but it is not designed to be compatible" ([runner releases](https://code.forgejo.org/api/v1/repos/forgejo/runner/releases), [actions configuration](https://forgejo.org/docs/v16.0/admin/actions/configuration/), [github-actions doc](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/user/actions/github-actions.md)). External CI can post commit statuses.

**5. Fit for an agents-only territory**
- [V] Every push to a base branch enqueues a conflict check for every unmerged PR on that base, in the unique queue `pr_patch_checker`, with workers defaulting to "CpuNum/2 clipped to between 1 and 10"; Forgejo has no delay for idle PRs ([pull.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/pull/pull.go), [cheat sheet](https://codeberg.org/forgejo/docs/src/commit/ee287bcd948f2dedc74cda8f7ff3d8a9b0aa3f37/docs/admin/config-cheat-sheet.md)). [I] The Gitea measurement in Appendix A applies to the shared code path; it was not repeated on Forgejo.
- [V] Other scale knobs and reports: `SUCCESSFUL_TOKENS_CACHE_SIZE` defaults to 20 because token checks hash with pbkdf2; `cron.delete_old_actions` is off by default and a maintainer reports the activity table is "always being near 50% of the whole database size" on Codeberg ([issue 13932](https://codeberg.org/forgejo/forgejo/issues/13932)); `AUTO_WATCH_NEW_REPOS` defaults to true, so watchers get a notification row per event unless it is turned off [I].
- [V] Bots are ordinary users: `UserTypeBot` exists in the model but a grep of `services/` and `routers/` at v16.0.5 found no admin UI, API or CLI surface for it ([user.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/models/user/user.go)).

**6. Flow to GitHub**
- [V] Push mirrors: `remote_address`, `remote_username`, `remote_password` (a token works), `interval`, `sync_on_commit`, `branch_filter`, `use_ssh`. Without a filter "Forgejo will use git push --mirror"; with a comma-separated branch filter only those branches are pushed; tags always go; "This will force push to the remote repository. This will overwrite any changes in the remote repository!" ([repo-mirror, v16.0](https://forgejo.org/docs/v16.0/user/repo-mirror/), checked directly; [mirror_push.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/services/mirror/mirror_push.go)).
- [V] Pull mirrors (read-only) and one-time GitHub migration of issues, labels, milestones, releases and PRs through `POST /repos/migrate`; with `mirror` true, issues and PRs are forced off ([migrate.go](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/routers/api/v1/repo/migrate.go)). No documentation describes Forgejo opening a PR on GitHub [U: absence checked in docs, not proven].
- [I] One change to GitHub: squash-merge the release PR into a dedicated branch on the forge, then either a push mirror with `branch_filter` set to that branch and `sync_on_commit`, or a script that pushes it to a GitHub branch and opens one PR with `gh`. Pointing a mirror at GitHub `main` would force-push over human work.

## 2. Gitea

Measured on this machine (macOS 27.0.1, Apple Silicon, 10 cores, 16 GB, Apple Git 2.39.5) with the official `gitea-28.1.0-darwin-arm64` binary, SQLite and default queue settings; method and raw numbers are in Appendix A.

**1. What it is, maturity, license, version, cadence**
- [V] Self-hosted forge in Go run by Gitea Ltd and a Technical Oversight Committee: "Three positions are elected ... and the other three consist of appointed members from the Gitea company" ([community-governance.md](https://github.com/go-gitea/gitea/blob/v28.1.0/docs/community-governance.md)). MIT ([LICENSE](https://github.com/go-gitea/gitea/blob/v28.1.0/LICENSE)).
- [V] Current stable v28.1.0 (2026-10-06). New version scheme: "Gitea drops the historical `1.` prefix from its version numbers, so this release is 28.0.0 rather than 1.28.0" ([first-party blog, 2026-09-30](https://blog.gitea.com/release-of-28.0.0/), checked directly). [M] Releases: v28.0.0 2026-09-29, v1.27.3 2026-08-29, v1.27.2 2026-08-13, v1.27.1 2026-07-27, v1.27.0 2026-07-13, v1.26.0 2026-04-18 (`gh api repos/go-gitea/gitea/releases`, 2026-10-07).
- [V] Cadence and support: "Aim for a major release about every three or four months"; "We support per standard the last major release"; no LTS line is documented ([release-management.md](https://github.com/go-gitea/gitea/blob/v28.1.0/docs/release-management.md)). [U] What the minor number means under the new scheme (28.1.0 shipped seven days after 28.0.0 with backports) is not defined there.
- [V] 28.0.0 added what an agents-only forge wants: Bot accounts ("meant for automation ... authenticate with access tokens, cannot sign in interactively, and receive no notifications or emails"), audit logging (off by default), admin impersonation, repository-scoped HTTPS deploy tokens, a block-on-pending-code-owner-review branch rule; breaking: registration off by default, `[server] DOMAIN` ignored, git 2.25 or later enforced, Git network operations routed through an internal proxy with new egress settings ([release post](https://blog.gitea.com/release-of-28.0.0/), [release notes](https://github.com/go-gitea/gitea/releases/tag/v28.0.0)).

**2. Install footprint**
- [M] Official assets for v28.1.0: `gitea-28.1.0-darwin-arm64` 115,624,914 bytes, `darwin-amd64` 123,306,464, `linux-amd64` 119,423,136, `linux-arm64` 110,887,072 (release API, 2026-10-07). The darwin-arm64 binary's SHA-256 matched the published checksum and it ran (`gitea version 28.1.0 built with go1.27.1`). Docker `gitea/gitea:28.1.0` is 69,202,082 bytes compressed for arm64.
- [V] The docs list darwin-arm64 for Apple Silicon but also say "Currently, the only supported method of installation on MacOS is Homebrew" ([install from package](https://docs.gitea.com/installation/install-from-package), checked directly). "All downloads come with SQLite, MySQL and PostgreSQL support" and the SQLite driver is pure Go by default, so source builds need no C toolchain ([from-binary](https://gitea.com/gitea/docs/src/commit/f940b0bc9efbd3787994287892d1e58cc124f48e/versioned_docs/version-28/installation/from-binary.md), [driver_sqlite_modernc.go](https://github.com/go-gitea/gitea/blob/v28.1.0/models/db/driver_sqlite_modernc.go)).
- [V] Docs: "2 CPU cores and 1GB RAM is typically sufficient for small teams/projects"; "Gitea should be run with a dedicated non-root system account on UNIX-type systems"; "Gitea manages the ~/.ssh/authorized_keys file. Running Gitea as a regular user could break that user's ability to log in" ([docs home](https://docs.gitea.com/), checked directly). Minimum git is 2.25.0 in code ([git.go](https://github.com/go-gitea/gitea/blob/v28.1.0/modules/git/git.go)), though the docs still say 2.0.0.
- [M] Memory: idle RSS 170 MB right after start, 175 MB after 20 s; 239 to 256 MB after creating 300 PRs and merging dozens. Start-up to healthy `/api/healthz` took under 6 s. Data after about 310 PRs (roughly 130 merged, 178 closed unmerged): 7.8 MB data directory, 4.5 MB repositories, 3.2 MB SQLite file.
- [M] Footgun measured: with `DISABLE_SSH = true` and no other change, the first start logged `rewriteAllPublicKeys ... Unable to remove temporary authorized keys file: /Users/<me>/.ssh/authorized_keys.tmp`, which shows Gitea rewrote the real `~/.ssh/authorized_keys` at start-up. **5. Fit for an agents-only territory**
- [M] What breaks at hundreds of PRs, measured on SQLite with one sequential client and PRs touching distinct files: 300 branches pushed in one `git push` took 18 s; 300 PRs took 158 s (mean 523 ms per create, p95 552 ms); 303 approvals took 27 s (mean 82 ms). Merging then degrades with the number of open PRs on the same base: at 223 to 255 open the median wait for a PR to become mergeable after the previous merge was 14.1 s (mean 12.8 s, min 1.4 s, max 30.5 s; 32 merges in 420 s); a blind retry loop got HTTP 405 "Please try again later" on 236 of 284 merge calls in the first run (the PR was still being re-checked). After closing 178 PRs (0.2 s each), the median wait was 2.8 s between 45 and 25 open (1.1 to 6.4 s) and 1.65 s at 10 or fewer open (1.1 to 2.4 s). That is roughly 1.3 s plus 0.05 s per open PR on the base branch, per merge. The code explains it: every push to a base branch re-checks every unmerged PR on that base in the `pr_patch_checker` queue ([pull.go](https://github.com/go-gitea/gitea/blob/v28.1.0/services/pull/pull.go), [check.go](https://github.com/go-gitea/gitea/blob/v28.1.0/services/pull/check.go)), and the merge API maps a not-yet-mergeable PR to 405 "Please try again later" ([pull.go in the API router](https://github.com/go-gitea/gitea/blob/v28.1.0/routers/api/v1/repo/pull.go)). GitHub documents the same effect: "Having many open pull requests targeting the same branch can slow down mergeability checks or lead to timeouts" ([repository-limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)).
- [V] Gitea delays the check for PRs idle for more than 7 days (`DELAY_CHECK_FOR_INACTIVE_DAYS`, [app.example.ini](https://github.com/go-gitea/gitea/blob/v28.1.0/custom/conf/app.example.ini)); that did not apply here because the PRs were new. Other tracker reports: slow PR creation with many repositories and long-running SQLite queries freezing the UI ([issue 36111](https://github.com/go-gitea/gitea/issues/36111), [issue 28933](https://github.com/go-gitea/gitea/issues/28933), both open). The docs themselves say "Be aware that SQLite does not scale" ([database-preparation](https://gitea.com/gitea/docs/src/commit/f940b0bc9efbd3787994287892d1e58cc124f48e/versioned_docs/version-28/installation/database-preparation.md)).

### Where Forgejo and Gitea differ (decision-relevant)
- Licence: GPL-3.0-or-later (Forgejo) against MIT (Gitea). Governance: Codeberg e.V. against Gitea Ltd plus a TOC with three company seats.
- macOS: Gitea ships darwin-arm64 binaries and a darwin-arm64 runner (docs still call Homebrew the supported route); Forgejo ships Linux only and its runner is Linux only.
- Bots and tokens: Gitea 28 has a Bot account type and repository-scoped deploy tokens; Forgejo has repository-restricted tokens, admin token issuance through the API and Authorized Integrations (v16).
- Push mirrors: Forgejo has `branch_filter` and SSH auth; Gitea mirrors all branches over HTTPS only.
- Stacked PRs after a parent merge: Forgejo retargets children only through the delete-after-merge paths and otherwise closes them; Gitea retargets to the default branch on any deletion.
- Scale and admin controls: Gitea delays checks for idle PRs and can forbid even admins from force-merging (`block_admin_merge_override`); Forgejo instance admins can always force-merge.
- Ecosystem: tea, the Go SDK and an official MCP server exist for Gitea only; Forgejo's API compatibility promise is frozen at Gitea 1.22.0.
- Webhook allow-list key: `[webhook]` in Forgejo, `[security]` in Gitea 28. Gitea has a commit-status webhook event, Forgejo does not.
- AI policy for upstream contributions (does not restrict use): Forgejo "does not accept any works ... partially or fully authored by coding agents" ([CONTRIBUTING.md](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/CONTRIBUTING.md)); Gitea welcomes disclosed AI-assisted contributions and ships an `AGENTS.md` ([CONTRIBUTING.md](https://github.com/go-gitea/gitea/blob/v28.1.0/CONTRIBUTING.md)).

**5. Fit for an agents-only territory**
- [V] Local-only is possible but not the default: `init` writes HTTP address `*` and SSH `*:29418` (`InitHttpd.java`, `InitSshd.java` at v3.14.4); the quickstart says to change the listen URL "from * to localhost" ([linux-quickstart](https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.4/linux-quickstart.html)). - [I] End-to-end scripting without a browser is feasible: init in batch mode, create agent accounts with tokens by REST, push `HEAD:refs/for/main`, review as a second account, submit. [U] The bootstrap of the first admin account without a browser (through the dev-mode `/login/?action=create_account` servlet, read from source) is not documented as a workflow and was not run.
- [V] Scale: the homepage claims Gerrit is "Proven to scale to thousands of concurrent developers" (first-party marketing, [home](https://www.gerritcodereview.com/)); configured ceilings include `change.maxPatchSets` 1000 and `change.maxComments` 5,000 ([config-gerrit](https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.4/config-gerrit.html)). 3.14 indexes changes asynchronously for regular users, while accounts in "Service Users" are indexed synchronously and so read their own writes at once ([3.14](https://www.gerritcodereview.com/3.14.html), [access-control](https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.4/access-control.html)).

**6. Flow to GitHub**

- [I] One-commit landing is not a documented workflow: squash locally onto a release branch, give it a Change-Id, push to `refs/for/release` for the final agent review, then replicate that single branch, or push the squashed commit to GitHub from a script.

- [V] No server, no database, no daemon: local paths and `file://` URLs are "supported by Git natively" ([git-clone, 2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/urls.adoc)). Git 3.0 is planned with changed defaults (`safe.bareRepository=explicit`, SHA-256, reftable) but "There is no planned release date" ([BreakingChanges.adoc, v2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)).

**3. Surfaces**
- [V] CLI and hooks only. `merge-tree` "is intended as low-level plumbing", and the docs show a scripted merge with `merge-tree`, `commit-tree` and `update-ref` ([git-merge-tree](https://github.com/git/git/blob/v2.56.0/Documentation/git-merge-tree.adoc)). Push options reach hooks as `GIT_PUSH_OPTION_<n>` when the server sets `receive.advertisePushOptions` ([githooks](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc), [receive config](https://github.com/git/git/blob/v2.56.0/Documentation/config/receive.adoc)).
- [I] There is no API, no auth system and no event bus. Agent identity must come from SSH keys, signing keys and hooks.

**4. Change and review primitives**

| `rebase --update-refs` | 2.38.0 | yes [M] | same |
| `merge-tree --stdin` | 2.39.0 | yes [M] | [RelNotes 2.39.0](https://github.com/git/git/blob/v2.56.0/Documentation/RelNotes/2.39.0.adoc) |

- [V] `pre-receive` runs once per push and "If the hook exits with non-zero status, none of the refs will be updated"; `update` runs once per ref and "can be used to implement access control" ([githooks](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc)). `proc-receive` hands matching pushes (for example `refs/for/master`) to a hook that "may create or update a pull request directly" ([receive config](https://github.com/git/git/blob/v2.56.0/Documentation/config/receive.adoc)). This is the core Git hook point for Gerrit-style push-to-create-a-review [I].
- [V] `git merge-tree --write-tree` "Performs a merge, but does not make any new commits and does not read from or write to either the working tree or index"; exit status 0 is clean and 1 is conflicts ([git-merge-tree](https://github.com/git/git/blob/v2.56.0/Documentation/git-merge-tree.adoc)). [M] On Apple Git 2.39.5 a clean merge returned exit 0 and a conflicting pair returned exit 1 with the conflicted file name.
- [V] `git worktree add` refuses a branch "already checked out by another worktree" unless `--force`; `rebase --update-refs` skips branches checked out in another worktree; the worktree docs still call multiple checkout "still experimental" for submodules ([git-worktree](https://github.com/git/git/blob/v2.56.0/Documentation/git-worktree.adoc), [git-rebase](https://github.com/git/git/blob/v2.56.0/Documentation/git-rebase.adoc)). [M] Confirmed: `fatal: 'feat-a' is already checked out at ...`.
- [V] `git notes` attach data without touching objects, but notes need explicit refspecs to travel and "Avoid 'cherry-pick', as it does not propagate notes by design" ([git-notes](https://github.com/git/git/blob/v2.56.0/Documentation/git-notes.adoc), [maintain-git](https://github.com/git/git/blob/v2.56.0/Documentation/howto/maintain-git.adoc)). [M] A verdict note pushed to `refs/notes/reviews` and read back on Apple Git 2.39.5.
- [V] Identity without accounts: `gpg.format=ssh` with `gpg.ssh.allowedSignersFile` ([gpg config](https://github.com/git/git/blob/v2.56.0/Documentation/config/gpg.adoc)). [M] On Apple Git 2.39.5 with OpenSSH 10.3, per-agent throwaway ed25519 keys gave `%G?` = G and `%GS` = the principal for signed commits; a `pre-receive` hook that accepted a push to `main` only when the head commit was signed by a principal in a reviewers file, and no non-merge commit in the range was authored by that principal, rejected an author-signed push, accepted a reviewer-signed merge, and rejected a reviewer-authored commit (2026-10-07, Appendix A).
- [V] `git interpret-trailers` can parse `Reviewed-by:`-style trailers ([docs](https://github.com/git/git/blob/v2.56.0/Documentation/git-interpret-trailers.adoc)); [M] a `pre-receive` hook that required a `Reviewed-by:` trailer rejected an unreviewed push and accepted the amended commit. A trailer alone proves nothing about who wrote it, so signatures are needed for identity [I].
- [V] One-commit landing primitives: `git merge --squash`, `git reset --soft` plus commit, `git commit-tree` ("Creates a new commit object based on the provided tree object", any number of parents), `git push --force-with-lease` ([git-merge](https://github.com/git/git/blob/v2.56.0/Documentation/git-merge.adoc), [git-commit-tree](https://github.com/git/git/blob/v2.56.0/Documentation/git-commit-tree.adoc), [git-push](https://github.com/git/git/blob/v2.56.0/Documentation/git-push.adoc)). [M] `git commit-tree -p <base> "main^{tree}"` produced a single commit whose diff against the base held the whole range.
- [V] Gap: Git has four object types ("commit", "tree", "tag" or "blob") ([gitglossary](https://github.com/git/git/blob/v2.56.0/Documentation/glossary-content.adoc)), so there is no review, comment, approval or check object, and no change identity across rewrites ([git-range-diff](https://github.com/git/git/blob/v2.56.0/Documentation/git-range-diff.adoc) pairs commits by similarity). Missing pieces a minimal review layer would still need [I]: a change entity with lifecycle and owner; stable change identity; comments anchored to file and line per revision; approval policy data and its enforcement point; required-check results and gating; event delivery; serialized landing with conflict detection; an inbox for the human; an agent identity map.

**5. Fit for an agents-only territory**
- [I] Local-only and account-free by construction; every primitive is a CLI command with an exit code. Nothing indexes or garbage-collects review state, and parallel agents in worktrees need distinct branches. Concurrent writers to the same notes ref conflict unless a line-oriented format with `cat_sort_uniq` is used.

**6. Flow to GitHub**
- [I] One commit: build the final tree, `git commit-tree <tree> -p <github-main>` (or `git merge --squash`), push one branch with `--force-with-lease`, open one PR. Review metadata in `refs/notes/*` stays local unless pushed explicitly and is dropped by squash or cherry-pick, so nothing leaks to GitHub by default. Inbound work: fetch GitHub into a separate namespace of the territory repo.

### 9a. git-appraise
- [V] Dormant: last commit 2023-08-12, last release v0.7 on 2021-04-22, not archived; Apache-2.0 ([repo API](https://api.github.com/repos/google/git-appraise), [LICENSE](https://github.com/google/git-appraise/blob/be4751005fb4/LICENSE)). Go client, no server ([README](https://github.com/google/git-appraise/blob/be4751005fb4/README.md)).
- [V] Reviews are JSON lines in git notes under `refs/notes/devtools/{reviews,ci,analyses,discuss}`, merged with `cat_sort_uniq`; commands `request`, `comment`, `accept`, `reject`, `submit --merge|--rebase|--fast-forward`, `show --json` ([README](https://github.com/google/git-appraise/blob/be4751005fb4/README.md), [commands.go](https://github.com/google/git-appraise/blob/be4751005fb4/commands/commands.go)). Comments carry file and line locations and a `resolved` flag ([comment.json](https://github.com/google/git-appraise/blob/be4751005fb4/schema/comment.json)).
- [I] Usable by non-human actors (flags are non-interactive) and a working reference for a notes-based schema, but unmaintained for three years. Reviews travel only with `git appraise push/pull`.

### 9b. git-bug
- [V] v0.11.0 (2026-09-22), GPL-3.0, active; bugs live in `refs/bugs/*` and identities in `refs/identities/*`, with a GraphQL API (v0.11.0 adds subscriptions and atomic compare-and-swap commits), CLI with `--non-interactive` and `-f json`, and bridges to GitHub, GitLab, Jira ([releases API](https://api.github.com/repos/git-bug/git-bug/releases), [feature matrix](https://github.com/git-bug/git-bug/blob/v0.11.0/doc/feature-matrix.md)). Pull requests are marked not working in every interface.
- [I] A candidate local task store with live events, not a review layer; exporting through the GitHub bridge would create GitHub issues, the flooding this effort wants to avoid.

### 9c. Patch-based forges: Sourcehut and Tangled
- [V] Sourcehut: review object is a mailing-list patchset with statuses PROPOSED, NEEDS_REVISION, SUPERSEDED, APPROVED, REJECTED, APPLIED ([lists.sr.ht manual](https://man.sr.ht/lists.sr.ht/)). Self-hosting needs PostgreSQL, a Redis-compatible store, a mail server and Alpine Linux ("the only officially supported environment"), and accounts are mandatory (meta.sr.ht) ([installation](https://man.sr.ht/installation.md)). AGPL-3.0; public alpha ([sourcehut.org](https://sourcehut.org/)). [I] Not realistic on one macOS machine, and it conflicts with "no accounts".
- [V] Tangled: AT Protocol based; "knots" host repos, "spindles" run CI; MIT; releases are `v1.x-alpha` (v1.16.1-alpha 2026-07-17); PRs are round-based, stacked PRs use jj change IDs, and every actor is an AT Protocol DID ([docs](https://docs.tangled.org/single-page.html), [tags](https://tangled.org/tangled.org/core/tags), [blog: pulls](https://blog.tangled.org/pulls), [blog: stacking](https://blog.tangled.org/stacking)). [I] Not compatible with "no accounts" and not realistic as a one-machine, local-only setup. Only the knot has a self-hosting guide and it needs a domain, TLS and an `AuthorizedKeysCommand`.

## 10. Radicle

**1. What it is, maturity, license, version, cadence**
- [V] "Radicle is an open source, peer-to-peer code collaboration stack built on Git" ([radicle.dev](https://radicle.dev/)); the protocol is Heartwood. Latest 1.10.3 (2026-09-08); previous 1.10.2 2026-08-26, 1.10.1 2026-08-12, 1.10.0 2026-08-05, 1.9.1 2026-05-22, 1.9.0 2026-05-19, 1.8.0 2026-03-30 ([release post](https://radicle.dev/2026/09/08/radicle-1.10.3.html), [CHANGELOG at releases/1.10.3](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/CHANGELOG.md)). 1.0.0 shipped 2024-09-10 ([post](https://radicle.dev/2024/09/10/radicle-1.0.0.html)).
- [V] Dual MIT and Apache-2.0 ([LICENSE-MIT](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/LICENSE-MIT), [Cargo.toml](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/Cargo.toml)). Maintainer-led, funded by Radworks grants, "around 12 people working on Radicle" ([FAQ](https://radicle.dev/faq)).
- [V] Mid-transition: "Work on the next major version of Radicle has started" ([1.10.0 post](https://radicle.dev/2026/08/05/radicle-1.10.0.html)). On 2026-09-23 the project disclosed that "Network traffic between nodes is not encrypted and not authenticated", that peer authentication "allows impersonation", that "All versions of Radicle that were released to date are vulnerable", and that the fix replaces the transport with iroh and "will be breaking, thus bump the major version number" ([disclosure](https://radicle.dev/2026/09/23/disclosure-of-vulnerability-in-network-protocol.html), re-read 2026-10-07). Private repositories are "unfit for use today" ([user guide](https://radicle.dev/guides/user/)).
- [V] Versioning policy: "none of the user-facing commands should be considered stable APIs, and may therefore break in `<minor>` or `<major>` version updates" ([VERSIONING.md](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/VERSIONING.md)).

**2. Install footprint**
- [V] Install script `curl -sSf https://radicle.dev/install | sh` (options `--no-modify-path`, `--version=`, `--prefix=`, default `~/.radicle`); it verifies an SSH signature and installs `rad`, `radicle-node`, `git-remote-rad`; it edits the shell profile unless told not to ([install script](https://radicle.dev/install)). No Homebrew channel is listed ([download](https://radicle.dev/download)).
- [M] The macOS arm64 archive is 9,599,656 bytes; unpacked `rad` is 28,949,216 bytes, `radicle-node` 11,054,400, `git-remote-rad` 8,088,032; the archive signature verified with the script's three maintainer keys (downloaded from `files.radicle.dev/releases/latest/`, 2026-10-07). `radicle-httpd` 0.29.0 is a separate download, 4,181,984 bytes for macOS arm64 ([file index](https://files.radicle.dev/releases/radicle-httpd/latest/)).
- [V] Needs Git 2.34 or later and OpenSSH 9.1 or later with `ssh-agent`; `RAD_PASSPHRASE` bypasses the agent ([README](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/README.md), [rad.1.adoc](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/rad.1.adoc)). No external database: SQLite is bundled ([Cargo.toml](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle/Cargo.toml)). One bare Git repo per RID under `RAD_HOME/storage` ([HACKING.md](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/HACKING.md)).
- [M] Idle RSS of `radicle-node`: 41 MB and 38 MB for two nodes on macOS arm64 (`ps`, 2026-10-07, Appendix A). Plain user processes: `rad node start` daemonizes by itself.

**3. API and CLI surfaces, auth for non-human actors**
- [V] Identity is an Ed25519 key pair, DID `did:key:z6Mk...`, no accounts ([user guide](https://radicle.dev/guides/user/)); `rad auth --alias <name>` is non-interactive with `RAD_PASSPHRASE` or `--stdin`. [M] Gotcha: `rad auth` adds the new key to the running ssh-agent. On this machine it added a throwaway key to the user's agent, which had to be removed with `ssh-add -d`; with `SSH_AUTH_SOCK=` empty and `RAD_PASSPHRASE` set, `rad auth`, the node and `git push rad` all worked without an agent (2026-10-07). Version 1.10.3 documents that an empty `SSH_AUTH_SOCK` is no longer treated as a socket path ([CHANGELOG](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/CHANGELOG.md)).
- [V] One identity per `RAD_HOME`; "This is useful if you are running multiple nodes on the same machine" ([HACKING.md](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/HACKING.md)). Environment variables: `RAD_HOME`, `RAD_SOCKET`, `RAD_PASSPHRASE` and a few test seeds ([profile.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle/src/profile.rs)). [M] On macOS the default `RAD_HOME` path in a deep directory overflowed the Unix socket limit ("path must be shorter than SUN_LEN"); `RAD_SOCKET` with a short path fixed it.
- [V] Scripting: porcelain has no JSON flag (`rad patch list` has none); JSON comes from plumbing: `rad cob list|show|log`, `rad cob create|update` with JSONL actions, `rad node events` (JSON lines from the control socket) ([cob/args.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle-cli/src/commands/cob/args.rs), [events.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle/src/node/events.rs)). `radicle-httpd` 0.29.0 is a read-only JSON API (every `/api/v1` route is GET) with no auth and no write endpoint ([repos.rs](https://github.com/radicle-dev/radicle-explorer/blob/7acf07393f57de663fda4a3a7af8cddb0bceac31/crates/radicle-httpd/src/api/v1/repos.rs)); it binds `0.0.0.0:8080` by default. Rust crates are on crates.io (`radicle` 0.25.1, `radicle-cli` 0.23.0). No MCP or agent integration found in the heartwood or explorer sources (grep, 2026-10-07) [U for third parties].

**4. Change and review primitives**
- [V] Patches and issues are Collaborative Objects under `refs/cobs/xyz.radicle.patch/<id>`; custom COB types are allowed ([protocol guide](https://radicle.dev/guides/protocol/)). Open a patch with `git push rad HEAD:refs/patches` (push options `-o patch.message=...`, `-o patch.draft`, `-o no-sync`); push again to add a revision ([rad-patch.1.adoc](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/rad-patch.1.adoc)).
- [V] `rad patch review <id> [--revision] --accept|--reject -m`; inline located comments are only available through the interactive hunk reviewer, which the help text now marks obsolete, or through raw `review.comment` actions with a `CodeLocation` ([patch/args.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle-cli/src/commands/patch/args.rs), [cob/patch.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle/src/cob/patch.rs)). The user guide says "Radicle doesn't have advanced code review features yet for patches" ([user guide](https://radicle.dev/guides/user/)).
- [V] Merging is plain Git by a delegate: merge into the default branch and push to `rad`; patches whose revisions become reachable are marked merged ([rad-patch.1.adoc](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/rad-patch.1.adoc), [push.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle-remote-helper/src/push.rs)). "A delegate is authorized to do all actions"; "Anyone can submit a review" ([patch.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle/src/cob/patch.rs)). Merge authorization never checks review verdicts, so there is no required-approval gate; separation of duties has to come from who is a delegate, or from canonical-reference rules with an `allow` list and `threshold` ([canonical references post](https://radicle.dev/2025/08/12/canonical-references.html)) [I].
- [M] End to end on one machine with two identities: author agent B pushed `HEAD:refs/patches` and the patch appeared on delegate A's node; A rejected with a message; B pushed a new commit with plain `git push`, creating a second revision; A accepted it and merged by `git merge` plus `git push rad main`; the log said "Canonical reference refs/heads/main updated", the patch showed as merged on both nodes. B pushing its own `main` created a `main` only in B's namespace and left canonical `main` unchanged (2026-10-07, Appendix A).
- [V] No first-class stacked patches; the man page only suggests `patch.base` for stacks ([rad-patch.1.adoc](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/rad-patch.1.adoc)). CI is a separate broker (`radicle-ci-broker`) that listens to node events and needs its own node ([CI broker guide](https://radicle.liw.fi/raw/rad:zwTxygwuz5LDGBq255RA2CbNGrz8/head/doc/userguide.md)).

**5. Fit for an agents-only territory**
- [V] The default node is not local-only: with network `main` and an empty address book it adds the public bootstrap seeds iris and rosa ([runtime.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle-node/src/runtime.rs), [config.rs](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/crates/radicle/src/node/config.rs)). The project's isolation recipe is `node.network = "test"`, empty `preferredSeeds` and `connect`, static peers ([HACKING.md](https://github.com/radicle-dev/heartwood/blob/releases/1.10.3/HACKING.md)). [M] With `network = "test"` and loopback `listen` and `connect`, the log said "0 nodes added to address book", and the two nodes replicated over 127.0.0.1.
- [I] Per-identity cost: separate `RAD_HOME`, separate node process and a full copy of the repository objects for each agent identity. Scripting is feasible but the CLI output is not a stable contract. The only scale evidence is the heartwood repository's own 886 patches accumulated over years ([seed API, 2026-10-07](https://seed.radicle.dev/api/v1/repos/rad:z3gqcJUoA1n9HaHKufZs5FCSGazv5)); [U] hundreds of simultaneous agent patches are untested.
- [I] Because of the 2026-09-23 disclosure, loopback-only isolated nodes keep traffic on the host, but any non-loopback listener or public seed exposes it; adopting 1.x means a forced move to the breaking 2.0 later (storage layout is promised compatible).

**6. Flow to GitHub**
- [V] Official guidance is dual remotes: the team pushed to both `github` and `rad` ("The code review would happen in Radicle, and GitHub would run our tests", [post](https://radicle.dev/2025/05/30/radicle-with-github-actions.html)). "There is no built-in mirroring yet, but you can easily set up a cron job to pull from GitHub and push to Radicle periodically" ([FAQ](https://radicle.dev/faq), checked directly).
- [I] Landing one commit or PR on GitHub is plain Git outside Radicle: squash the merged canonical range onto a release branch and push it to the `github` remote.

## 11. jj (Jujutsu)

jj is a version control system that uses Git as its storage, not a forge: it has no pull requests, review comments, approvals or checks ([README v0.45.1](https://github.com/jj-vcs/jj/blob/v0.45.1/README.md), command list in the [CLI reference snapshot](https://github.com/jj-vcs/jj/blob/v0.45.1/cli/tests/cli-reference@.md.snap)). The roadmap lists forge integration only as a goal ([roadmap](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/roadmap.md)).

**1. Maturity, license, version, cadence**
- [V] "Jujutsu is an experimental version control system. While Git compatibility is stable, and most developers use it daily for all their needs"; still 0.x; "Today, only the Git backend is production-ready" ([README](https://github.com/jj-vcs/jj/blob/v0.45.1/README.md)). Apache-2.0 ([LICENSE](https://github.com/jj-vcs/jj/blob/v0.45.1/LICENSE)). Started by a Google engineer; "not a supported Google product" ([README](https://github.com/jj-vcs/jj/blob/v0.45.1/README.md)); elected maintainers ([GOVERNANCE.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/governance/GOVERNANCE.md)).
- [V] Releases: v0.45.1 and v0.45.0 2026-09-03, v0.44.0 2026-08-06, v0.43.0 2026-07-02, v0.42.0 2026-06-04, v0.41.0 2026-05-07, v0.40.0 2026-04-02, v0.39.0 2026-03-04 ([releases API](https://api.github.com/repos/jj-vcs/jj/releases), fetched 2026-10-07): monthly. Deprecation window: "As we currently release monthly this translates to a six month deprecation period" ([contributing.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/contributing.md)).

**2. Install footprint**
- [V] macOS arm64 archive 9,989,930 bytes, Linux arm64 musl 10,347,138 bytes (release API). [M] The `jj` binary is 26,850,432 bytes unpacked and ran here (`jj 0.45.1-7c41cdeb16b6`). Needs "git 2.41.0 or above" at runtime because "`git` is used for remote operations under the hood" ([install-and-setup](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/install-and-setup.md), [git-compatibility](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-compatibility.md)). A CLI process: no daemon, no database. Homebrew has a bottle ([formula API](https://formulae.brew.sh/api/formula/jj.json)). [M] Apple Git 2.39.5 is below the documented 2.41.0 requirement; remote operations worked in the smoke test, but a newer Git is the documented baseline [U].

**3. Surfaces (CLI only) and what matters for scripting**
- [V] Templates have `json(x)` since v0.31.0, with the caveat that "backward compatibility isn't guaranteed" ([templates.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/templates.md)); [M] `jj log -T 'json(self)'` returned commit id, parents, change id, description and author on 0.45.1. `--no-pager`, `--color`, `--config`, `JJ_CONFIG`, `JJ_USER`, `JJ_EMAIL` and `-m` flags avoid prompts ([config.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)).
- [V] Operation log with `jj undo`, `jj op restore`; "it allows lock-free concurrency -- you can run concurrent `jj` commands without corrupting the repo" but "with the Git backend, repository corruption is possible because the backend is not entirely lock-free" (recoverable with `jj debug reindex`) ([operation-log.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/operation-log.md), [technical/concurrency.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/technical/concurrency.md)). [M] Two workspaces committing at the same time printed "Concurrent modification detected, resolving automatically" and both changes survived, with a "reconcile divergent operations" entry in `jj op log` (2026-10-07).
- [V] Workspaces: "git-worktree: No. However, there's native support for multiple working copies backed by a single repo" ([git-compatibility](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-compatibility.md)); a workspace goes stale when another workspace rewrites its commit ([working-copy.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/working-copy.md)). Colocated repos allow mixing `jj` and `git`, with documented caveats; "Hooks: No." means Git hooks do not run; v0.45.0 notes "Git HEAD state is now tracked per worktree internally. This prepares colocated repositories for support of multiple Git worktrees" ([git-compatibility](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-compatibility.md), [CHANGELOG](https://github.com/jj-vcs/jj/blob/v0.45.1/CHANGELOG.md)).

**4. Primitives relevant to agents as authors and reviewers**
- [V] Change IDs survive rewrites; descendants rebase automatically; conflicts are committed; immutable heads protect trunk by default; `jj squash`, `split`, `absorb`, `rebase`, `abandon`, `interdiff`, `evolog`, `fix` exist ([README](https://github.com/jj-vcs/jj/blob/v0.45.1/README.md), [config.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)). [M] `jj describe -r main` on a pushed trunk commit failed with "Commit ... is immutable".
- [V] `jj git push --change <rev>` creates a bookmark named `push-<change id>`; also `--bookmark`, `--named`, `--all`, `-o` push options (since 0.39.0); "There is no option to push to multiple remotes" ([CLI reference](https://github.com/jj-vcs/jj/blob/v0.45.1/cli/tests/cli-reference@.md.snap)). [M] `jj git push --change 'main..@'` pushed a two-change stack as two `push-...` branches, and after amending the lower change the descendants rebased and the same remote branches were updated ("move sideways"). jj refuses to push a commit with no description unless `--allow-empty-description` is given.
- [V] `jj gerrit upload` since v0.34.0 ([CHANGELOG](https://github.com/jj-vcs/jj/blob/v0.45.1/CHANGELOG.md), [gerrit.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/gerrit.md)); [M] `jj gerrit --help` lists it on 0.45.1.

**5. Fit for an agents-only territory**
- [V] jj can sit on a bare repo: "Bare repositories: Yes. You can use `jj git init --git-repo=<path>`" ([git-compatibility](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-compatibility.md)). It is the client-side VCS on top of a territory forge, not the territory itself [I].
- [V] Risks for agents from the docs: the working copy "is automatically committed" and new non-ignored files are tracked by default ([git-comparison](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-comparison.md), [config.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)); Git hooks do not run; colocated repos with very many refs get slower ([git-compatibility](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-compatibility.md)). jj writes a `change-id` header into Git commits by default since 0.30.0 and it travels with pushes ([CHANGELOG](https://github.com/jj-vcs/jj/blob/v0.45.1/CHANGELOG.md)).

**6. Flow to GitHub**
- [V] Official flow: commit, `jj git push --change @-` or a tracked named bookmark, then open the PR on GitHub (jj has no PR command); several remotes via `[git] fetch = [...]`, `push = "origin"` ([github.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/github.md)).
- [M] One-commit landing worked: `jj new main` then `jj restore --from <stack tip>` produced one commit holding the whole stack's tree, and `jj git push --change @` pushed it as one branch (2026-10-07). The combination is not a documented recipe [I].

## 14. Agent-oriented layers found in 2025-2026 (not git engines)

A scan for tools aimed at an agents-only git territory found no mature, locally runnable, agent-first git engine. [I] Everything agent-first that runs locally is a layer over plain git: a worktree per task plus a local integration step. PR-like objects live in the orchestrator's own database or on GitHub. Each item below is classified as engine (stores and serves repositories, has PR-like objects), layer, or cloud service.

- **Forge (ForgeAILab/forge), layer with PR-like objects.** MIT; v0.13.12 (2026-10-01), eight releases in six days at the end of September; "public beta" with APIs that "can change without deprecation cycles". "Every standalone coding Task still gets an isolated git worktree, CI gate, and review before changes touch `main`"; review modes are agent review, none, or human-required; integration is `git merge --ff-only <reviewed_sha>` after `git checkout <target>` in the registered repo path, so registering the human's own checkout would switch the human's branch; remote URL may be empty since v0.13.12; local-first single binary with SQLite and an auth model of session JWT or `fg_` tokens; the only PR provider is a placeholder stub that logs "placeholder GitHub PR create" ([README](https://github.com/ForgeAILab/forge/blob/v0.13.12/README.md), [architecture.md](https://github.com/ForgeAILab/forge/blob/v0.13.12/docs/architecture.md), [pr_service.rs](https://github.com/ForgeAILab/forge/blob/v0.13.12/crates/services/src/pr_service.rs), [CHANGELOG](https://github.com/ForgeAILab/forge/blob/v0.13.12/CHANGELOG.md); the README quote and the stub were checked directly on 2026-10-07). [I] It keeps every task commit on fast-forward, so a squash to one commit for GitHub would be a separate step.
- **Gas Town and Gas City (gastownhall), layer.** MIT; Gas Town v1.2.1 (2026-06-06), `main` quiet since 2026-07-23, development moved to Gas City v1.5.0 (2026-10-05). The Refinery "merges to main using a Bors-style bisecting queue"; merge strategy `direct` does a local squash merge plus push, `pr` uses the GitHub merge API; `AutoPush=false` merges locally without pushing (re-read in [engineer.go](https://github.com/gastownhall/gastown/blob/v1.2.1/internal/refinery/engineer.go)). Prerequisites include Dolt, tmux and the `bd` tool, so the footprint is heavy ([README](https://github.com/gastownhall/gastown/blob/v1.2.1/README.md), [Gas City README](https://github.com/gastownhall/gascity/blob/v1.5.0/README.md)).
- **Entire CLI (entireio/cli), layer.** MIT; v0.11.4 (2026-10-06). Records agent sessions as per-checkpoint refs `refs/entire/checkpoints/...` and a commit trailer; "By default, checkpoint data rides along with your own pushes, but only to one remote" ([README](https://github.com/entireio/cli/blob/v0.11.4/README.md), checked directly). `entire review` is experimental; its hosting product entire.io is a cloud service with no self-host option found ([docs](https://docs.entire.io/guides/repositories/overview.md)). [I] With GitHub as `origin`, checkpoint refs and trailers reach GitHub unless local-only mode is configured.
- **SmolForge (forge.smol.ai), the only agent-first engine found, cloud only.** Alpha; built on Cloudflare Workers, D1, R2 and Durable Objects; its own README lists reviews, approvals and squash or rebase merges as not yet built; no repo-wide LICENSE file at the commit read ([llms.txt](https://forge.smol.ai/llms.txt), [source README](https://forge.smol.ai/swyx/forge)). Cloud services Cloudflare Artifacts ("now in open beta", 2026-10-01, paid plan; [changelog](https://developers.cloudflare.com/artifacts/platform/changelog/), checked directly) and Pierre Code Storage ("there is no pull request, issue, or code review API", [llms.txt](https://code.storage/llms.txt)) are not self-hostable and out of scope.
- **Harness-native worktrees, layer.** Claude Code: `claude --worktree <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; new worktrees branch from the repository's default branch on the remote (`worktree.baseRef: "head"` branches from local work); subagents can use `isolation: worktree`; a `WorktreeCreate` hook is documented for SVN, Perforce, Mercurial or other systems and "replaces the default git behavior"; for `--worktree "#N"` on hosts other than github.com and gitlab.com it "tries `pull/<number>/head` first, then `merge-requests/<number>/head`" ([worktrees doc](https://code.claude.com/docs/en/worktrees.md), checked directly 2026-10-07). Codex worktrees and Handoff are ChatGPT desktop app features; the Codex CLI reference has no worktree command ([git-worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees.md)). OpenCode has experimental worktree and workspace endpoints ([v1.18.35 source](https://github.com/anomalyco/opencode/blob/v1.18.35/packages/opencode/src/worktree/index.ts)).
- **GitHub-bound orchestrators.** Emdash, Superset (Elastic License 2.0), Sculptor (research preview), Claude Squad (AGPL-3.0; `s` commits and pushes to GitHub) use a worktree per task and open PRs only on GitHub; Vibe Kanban's company shut down on 2026-04-10; Crystal was renamed ([Emdash docs](https://emdash.com/docs/diff-view.md), [Superset license](https://github.com/superset-sh/superset/blob/main/LICENSE.md), [Claude Squad](https://github.com/smtg-ai/claude-squad/blob/v1.0.20/README.md), [Vibe Kanban blog](https://www.vibekanban.com/blog/shutdown)).
- **Local merge-queue micro tools.** `claude-code-merge-queue` ("The local, zero-cost merge queue for parallel Claude Code agents"), `agent-merge` (serializes work from worktrees onto one local branch under a lock) and `jjq` (local merge queue for jj): young single-maintainer projects that show the pattern ([claude-code-merge-queue](https://github.com/funador/claude-code-merge-queue), [agent-merge](https://github.com/aleclarson/agent-merge), [jjq](https://github.com/paulsmith/jjq)).
- **Review of agent-written changes without a forge.** Claude Code `/code-review main...my-feature` reviews a local range and posts comments only to GitHub or GitLab; `codex review --base main` reviews a branch non-interactively; PR-Agent (v0.47.0, MIT) has `local` and `gitea` providers ([Claude Code code-review](https://code.claude.com/docs/en/code-review.md), [Codex commands](https://learn.chatgpt.com/docs/developer-commands.md?surface=cli), [PR-Agent](https://github.com/The-PR-Agent/pr-agent/blob/v0.47.0/README.md)).
- [V] Side effects that reach GitHub even without PRs: Entire checkpoints, Beads' `refs/dolt/data` ref ([Beads README](https://github.com/gastownhall/beads/blob/v1.3.1/README.md)), Gas Town polecat branches pushed to `origin`, Claude Squad pushes, and Claude Code `/batch`, which decomposes work into 5 to 30 units that each "publish" through version-control commands ([commands](https://code.claude.com/docs/en/commands.md), [worktrees doc](https://code.claude.com/docs/en/worktrees.md)). [I] Making the territory the `origin` of every agent worktree, with GitHub as a separate human-only remote, neutralizes most of them.
- [V] Product churn is high: Gas Town moved to Gas City, Beads moved from JSONL in git to Dolt, Crystal became Nimbalyst, Mux became Xum, OpenCode moved to `anomalyco`, PR-Agent moved to `The-PR-Agent` (each in the cited repositories). [I] Assume renames and rewrites within months.

## 15. GitHub itself: what reduces the need for a separate territory

All links are docs.github.com or github.blog pages fetched on 2026-10-07; the page date in parentheses is the last commit to the page source in `github/docs` where the research recorded one. The assumed situation is the likely one for this project: a personal account (not an organization) that owns private repositories. The plan matters, so availability comes first.

| Feature | Free account, private repo | Pro account, private repo | Where it is available |
|---|---|---|---|
| Rulesets and classic branch protection | no | yes | public repos on Free; public and private on Pro, Team, Enterprise Cloud |
| Required approvals, code owners | no | yes | with rulesets or protection |
| Auto-merge | no | yes | public on Free; public and private on Pro and above |
| Merge queue | no | no | org-owned public repos; private repos only in Enterprise Cloud orgs |
| Push rulesets (paths, extensions, size) | no | no | Team plan, org-owned private and internal repos |
| Stacked pull requests | yes | yes | "all github.com plans", generally available 2026-10-06 |

Sources: [about-rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets) (page checked directly: "Rulesets are available in public repositories with GitHub Free ... and in public and private repositories with GitHub Pro, GitHub Team, and GitHub Enterprise Cloud"), [about-protected-branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [managing-auto-merge](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request), [managing-a-merge-queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) (checked directly: "available in any public repository owned by an organization, or in private repositories owned by organizations using GitHub Enterprise Cloud"), [stacked PR GA changelog](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available) (checked directly). [I] On a Free personal account a private repo has no server-side gate at all: no required reviews, no required checks, no auto-merge. Pro adds rulesets and auto-merge but never a merge queue.

**Merge queue.** CI must listen to the `merge_group` event; squash-only works ("Select which method to use when merging queued pull requests: merge, rebase, or squash"); concurrency and group size are between 1 and 100 ([managing-a-merge-queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue), docs 2026-08-14).

**Rulesets.** Rules include require a pull request (approvals, dismiss stale approvals, code owners, "require approval of the most recent reviewable push" by someone other than the last pusher, conversation resolution, allowed merge methods), required status checks, linear history, signed commits, block force pushes; up to 75 rulesets per repository ([available-rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), docs 2026-09-30; [about-rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). GitHub Apps can be ruleset bypass actors ([creating-rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)). "Pull request authors cannot approve their own pull requests" ([approving-a-pull-request-with-required-reviews](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews), checked directly); the owner of a personal repository can still merge on a protected branch "even if there are no approving reviews" ([permission-levels](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)). [I] If every agent acts through the human's own token, every PR is authored by the human and nobody else can supply a counted approval.

**Auth for non-human actors.**
- GitHub Apps act independently of a user; installation tokens "will expire after 1 hour"; a user can register up to 100 apps; installation tokens can open PRs, create reviews and merge; the installation rate limit starts at 5,000 per hour and cannot exceed 12,500 ([about-creating-github-apps](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps), [installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), [permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps), [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). [U] Whether an approving review from an App installation counts toward required approvals is not stated.
- Fine-grained personal access tokens: at most 50 per user, limited to one user or organization, with documented gaps including "Using fine-grained personal access token to contribute to repositories where the user is an outside or repository collaborator" ([managing-your-personal-access-tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), docs 2026-07-30). [I] A machine user added as a collaborator on a personal repo therefore needs a classic token.
- Machine users: "you can create accounts to automate activity on GitHub. This type of account is called a machine user"; the Terms say "Accounts registered by 'bots' or other automated methods are not permitted" and "You may maintain no more than one free machine account in addition to your free Personal Account" ([types of accounts](https://docs.github.com/en/get-started/learning-about-github/types-of-github-accounts), [Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)). Rate limits may not be multiplied by sharing tokens: "You may not share API tokens to exceed GitHub's rate limitations."
- `GITHUB_TOKEN`: events it triggers do not create new workflow runs except `workflow_dispatch` and `repository_dispatch`; since 2026-06-11 PRs it opens run workflows in an approval-required state ([trigger-a-workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow), [changelog](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved)); a new personal repo does not let workflows create or approve PRs by default ([actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)). Deploy keys are Git transport only [I].
- [I] There is no account-free or local-only mode: every actor is a user account, an App, a deploy key or `GITHUB_TOKEN`.

**Copilot cloud agent and third-party agents (conventions for agent PRs).** Documented conventions: a new `copilot/` branch the agent alone can push to; the PR opens as a draft and the agent "cannot mark its pull requests as 'Ready for review' and cannot approve or merge a pull request"; "Prevents the user who asked Copilot cloud agent to create a pull request from approving it"; commits are authored by Copilot with the requester as co-author; workflows do not run until a writer clicks "Approve and run workflows" (an admin setting can skip this, since 2026-03-13); an unattributed Copilot PR needs one more approval than configured (public preview) ([risks-and-mitigations](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations), docs 2026-09-23; [use-cloud-agent-on-github](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github); [available-rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Requires a paid Copilot plan. Anthropic Claude and OpenAI Codex run as coding agents in public preview and "consume GitHub Actions minutes and AI credits" ([about-third-party-coding-agents](https://docs.github.com/en/copilot/concepts/agents/about-third-party-coding-agents), docs 2026-10-05). Copilot code review leaves a "Comment" review by default; since 2026-09-01 it can be configured, off by default, to submit approvals that "counts toward the repository's required-approvals rule" (public preview) ([changelog](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests)). `gh agent-task` is a public preview and the agent tasks API supports only user-to-server tokens ([use-cloud-agent-via-the-api](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api)). A "[WIP]" title convention is not documented [U].

**Stacked pull requests.** Generally available 2026-10-06 on all github.com plans with no setup; each PR targets the branch of the PR below; "Every pull request in a stack is evaluated against rules for the base of the stack"; a stack lands through a merge queue as a single merge group; "Merging `n` pull requests creates `n` squashed commits on the base branch"; up to 100 PRs per stack and no cross-fork stacks; merging requires the new async merge API; `gh stack` (github/gh-stack v0.2.0) and a `gh-stack` skill target agents ([stacked-pull-requests reference](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests), [about-stacked-prs](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs), [roll-out-stacked-prs](https://docs.github.com/en/pull-requests/tutorials/roll-out-stacked-prs), [gh-stack FAQ](https://github.com/github/gh-stack/blob/v0.2.0/docs/src/content/docs/faq.md)). [I] A stack reduces review cost but still creates N PRs on GitHub and lands n commits, so it is the wrong tool for landing one change per release. Separately, GitHub retargets child PRs when a merged PR's head branch is deleted ([managing-branches](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository)).

**Noise controls.** Owners watch repositories they create by default; per-repo settings allow "Participating and @mentions" or ignoring a repository; comments can be hidden ("Hidden comments are minimized but people with read access to the repository can expand them"); interaction limits target non-collaborators and are temporary; draft PRs do not count toward the open-PR cap for users without write access ([about-notifications](https://docs.github.com/en/subscriptions-and-notifications/concepts/about-notifications), [configuring-notifications](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications), [managing-disruptive-comments](https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments), [limiting-interactions](https://docs.github.com/en/communities/moderating-comments-and-conversations/limiting-interactions-in-your-repository)). [I] No create-PR parameter suppresses notifications and no bot-specific filter is documented; suppression is only on the recipient side. [U] Draft PRs on private repos of Free and Pro accounts: the OpenAPI text says they need Team or Enterprise Cloud while the docs prose is silent.

**Rate and repository limits (what an agent swarm hits).** Secondary limits: "no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour" (including actions in the web UI), "No more than 100 concurrent requests", and 900 REST points per minute with writes costing 5; "Continuing to make requests while you are rate limited may result in the banning of your integration" ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), checked directly; [best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api): serial requests, one second between mutations). The create-PR endpoint "triggers notifications. Creating content too quickly using this endpoint may result in secondary rate limiting" ([pulls API](https://docs.github.com/en/rest/pulls/pulls)). Recommended repository limits: 5,000 branches, "6 pushes per minute per repository", 1,000 open PRs against the same branch, "1 merged pull request per minute" ([repository-limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits), docs 2026-08-28, checked directly). The same page warns: "Having many open pull requests targeting the same branch can slow down mergeability checks or lead to timeouts", the effect measured on Gitea in Appendix A. The Acceptable Use Policies forbid "automated excessive bulk activity" ([AUP](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)). [I] Each PR open, review, comment and merge is content creation, so roughly 50 PRs per hour from one identity exhausts the hourly budget; [U] whether the content limit is per user, per installation or per repository is not stated.

**One-change landing and tooling.** Enabling only the squash method gives one commit per PR; squash messages can use the PR title and description ([about-merge-methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github), [configuring-commit-squashing](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests)). `gh pr create --draft`, `gh pr review --approve`, `gh pr merge --squash --auto --delete-branch` exist in `gh` v2.102.0 ([cli source](https://github.com/cli/cli/tree/v2.102.0/pkg/cmd/pr)); the official GitHub MCP server (v2.0.1) has PR create, review and merge tools, remote at `https://api.githubcopilot.com/mcp/` ([README](https://github.com/github/github-mcp-server/blob/v2.0.1/README.md)). Signed-commit rules can block a squash merge when any head-branch commit is unsigned ([available-rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). [I] Landing pattern supported by these facts: push the release-ready branch from the territory to GitHub, open one PR, squash-merge it; collaborators' work comes back with an ordinary `git fetch` of GitHub's `main` into the territory (GitHub offers no pull mirror into a local engine).

**GitHub Enterprise Server and a "shadow" repository.** GHES is a self-hosted GitHub but is "a self-contained virtual appliance" needing a license, with 4 vCPUs and 32 GB memory for trial or demo ([about GHES 3.22](https://docs.github.com/en/enterprise-server@3.22/admin/overview/about-github-enterprise-server), [VMware install](https://docs.github.com/en/enterprise-server@3.22/admin/installing-your-enterprise-server/setting-up-a-github-enterprise-server-instance/installing-github-enterprise-server-on-vmware)); ruled out for one laptop. A second private GitHub repository as the territory is possible, but the owner auto-watches every repo they create, every GitHub limit above still applies to the identity, and agent churn still counts as GitHub activity under the AUP; whether PRs in a private fork notify upstream watchers is not documented [U] ([forks reference](https://docs.github.com/en/pull-requests/reference/forks)).

**What this adds up to.** [I] GitHub reduces the cost of agent output in three ways: stacked PRs (review in small units), Copilot's own guard rails (requester cannot approve, workflows need approval, extra approval for unattributed PRs) and rulesets with required approvals on Pro. It does not remove the need for a territory when the goals are "no flood of PRs and comments", "no accounts" and local speed: every actor must be a GitHub identity, PR and comment creation is rate limited at 500 per hour, merge queue is unavailable for personal accounts, and a stack still lands n commits.

## 17. Implications for the git strategy

Facts and trade-offs only; nothing here is a decision. Section numbers refer to the sections above, and Appendix A holds the measurements.

### 17a. Four shapes a territory can take

1. **Git only, no server (sections 9, 11).** A bare or integration repository, a worktree per session, hooks for policy, SSH-signed commits for identity, `git merge-tree --write-tree` for conflict checks, `git commit-tree` for squashing.
   - Gives: nothing to install or keep running, no accounts, no ports, no database; policy enforcement was demonstrated with plain hooks on the stock macOS Git 2.39.5.
   - Costs: Git has no review, comment, approval or check object and no stable change identity (section 9 gap list), so cland would own the change entity, comment anchoring, approval policy, check results, the merge queue and the inbox. Apple Git lacks `git replay`, `merge-tree --merge-base` and reftable, which exist in Git 2.56.0.
2. **A general forge as a local process (sections 1 to 7).** Gitea and Forgejo give the whole PR loop in one Go binary with SQLite: PRs and AGit push-to-PR, reviews by a different account with inline comments, branch protection with required approvals and status checks, auto-merge, merge styles, webhooks and a REST API (Gitea's loop was run end to end here).
   - Costs: at least an admin and one account per reviewing identity (no account-free mode exists), a listening port, a database file, upgrades (Forgejo v16 ends support on 2026-10-29 with v17 planned for 2026-10-15; Gitea renumbered to 28.x and changed defaults in 28.0), configuration traps (authorized_keys rewrite, egress allow-list), and 170 to 256 MB of RAM for Gitea. Forgejo has no official macOS binary (container or third-party Homebrew), which matters on the main platform.
   - Gerrit (JRE 21, 97 MB war, no external DB) and OneDev (Java 17+, HSQLDB or Postgres) give richer review or built-in agent features but are JVM servers that were not run here; OneDev also runs its own AI users and workspaces, which overlaps cland's role and session model (section 5).
3. **Peer to peer (section 10).** Radicle ran locally with two identities, patch, review verdict and merge (38 to 41 MB per node), but it has no required-approval gate, its CLI is explicitly not a stable API, a 2026-09-23 disclosure says all released versions have an unauthenticated, unencrypted transport, and the fix is a breaking 2.0.
4. **Orchestrator layers (section 14).** Forge (ForgeAILab) provides tasks in worktrees, an agent reviewer, a CI gate and fast-forward integration with local-first SQLite, in public beta with a stub GitHub PR provider. Gas Town and Gas City add a bisecting merge queue but need Dolt and tmux. These bring their own agent launching and review state, which overlaps cland's hub and roles.

GitHub alone (section 15) is the baseline the territory is compared against: no server to run, but every actor is a GitHub identity, content creation is limited to 500 requests per hour, and merge queue is not available to personal accounts.

### 17b. Constraints that hold whichever shape is chosen

- **Reviewer and author must be different identities.** GitHub (documented), Gitea and Forgejo (measured and in code), OneDev and Harness (in code) refuse the author's own approval. Gerrit's default lets the uploader approve and needs `user=non_uploader`. Radicle lets anyone review and delegates do everything, so separation comes from who is a delegate. In plain Git it can be enforced with signed commits and a hook (measured). So the number of identities cland needs equals the number of distinct review roles in play. In Gitea and Forgejo one admin token with `Sudo` can drive all of them over the API, at the price that one token represents every agent; in Gitea the repo owner can force past approvals unless `block_admin_merge_override` is set, so an authoring bot that owns or administers the repository can bypass the approval rule.
- **Open changes per base branch are a scarce resource.** Measured on Gitea: merging gets slower roughly linearly with the number of open PRs on the same base (median 14.1 s per merge at 223 to 255 open, 2.8 s at 25 to 45 open, 1.65 s at 10 or fewer), and a naive client sees HTTP 405 "Please try again later". GitHub documents the same effect and recommends at most 1,000 open PRs per branch, 6 pushes per minute and 1 merged PR per minute. The Forgejo code path is the same and Forgejo lacks Gitea's idle-PR delay. Gerrit's `mergeabilityComputationBehavior` defaults to never computing it. Serializing integration (a queue) is the pattern used by Gas Town, the local merge-queue tools, GitHub's merge queue and git-spice's experimental `merge`.
- **No engine lands one commit per release by itself.** Squash exists per PR (Gitea, Forgejo, OneDev, Harness, GitHub), and none squashes a whole integration range except by opening a release PR whose merge style is squash, or by a Git step (`commit-tree`, `merge --squash`, jj `restore`) outside the engine. GitHub stacks land n commits. Whatever the shape, the release step is a separate, cland-owned step; per-change history, review metadata (notes, COBs, change-id headers, Entire checkpoints) is not carried by a squash [I].
- **What can leak to GitHub without any PR.** Gitea's push mirror copies every branch and tag and force-pushes; Forgejo's does so unless `branch_filter` is set; Gerrit replication pushes all refs including `refs/changes/*` unless a refspec is given; Entire pushes checkpoint refs to `origin`; Beads uses `refs/dolt/data`; Claude Code `/batch` publishes one change per unit; Claude Code worktrees branch from the remote's default branch. So which remote is `origin` inside agent worktrees decides most of the leakage [I].
- **Collaborators' work comes back through ordinary fetches.** No engine has a documented way to open a PR on GitHub or to import GitHub review state continuously; pull mirrors (Gitea, Forgejo, soft-serve, OneDev), one-time migrations (Gitea, Forgejo, Harness, OneDev issues) and a scripted `git fetch github` into the territory are what exist. Radicle's FAQ suggests a cron job. GitHub offers no pull mirror into a local engine.
- **Events for the hub.** Gitea and Forgejo webhooks reach loopback only with an allow-list entry (`[security]` in Gitea 28, `[webhook]` in Forgejo); soft-serve webhooks cannot target loopback at all; Gerrit has `stream-events` and a webhooks plugin; Radicle has `rad node events`; plain Git has hooks; jj does not run hooks. A territory that wants push-time events without polling has a different cost per engine.
- **Harness coupling.** Claude Code can place worktrees through a `WorktreeCreate` hook, branches new worktrees from the remote's default branch unless `worktree.baseRef` is `"head"`, and for `--worktree "#N"` on other hosts tries `pull/<N>/head` then `merge-requests/<N>/head` (Gitea and Forgejo expose `refs/pull/N/head` [I]). Codex's worktrees are a desktop-app feature and the CLI has none; OpenCode's are experimental. Claude Code `/code-review` and `codex review --base` can review a local branch without a forge, but they post comments only to GitHub or GitLab; PR-Agent can post to Gitea. OneDev ships `tod` skills for Codex, Claude Code, Cursor and OpenCode; Gitea ships an official MCP server; Gerrit's MCP server lacks submit and rebase.
- **macOS and install realities.** Official macOS arm64 binaries exist for Gitea, soft-serve, jj, Radicle and Gogs; Forgejo, Gerrit, OneDev and Harness need a container, JVM or source build, and Docker was not running on the test machine. The Linux-only Forgejo and forgejo-runner mean a macOS host would run Forgejo in a container or from a third-party package.
- **Maintenance, licensing and churn.** Forgejo majors are quarterly with three months of support for non-LTS lines and 15 months for LTS; Gitea publishes a major about every three months with no LTS line documented; OneDev ships about 15 releases a month with REST breaking changes in minors; jj is 0.x with monthly releases; Radicle 2.0 will be breaking; Gas Town, Crystal, Vibe Kanban and others changed or ended within months. Licences differ: Gitea MIT, Forgejo GPL-3.0-or-later, OneDev MIT plus a commercial EE jar in the download, GitButler FSL-1.1-MIT (not OSI), Harness Apache-2.0.
- **Security posture of a local server.** A local server is only as private as its listener: Gerrit dev mode lets anyone reach it become any account; soft-serve's no-accounts mode grants admin to anyone who can connect (and its 2026 releases fixed a critical privilege escalation and LFS path traversal); Forgejo and Gitea header auth trusts any local process; Radicle's httpd binds `0.0.0.0` by default; Gitea and Forgejo write the invoking user's `~/.ssh/authorized_keys` unless told not to (measured on Gitea). Tokens in these forges authenticate as full users, and `Sudo` makes one admin token equivalent to all agents.

### 17c. Trade-offs in one place

| Question | Git only | Gitea or Forgejo | Gerrit or OneDev | Radicle | GitHub only |
|---|---|---|---|---|---|
| What cland must build | change entity, comments, approvals, checks, queue, inbox | queue and polling; reviewer logic | little for review; OneDev overlaps roles | review gate, UI, stable wrapper around CLI | nothing locally; limits to respect |
| Accounts | none (SSH keys) | admin plus one per identity or `Sudo` | one per identity | one key per identity and node | user, App, one machine user |
| Resident process and memory | none | one process, 170-260 MB (Gitea) | JVM server | one node per identity, about 40 MB each | none |
| Review by another agent enforced | by hook and signature | by protection rules | by submit requirements (Gerrit) or code (OneDev) | not enforced | by rulesets (Pro) |
| Agent noise reaches GitHub | only what is pushed | only via mirror or script | only via replication or job | only via push | all of it |
| Maturity and churn risk | stable primitives | active; Forgejo quarterly, Gitea 28 renumbering | active; Gerrit slow and steady, OneDev fast | in transition (2.0 break, protocol disclosure) | active, preview features |

### 17d. Not answered here, and cheap to check before an ADR locks
- Forgejo's idle memory and behaviour on macOS (container or Homebrew) and whether `tea`, the Go SDK and `gitea-mcp` work against it (its compatibility promise is Gitea 1.22).
- Gerrit and OneDev idle memory and a scripted loop (no JRE or Docker daemon was available here), and whether a Gerrit dev-mode first account can be created without a browser.
- Whether a GitHub App installation's approving review counts toward required approvals, and the scope of the 500-per-hour content limit.
- Gitea at hundreds of PRs on Postgres instead of SQLite, and with a tuned `pr_patch_checker` queue.
- Whether Claude Code's `--worktree "#N"` works against a Gitea or Forgejo `refs/pull/N/head` in practice.
- Radicle two-identity behaviour with a `threshold = 2` canonical-ref rule, and posting located review comments through `rad cob update`.

### A.5 Side effects of the tests on the machine
- Gitea's first start rewrote the real `~/.ssh/authorized_keys` (section 2); its contents could not be inspected afterwards. The source keeps lines not marked as Gitea-owned.
- The first `rad auth` added a throwaway key to the user's ssh-agent; it was removed with `ssh-add -d`. Later Radicle runs used `SSH_AUTH_SOCK=` empty.
- Throwaway servers were stopped after each series; the sockets created under `/private/tmp/claude-501/` were deleted.
