# cland v0.1.3: Rhythm and rules

Status: complete (2026-10-14). Grilled with the human in the cland-design session in one round on the release as a whole (tracker item T-294, "Release: v0.1.3"), on the research and the observations of the v0.1.2 build; each section is one decided ticket. The epics are tracker items labelled `v0.1.3` (section 4). The v0.1 and v0.1.2 specs stay in force where this one is silent.

## 1. Purpose

v0.1.3 is "Rhythm and rules": the suite several times faster, a crew that never idles between epics, a Coordinator that wakes on its own when a chain of events breaks, the project's rules kept with the project rather than in one session's memory, and OpenCode v2 driven without its hazards. It ships before v0.2 (the web workbench), whose build starts after it.

## 2. Vocabulary

New terms in `GLOSSARY.md`: Rulebook, Rule, Heartbeat, Follows.

## 3. Decisions

### 3.1 OpenCode v2 hygiene

Decided in T-296, Q-297, Q-298 and Q-299 on 2026-10-14, on the research `docs/research/opencode-v2.md` (`research/opencode-v2`).

- **Own database.** cland's per-session OpenCode servers use a database of their own, per user at once and per account once the accounts registry exists (v0.1.2 §3.13), so that OpenCode's background service can never resume a cland session (upstream #51213). Doctor names the database and the login it needs; until the fix lands the clauses forbid running the `opencode` CLI inside a session.
- **Versions: follow with a check.** The adapter follows OpenCode 2.x; doctor re-verifies the tested range at each cland release with the research's API diff tool, points 1.x users to `opencode upgrade --major`, and its install hint leads to the v2 installer. The two fragile points are fixed: launch waits for the server's own readiness, not for a log line; a rejected approval is reported as a rejection, never as a server shutdown.
- **Launch policy.** The roles.toml policy (approval, sandbox, permissions, the item rule, effort) maps onto OpenCode's per-session rules at session creation; the `provider/model#variant` syntax is handled; the `codemode: false` experiment for cland's MCP server is measured before the default changes.
- **Capabilities.** Taken: caller-chosen idempotent prompt ids (OpenCode-only behind the shared contract) and child-session tracking into the instrumentation of v0.1.2 §3.12. The role clause as durable session instructions only as a measured experiment. The approval reply and the mid-session model switch wait for the v0.2 approvals relay (spec v0.2 §3.8).
- **Risks.** Doctor warns that the free default model may train on the code it sees and that OpenCode has no OS sandbox; the clause forbids moving a session out of its item's worktree.

### 3.2 The rulebook

Decided in Q-378 on 2026-10-14.

- **The file.** `.cland/RULES.md` in the project: one rule per heading with a number (referred to as "rule 12"; no letter prefix, since `R-n` is a release id), a scope (all roles or named roles), the date, the reason and a status (active, retired). AGENTS.md stays the hand-written static instructions; the harness memories become caches of what the rulebook holds.
- **How a rule is added.** `cland rule add` from the shell or the workbench, and a `rule.add` tool for sessions: the Coordinator records a rule when the human states one in a thread, instead of writing it into its private memory; a rule can be edited and retired the same way.
- **How it reaches sessions.** The hub puts the rules of a role into its clause at launch and into the brief, and delivers a changed or new rule to running sessions as a delivery (ADR 0007). The workbench shows the rulebook with each rule's origin.
- **The seed.** The rules this project accumulated in the planning session's and the stand-in's memories (briefs address the role; no long foreground commands; one suite at a time; verdicts go to the lead; no routing around refusals; the batch-merge rule; verify the head before merging; check the verify queue before committing on dev) are migrated by one Aide task.

### 3.3 The heartbeat

Decided in Q-380 on 2026-10-14.

- **Interval per role** in `crew.toml`: `heartbeat = "1h"` for the Coordinator by default, off for the other roles unless set.
- **The delivery** carries a digest the hub computes: what is in flight and what looks stale (items in review with no verdict requested, ready items not merged, sessions idle longer than `idle_minutes`, runs that never reported, asks nobody answered).
- **When it fires.** A heartbeat starts a turn only when the session is idle; otherwise it folds into the next turn's digest (v0.1 §3.9 hygiene). It is never a needs-you; it shows in the events view; the timer is an event kind under ADR 0007.
- **The clause** of the Coordinator says what to check on a heartbeat, what to repair and when to escalate to the human.

### 3.4 Lane flow

Decided in T-335 on 2026-10-14.

- **The next epic starts on the last merge.** A lane's next epic may be cut (`to-tickets`, `plan-epic`) and its first stage launched as soon as the previous epic's last ticket merges; the previous epic's QA demo runs in parallel and still closes the epic and gates the release (D16). Merges of the next epic's tickets that touch the same surfaces wait for the demo's verdict so it sits on the dev tip. The next epic's to-tickets and plan-epic are prepared while the previous epic's last stage is in review.
- **`follows`, not `blocked_by`.** Lane order is a relation of its own, `follows`, so that nobody unlinks blocking edges by hand; `blocked_by` keeps meaning a real dependency.
- **Demos off dev.** Epic demos run on a droplet (v0.1.2 §3.14) so that dev need not freeze for them.

### 3.5 Hub hygiene

Decided on 2026-10-14.

- **Tracker-only commits never cancel a dev run** (T-379): a run's identity follows the tree it verifies, the inputs the tree-hash cache knows; docs and tracker commits neither cancel nor invalidate an integrated run, whose result then covers the new head.
- **Orphan hook bridges** (T-311): the cause named, a bridge whose hub is gone exits within a bounded time, a full suite leaves no bridge behind, and doctor sweeps the existing orphans safely.
- **TypeScript 7** for the hub's typecheck (1.6 s against 18 to 26 s, from the web-stack research), when its output matches the current one on the whole repository.

## 4. The release

Decided in the grilling round of 2026-10-14.

- **Scope.** Everything in section 3, plus the epic the build planned itself: "Test speed: structural" (E-387: the in-process hub by default, coverage-based selection, sharded close runs, the worker re-measurement; its decisions of 2026-10-14 12:20Z stand). T-248 (the human's own terminals) stays in Tech debt.
- **Epics**, in the tracker as items labelled `v0.1.3` and `epic`, children of T-294 (now R-294 after the prefix migration):
  1. E-387 Test speed: structural (§4, Scope: the in-process hub by default, coverage-based selection, sharded close runs, the worker re-measurement).
  2. E-423 Rules and rhythm (§3.2, §3.3, §3.4).
  3. E-424 OpenCode v2 hygiene (§3.1).
  4. E-425 Hub hygiene (§3.5).
  5. E-426 Release v0.1.3 from the item (§4: the demos, the release from T-294, the retrospective, the docs).
- **Order.** Two lanes: the suite lane E-387 → Hub hygiene; the rules lane Rules and rhythm → OpenCode v2 hygiene; the release epic waits for all. The lane order is expressed with the new `follows` relation where the hub has it, with `blocked_by` until then.
- **When and who.** The build starts right after v0.1.2 ships, led by the cland-impl session; the crew as in v0.1.2 (Implementers on Codex gpt-6.1-sol, Claude Code roles on claude-sonnet-5-5, Reviewer pool 2); `[plan] approval = "none"`.
- **Dogfooding.** The heartbeat and the lane flow are used by the build that makes them; the rulebook is seeded from the planning memories and read by every clause from then on; the test-speed epic shortens the build's own waits.
- **Definition of done.** As v0.1.2: each epic's demo run by QA on dev with a clear verdict; v0.1.3 released with `cland release --item T-294`; a retrospective artifact; no human acceptance pass.
