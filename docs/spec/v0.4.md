# cland v0.4: beyond one machine

Status: complete (2026-10-31). Grilled with the human in the cland-design session over the map M-1511 (research Q-1513 to Q-1516, prototypes Q-1517 and Q-1518, grilling Q-1519 to Q-1522 and Q-1527); release item R-1530.

The epics are tracker items labelled `v0.4`, children of R-1530 (section 4). The earlier specs stay in force where this one is silent. A choice the map left open and this spec fills is marked "(assumed)"; the Coordinator confirms or replaces it during the build and records the outcome in section 5.

## 1. Purpose

v0.4 takes agent sessions off the human's machine. The hub stays on the human's Mac and launches sessions on pools of small remote Linux hosts that it creates, packs, watches and destroys through a host provider, DigitalOcean first. A host agent on each host spawns the harnesses, and one hub-owned SSH connection per host carries the session's spoke, the hub's socket and the territory over `git daemon`. Harness sign-ins on hosts become a scheduler resource, the logins, each on a small provider volume cland never reads. The web gains a choice of sign-in mode, single or users. This is shape A, shipped in 0.4.0.

The same Host abstraction carries shape B, the whole hub in a Kubernetes cluster with agent hosts as pods, designed here (§3.11) and built in 0.4.x; 0.4.0 carries only the hub changes shape B needs (§3.10). Verification stays separate: full suites run through the executor on large droplets, and agent hosts are small, sized by measurement. Out of scope for 0.4 (round 1, decision 12): a web terminal, macOS hosts, several projects on one agent host, one host for both tests and agents, autoscaling from the queue, and model-cost accounting. Section 4 lists what waits for 0.4.x.

## 2. Vocabulary

New terms in `GLOSSARY.md`: Host, Host agent, Host provider, Host pool, Slot, Waiting launch, Tunnel, Login, Login disk, Key login, User and Sign-in mode. Amended: Executor (hosts are not executors), Lease (a host's lease and its watchdog), Account (its sign-ins on hosts are logins), Session (a session runs on one host), Pool (a crew pool is not a host pool), Pairing, Remote and General (users mode), and Setup (its hosts and sign-in steps).

The glossary already has Pool for a crew's reusable sessions of one role, so the hosts' term is Host pool; in this spec "pool" alone always means a host pool, and "the `agents` pool" names the default one. "Shape A" and "shape B" are this spec's names for the two deployments, not glossary terms. A "card" is a remote card, as in v0.3.

## 3. Decisions

### 3.1 The Host interface and the local host

Decided in round 2 (decision 1), round 1 (decision 2), Q-1519 §8 and §9, and the host prototype's decisions 8, 9, 15 and 16 (Q-1517).

- **One interface for everything the hub does to a session's files and processes.** A Host has these operations: spawn a process with an environment and a working directory, detached; liveness and stop of a process by its birth identity; the process table of the host with memory and CPU per process tree; stat of a working directory; `git worktree add` and `remove` with the root `node_modules` symlink; read a file's bytes by path, for `artifact.create` with a path and for `artifact.upload`; "who stands inside this worktree"; limit polls; and a realpath, or sandbox-root, operation, because Codex's sandbox roots are computed from real paths and today they are the hub machine's. The hub calls nothing on a session's files or processes except through its Host.
- **Two implementations in 0.4.0.** `local` runs the operations in-process on the hub's machine, which is what the hub does today: the adapters (`hub/src/adapters/sessions.ts`, `claude-code.ts`, `codex.ts`, `opencode.ts`) and the worktree code (`hub/src/hub/worktrees.ts`, `hub/src/territory.ts`) move behind it unchanged in behaviour. `ssh` reaches a remote host's agent through the tunnel (§3.2). The test suite adds a fake remote host with the `ssh` behaviour on the same machine (§3.13).
- **A row carries its host.** `harness_processes` gains a `host` column, `local` for every existing row. A row on a remote host is checked, stopped and signalled only through that host's agent, with a Linux birth identity (boot id plus process start ticks); no pid of a remote row is ever probed or signalled on the hub's machine.
- **Claude Code on a host is found once.** One `claude agents --json` at launch finds the worker (a claimed warm spare keeps its pid); afterwards hooks and the mod bridge carry its state through the tunnel, and liveness is by pid. No `claude agents --json`, `claude auth status` or other short-lived `claude` command runs on a timer against a subscription login on a host, since each can start a refresh and lose rotated tokens (claude-code#95822).
- **Limits on hosts come from live sessions.** No idle `/usage` poll runs on a host. Codex's `account/rateLimits/read` runs only on the host that holds the login. On the `local` host the v0.1.2 §3.13 polls stay as they are.
- **An item launch creates its task branch in the territory**, not as a worktree on the hub's machine that is then pushed: the session's Host adds the worktree from the territory. On the `local` host the result is the same as today.
- **Where sessions run in shape A** (round 1, decision 9, narrowed by Q-1519 §7). The Coordinator and the Aide are always `local`: their Claude login is the Mac's own, and the hub refuses a pool for them. Any other role may be placed on a host (§3.5).
- **What sessions do on a host** (round 2, decision 4). Targeted tests, the typecheck and the `cland` CLI run on the host; full suites run only on droplets through the hub's executor. There is no load limiter in 0.4; the host status reports CPU and memory, and the host agent refuses a launch below a free-memory floor (§3.5).

### 3.2 The SSH transport, the tunnel layout and the host agent

Decided in round 1 (decision 3), round 2 (decision 2, amended), Q-1515 §1 to §8, the host prototype's decisions 1 to 5, 12 and 13 and its attach finding (Q-1517), and Q-1519 §8 and §9.

- **The transport is a layer of its own.** A host provider (§3.4) creates machines; a transport carries the hub's traffic to the host agent on them. 0.4.0 has one transport, `ssh`. The later `outbound` transport, a WebSocket the host agent opens to a reachable hub, carries the same four host-side sockets for providers without SSH and for Kubernetes (§3.11), and is added without touching the scheduler. A mesh such as Tailscale is not part of 0.4.
- **One SSH connection per host, owned by the hub.** The hub starts it as a `ControlMaster` with `-N`, `-a -x`, `-F /dev/null`, `BatchMode=yes`, `IdentitiesOnly=yes`, `ExitOnForwardFailure=yes`, `ServerAliveInterval=15` and `ServerAliveCountMax=4`. No autossh: the hub runs its own reconnect loop, with an exponential backoff from 1 s to 30 s with jitter, reset after 30 s of uptime, an immediate retry on wake, `ssh -O exit` on the control path and removal of a dead master's control socket before each start (without the removal a new master runs without multiplexing), and an end-to-end probe through `agent.sock` every 30 s as the host's liveness.
- **Host keys are pinned.** The hub generates each host's key pair, delivers it through the provider's user-data, and connects with `StrictHostKeyChecking=yes` against a per-lease `known_hosts`. The pinned key answering is also the provisioning gate. `StrictHostKeyChecking=no` stays a shortcut of the droplet executor only.
- **Every host-side endpoint is a Unix socket** in a directory the host agent owns on disk, `~/.cland-host/run` at mode 0700, never in `/run/user/<uid>`, which exists only while a login lives. The image's sshd sets `StreamLocalBindUnlink yes` so that a reconnect takes the paths over at once, `ClientAliveInterval 15`, `ClientAliveCountMax 4` and `MaxSessions 32`. There are no TCP forwards: a dead TCP reverse forward stays bound until the client-alive timeout, and the hub's spoke port changes every start.
- **The forwards** on the master:
  - `-R hub.sock` to the hub's existing Unix socket, for the CLI, hooks, the mod bridge and the host agent's calls to the hub;
  - `-R spoke.sock` to a new spoke edge of the hub on a Unix socket (`.cland/run/spoke.sock`), so spokes on hosts speak `ws+unix:` and the host's `hub.json` never changes across hub restarts;
  - `-R git.sock` to the per-host git socket (§3.3);
  - `-L agent.sock`, the hub's calls to the host agent;
  - per session, `ssh -O forward -L` for a Codex app-server socket or an OpenCode server port, cancelled with `-O cancel`, and all of them re-added from the process table after a reconnect, with a short retry.
- **The host's `hub.json` is a remote kind.** It names the forwarded sockets and carries a per-host secret, never the project secret; the hub can revoke it. The CLI and doctor never pid-check a remote `hub.json`. A spoke on a host always carries its launch credential and needs a role, since no `hub.db` exists there.
- **The host agent** is `cland host serve`, the hub's own code on the host, using Node built-ins only. It answers JSON lines on `agent.sock`, spawns harnesses detached in their own session and process group, keeps a process table with Linux birth identities, reports RSS and CPU per process tree, reads and writes files, runs commands, adds and removes worktrees, and watches task branches (§3.3). It stays unprivileged; the one root helper is the login-disk helper (§3.7).
- **The host agent protocol** (assumed; the map left it open). Each frame is one JSON line: a request `{id, op, args}` and a reply `{id, ok, result}` or `{id, ok: false, error}`, plus unsolicited events (`process-exited`, `ref-moved`, `memory`). The connection opens with a hello carrying the per-host secret and the agent's cland version. On a version that differs from the hub's, the hub delivers its own code to the host and restarts the agent; harnesses survive that restart. `local` implements the same operations as direct calls, with no frames.
- **No systemd dependency** (round 2, decision 2, amended after Q-1513 and Q-1517). A `setsid nohup` supervisor loop, started once by the hub over SSH, keeps the host agent alive and restarts it within about 2 s. Harnesses are spawned detached and outlive the host agent, the SSH login that started the supervisor, a tunnel loss and the hub (Ubuntu's `KillUserProcesses` defaults to `no`). systemd is used where present only as a wrapper, never required: Fly Machines and Kubernetes pods have none.
- **Survival.** On reconnect the hub re-establishes the tunnel, spokes reconnect by re-reading the host's `hub.json`, and the host agent reports its process table. Measured: after a 10 to 20 s hub stop the tunnel was back 1.4 to 1.7 s after start and spokes within 7 s; a killed SSH master was back in 3.2 s with its forwards; a killed host agent in about 2 s. A rebooted host means exited sessions and vacated roles.
- **Attach** (round 1, decision 10). `cland session attach` on a host session opens its own `ssh -t` with `ControlPath=none` and `ClearAllForwardings=yes`, never through the master, and runs `cland host attach <session>` on the host, which sets the session's harness environment and execs the harness's attach under `stty susp undef`: over `ssh -t`, Ctrl+Z otherwise ends the attach at once (the session survives and a new attach brings it back). The web terminal stays deferred.

### 3.3 Git through the tunnel

Decided in round 1 (decision 4), round 2 (decision 3), round 3 (decision 3), Q-1515 §4 and §5, and the host prototype's decisions 4, 6 and 16.

- **The territory is served by `git daemon --inetd`**, spawned by the hub per connection on a per-host socket at mode 0600 on the hub's side; there is no git TCP port on the Mac or on a host. Clone, fetch and push all go through it, with half-open sockets on both ends (`allowHalfOpen`): without them a fetch fails with "unexpected disconnect while reading sideband packet". Merge, the merge queue and verification stay in the hub.
- **The daemon's environment is explicit.** It drops `CLAND_TERRITORY_WRITE`, through which alone the `main` and `dev` guard would otherwise be lifted, sets `CLAND_PUSH_HOST=<host>` as the pushing host's identity, and sets `receive.fsckObjects=true`, `receive.autogc=false`, `receive.denyDeletes=true` and a `receive.maxInputSize` cap through `GIT_CONFIG_COUNT`.
- **A per-host allow list.** The territory's `update` hook accepts a daemon push only to a task branch leased to that host's sessions. Before a merge reads a branch, the hub revokes the host's lease on it under the territory lock.
- **The host's work disk** holds a clone of the territory, the worktrees and a root `node_modules` for the worktrees' symlinks; it is disposable and rebuilt from the image and the territory. The clone reaches the daemon through `core.gitProxy` (or `GIT_PROXY_COMMAND`) on `git.sock`. The first clone goes through the daemon, as the prototype did in about 33 s for this project's 52 MB territory; a bundle copied over `scp` on the same master is the fallback when the daemon path fails (assumed, after Q-1515 proposed the bundle for every first clone and the prototype showed the daemon path enough).
- **Every commit reaches the territory.** The host agent pushes a task branch on every ref move, by watching the ref and its reflog with a debounce, not from a `post-commit` hook; the prototype's 2 s poll put a commit into the territory in about 2 s. `cland verify` and `ready` from a host session flush the push first, and the hub compares the territory head with the head the session reports; the hub takes the branch from the territory, never from the session's working directory. The role clauses tell sessions that commits are pushed for them: Claude reported its pushed commit as "still unpushed" in the prototype.
- **A task stays on its host** (round 3, decision 3; Q-1519 §7). A task's worktree lives on the host of its session for that session's life. A relaunch goes to the same host while it is alive; otherwise the new host fetches the pushed branch and adds the worktree again, and uncommitted edits are lost, as with a local worktree today. Reviewers read branches from the territory on any host, and a lead and its Implementer need not share a host.

### 3.4 Host providers, images, the project provisioning hook and DigitalOcean

Decided in round 1 (decisions 2, 6 and 7, decision 6 amended by the image audit), Q-1513 §1 to §9, Q-1519 §2 and §8, and the host prototype's decisions 11, 17 and 19.

- **The host provider interface mirrors the executor's** (`hub/src/executor/executor.ts`): acquire, prepare, status, release and reap, plus the transport a host is reached by and the login-disk operations (create, attach, detach, snapshot and delete a volume; §3.7). It is a second interface beside the Executor, not a new executor kind: a host runs sessions, an executor runs verification, and one machine never does both.
- **What each provider declares**: its price per live hour and per idle hour, read from the provider's own size listing as the droplet executor reads `price_hourly` from `/v2/sizes`; whether a stopped machine still bills compute, and if it does, stopping a host destroys it; its billing granularity and minimum (DigitalOcean per second with a 60 s minimum), below which `idle_stop` never stops a host; how far its token can be confined; its API pacing and machine limit; its CPU architecture; and any extra paid address its SSH needs, which then counts in the idle price.
- **DigitalOcean droplets first.** The provider reuses the executor's token, API client, tags, snapshot code and spend ledger (`hub/src/executor/droplet/`). Regions near the human are lon1, fra1 and ams3; the default is lon1 (assumed, where every measurement ran). A powered-off droplet bills in full, so a stopped host is destroyed. Every host carries the tags `cland`, the project and the pool, and reaping works from tags as the executor's does. Creation respects DigitalOcean's 250 requests a minute and the account's machine limit, 25 droplets today; a refusal pauses creation with a retry and leaves the launch waiting, with no cascade. The token is confined as far as DigitalOcean allows, to custom scopes for droplet, ssh_key, image, tag and volume (whether a token can be held to one project or tag was not found).
- **Deletion is confirmed by reading back.** A DELETE that answers 404 is not proof: in the prototype the watchdog's key delete reported success while the key was still listed a minute later, and a GET by id answered 200 after a DELETE's 404. The host provider confirms every deletion with a GET; the executor's wrapper, which counts a DELETE 404 as success today, gets the same fix (§3.10).
- **Prices** (USD per hour without VAT, checked 2026-10-31; Q-1513 §6):

  | Size | Live | Idle |
  |---|---|---|
  | DigitalOcean s-2vcpu-4gb | 0.0357 | 0 once destroyed |
  | DigitalOcean s-4vcpu-8gb | 0.0714 | 0 once destroyed |
  | Fly shared-2x 4 GB, lhr | 0.0396 | 0.0068 with a volume and IPv4 |
  | Fly shared-4x 8 GB, lhr | 0.0791 | 0.0068 |
  | Hetzner CX23 / CX33 | EUR 0.0096 / 0.0144 | full price while stopped |
  | Serverless (DO MicroVM 2/4, E2B, Modal, Cloud Run, Daytona) | 0.078 to 0.380 | no SSH |

  Fly Machines are the second provider, deferred to 0.4.x: a stopped Machine bills storage only and starts in about a second, but it has no systemd, wipes its rootfs on start unless persisted, needs a $2-a-month IPv4 for sshd, and allows one API request a second per action. Hetzner could not be ordered on 2026-10-31 (every plan "currently unavailable" since 2026-06-26), has no London location and rounds hours up. Serverless sandboxes cost 2 to 12 times a droplet and give no SSH; they wait for the `outbound` transport.
- **One image recipe** for the droplet executor's snapshot, the agent host image and the Kubernetes image, with the CPU architecture as a parameter (`provision.sh` is x86_64-only today; arm64 is for Hetzner CAX and multi-arch images later). The image contains only what cland the tool needs on any project: Ubuntu with the apt timers off, git, curl, ca-certificates, jq, lsof, procps, xz-utils and locales, the hub's exact Node version, the unprivileged `runner` user, build-essential and python3 as common defaults, and on agent hosts the harness installers, the sshd prelude and the login-disk helper. Harness installs use pinned channels: OpenCode 2 comes only from `https://opencode.ai/v2/install`, while npm's `opencode-ai` is OpenCode 1. Neovim is never in an image or in the Helm chart, since the human's workbench stays a local client.
- **The project provisioning hook.** `[verification] provision` names a script run once as root on the image builder, for system packages a project needs and its `prepare` cannot install (`prepare` runs as `runner` without sudo). This project moves its Chromium runtime libraries and its Neovim into its own hook; they leave `provision.sh`.
- **Pool images.** A host boots from a pool image snapshot built like the executor's, by the same recipe and `[verification] prepare`, keyed from the Node version, the lockfile, the harness versions and the provisioning hook's content (assumed: the map's key named Neovim, which the image audit moved into the hook), and rebuilt by `cland host prepare`. The target is 60 to 90 s from create to ready, against 218 to 232 s from the stock image, most of which is DigitalOcean's apt-installed droplet agent before user-data.
- **The host prelude.** The user-data step, before the recipe's own steps, installs the pinned host key and the sshd settings of §3.2, deletes DigitalOcean's volume automount rule (`99-digitalocean-automount.rules`), and installs the login-disk helper with its sudoers line (§3.7).
- **The Linux spoke is slimmed** as its own task: it took 105 to 125 MB of each session on the hosts, four to five times its macOS size (a Claude Code session tree measured 508 to 599 MB, an OpenCode one 345 to 437 MB, the host agent 78 to 90 MB; Codex was not measured).

### 3.5 Pools, placement, the scheduler and the queue

Decided in round 3 (decisions 1, 2 and 4), Q-1519 §1, §2, §5 and §7, and the host prototype's decisions 10 and 11.

- **Pools live in `.cland/config.toml`**, are hot-reloaded, and are changed with `cland config set`, so `cland config set hosts.agents.max_hosts 4` scales at once:

  ```toml
  [hosts]
  daily_spend_usd = 3        # the hosts' share of the daily cap (§3.6)
  lease = "12h"
  # weights = { "claude-code" = 1.0, codex = 0.5, opencode = 0.75 }   (assumed: an optional override)

  [hosts.agents]
  provider = "digitalocean"  # (assumed name)
  size = "s-4vcpu-8gb"
  region = "lon1"
  slots = 8                  # weight a host holds (assumed key name; the map said "sessions per host")
  min_hosts = 1
  max_hosts = 2              # (assumed default)
  idle_stop = "20m"
  spread = false             # dense packing unless true
  transport = "ssh"

  [hosts.qa]
  provider = "digitalocean"
  size = "s-4vcpu-8gb"
  region = "lon1"
  slots = 1                  # one QA session with a browser per host
  min_hosts = 0
  max_hosts = 1
  idle_stop = "20m"
  ```

  `cland init` writes `[hosts]` with its defaults and no pool; a pool table is written when the human enables hosts in setup or adds it with `cland config set` (assumed, so that no project starts paying for an always-on host by surprise). A role binds to a pool in `roles.toml` as `[<role>.launch] pool = "agents"`, default `local`.
- **Slots are weights, not counts.** A Claude Code session weighs 1.0, a Codex session 0.5 until it is measured on the first live host, and an OpenCode session 0.75. A s-2vcpu-4gb host holds 4 and a s-4vcpu-8gb host 8: the measurements left room for one 1.2 GB typecheck at those loads, memory limits Claude Code, and CPU limits OpenCode at about two concurrent turns per vCPU. Droplets have no swap, so overcommit means OOM. The default size of the `agents` pool is s-4vcpu-8gb: twice the price, half the hosts and half the logins.
- **The memory floor.** The host agent refuses a launch when the host's free memory is below 1.3 GB, the typecheck reserve, whatever the slots say; the launch then waits as if the host were full.
- **Placement** packs densely: the fullest host of the pool with enough free weight and the logins the session needs (§3.7). A pool with `spread = true` takes the emptiest host instead. A host with a free slot that cannot serve the session's harness (its login there is signed out, or no login can be bound) is skipped.
- **The waiting launch.** With no host able to take a launch and no room or no login for a new host, the launch waits in the hub, visible as a status line: "waiting for a host", "waiting for a login <harness>" or "waiting for host <id> to boot", always the current reason. It is a status line in the inbox, not an ask; the Coordinator sees it in Agents, `cland session list` shows it, and it ends when the launch is placed or cancelled. Neither the reason nor the "create one?" card (§3.7) repeats per poll.
- **Scale up and down.** A pool keeps at least `min_hosts` hosts, 1 by default for `agents` so that the first session never waits for a cold boot; further hosts start on demand. An empty host stops after `idle_stop`, 20 minutes by default, never below `min_hosts`. The scheduler never stops a host with sessions; only `cland host stop <id>` does, and it ends those sessions as exited. A pool grows only when its new host would get every login it needs.

### 3.6 Host lifecycle: lease, watchdog, failures and money

Decided in round 1 (decision 8), round 3 (decision 4), and Q-1519 §3, §4 and §6.

- **Lifecycle.** A host is created from its pool image, provisioned, reached by its tunnel, handed its logins while it provisions (§3.7), and becomes ready; it serves sessions; it is stopped, which on DigitalOcean means destroyed, after its logins are released. The host's disk is disposable; nothing on it is kept.
- **The lease.** Every host has a lease in `hub.db`, written before the create call and held until its deletion is confirmed, as the executor's leases are. Its deadline is 12 hours, renewed while the host has sessions or is held by `min_hosts` (assumed: the renewal moves the deadline to 12 hours from now each hour). A detached watchdog per host, started at create and re-armed by the hub after a restart, deletes the host and its SSH key at the deadline even if the hub is gone; the prototype's watchdog deleted the last host 13 s after its deadline with the hub stopped.
- **Failures.**
  - No machine, or no SSH, within 5 minutes of the create call: the host is destroyed, its launches stay waiting, and the Coordinator gets one line.
  - Tunnel lost: the reconnect loop of §3.2 runs while sessions live on. After 3 minutes General gets one line, "host <id> unreachable", and the host's row turns red.
  - Not back within 15 minutes: its sessions become exited, their roles are vacated, and the watchdog destroys the host.
  - A host destroyed by anyone, the watchdog included, makes its sessions exited when the hub next sees it (the prototype left them "running"; liveness must treat an unknown host as gone, not alive).
- **Money.** The spend ledger (`spend.json` under `XDG_STATE_HOME`, shared by the user's project hubs) gains a category per entry: `verify` for the executor's runs, `hosts` for agent hosts. `[verification] daily_spend_usd` bounds both together, and `[hosts] daily_spend_usd`, default $3 (about 40 host-hours of s-4vcpu-8gb), bounds the hosts within it (assumed reading of "shared with a sub-cap"). A host reserves its price up to its lease deadline at create and at each renewal and settles on its real lifetime (assumed, as the executor reserves a run). At 80 % of the sub-cap General gets one line; at 100 % no new host starts and live ones are untouched. Volumes, snapshots and pool images are storage, shown in the month's figure but not reserved (assumed; a login costs about $0.12 a month). `cland host status` shows today's and the month's spend per pool.

### 3.7 Logins: disk and key, capacity, sign-in, signed-out and operations

Decided in round 4 (decisions 1 to 7), which replaced round 3's decisions 5 to 9; amended by the login-disk prototype (Q-1518) and by Q-1520 §1 to §5. The research found that no harness tolerates one subscription login copied to several hosts at once, and that Anthropic's terms bar a third party from storing or intermediating Claude.ai credentials (Q-1514).

- **A login** is one sign-in to a harness, held by the hub as a row in `hub.db` with: a name; the harness; the account, meaning the human's subscription it belongs to; its kind, `disk` or `key`; `exclusive`; its provider, region, volume id and backup snapshot ids; its state, `creating`, `ready`, `in-use <host>` or `signed-out`; and its last successful sign-in. The logins on the human's Mac stay outside cland and are never snapshotted or copied. A login whose sign-in has not finished never counts as bound.
- **A `disk` login lives on its own small provider volume**, 1 GiB (868 MB usable once formatted), mounted on the host at `/cland/auth/<harness>-<login>` and passed to the harness as `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `OPENCODE_DB`. cland never reads its contents. The volume is kept for good: at host stop it is unmounted and detached (about 7 s), and the next bind attaches the same volume again (about 7 s), so the login is never stale and never waits on a snapshot. A volume attaches to one droplet at a time, so the provider enforces `exclusive` by itself, as a Kubernetes ReadWriteOnce claim does.
- **Snapshots are backups.** One is taken after a sign-in and at most daily while the login is in use, and the last two are kept; DigitalOcean allows one snapshot per volume per 10 minutes, and a stop that waited for that window held its droplet 449 s. A host stop never waits on a snapshot: the hub detaches, deletes the droplet, and snapshots the detached volume later. Snapshots are also the source for non-exclusive readers and for moving a login.
- **`exclusive`.** True is the default for Claude Code and Codex: at most one host at a time. False lets readers mount volumes made from the latest snapshot on other hosts; the host holding the login's own volume is the writer, readers never write back, and their volumes are deleted at their host's stop. A non-exclusive subscription login is the human's responsibility.
- **A login belongs to a region.** Volumes and their snapshots cannot leave it; a pool in another region needs its own logins.
- **Per harness** (Q-1520 §2).
  - Claude Code: a sign-in per login over `ssh -t`, a new device for the account, `exclusive = true`. No setup-token and no copy of a Claude login is ever held by cland.
  - Codex: the same through `codex login --device-auth`, `exclusive = true`, and one login per account by default. One ChatGPT account keeps one login in use at one place at a time: a newer login signs out the account's other places, and the human's Mac counts as a place (openai/codex#17340, #22577). A second login of the same account is the human's deliberate choice, which the hint below names. A Codex login always starts in an empty home, with `cli_auth_credentials_store = "file"`.
  - OpenCode: the Go key as a `key` login, on any number of hosts.
  - Anthropic and OpenAI API keys: optional `key` logins, billed per token.
  - Nothing cland starts ever runs `codex logout`, `/logout` or `claude auth logout`, and hosts carry no stray `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `CODEX_API_KEY` or `CODEX_ACCESS_TOKEN`.
- **A `key` login** is a static key the human hands to cland: read from stdin or a hidden prompt, as `cland secret set` reads, and stored AES-256-GCM in `.cland/auth/<login>.key` with the store key from a known `[auth]` section of `.cland/secrets.toml`; the strict secrets reader (`hub/src/remote/secrets.ts`) and `cland secret` learn that section, since the prototype's hub would not start with it. A key reaches a host only in the spawn environment of the harness that uses it, sent over `agent.sock`; never in argv, a file on the host, a process row, `hub.db`, a log, the journal or a frame. A key login has no volume and no `exclusive`.
- **Binding.** A host needs one bound login per harness of the roles placed on it; a role's `account` in `roles.toml` narrows the choice to logins of that account (assumed; with no account, any login of the harness). For a new host the scheduler picks a free login and attaches its volume while the host provisions: attach needs only an active droplet, about 35 s after the create call, and provisioning takes longer, so a cold host's logins add no wait. On a running host a bind adds 8 to 10 s per harness; a launch on a host already holding the login, or with a key login, takes 2 to 5 s. A host's logins are released in parallel, and a release first ends every process using the login disk, cland's or not: OpenCode 2's `opencode serve --service` held its home open and left a stale mount.
- **Capacity.** Placement asks each host for a verdict per harness: serves, can bind, signed out, or no login. A pool's effective size is min(`max_hosts`, free logins of its scarcest harness). A launch blocked on logins waits as "waiting for a login <harness>", the Coordinator sees it in Agents, and the human gets one card per wait: "Not enough <harness> logins. Create one?". `cland host status` and the workbench row show the logins in use.
- **The login-disk helper.** Mounting needs root, so the image carries one privileged helper, `cland-auth`, run through sudo with strict arguments (mount, unmount, freeze, thaw; only volume names and `/cland/auth/<x>` paths). The host agent stays unprivileged.
- **Signing in.** `cland login add` boots or reuses a host of the pool, creates an empty login disk, and opens the harness's own sign-in over `ssh -t` in the human's terminal; on success the hub snapshots the disk and marks the login `ready` (22.4 s with a host up, 206 s on a fresh pool). Logins can be created ahead of pool growth. From the web and the remotes the sign-in is a card: the hub runs the sign-in on the host and shows its link and code; for Claude Code, which prints a link and takes a pasted code, the card's free answer carries the code back to the sign-in prompt (assumed; Codex's device code needs nothing back).
- **Signed out.** A harness reporting a dead login (Claude Code `authentication_failed`, `Login expired`, `OAuth token revoked` or a 401; Codex `refresh_token_reused`, `codexErrorInfo: "unauthorized"` or a 401; OpenCode `provider.auth`) marks the login `signed-out`. Placement then skips that host for that harness, the sessions already there keep running, and the human gets a "sign in again" card. `cland login signin <n>` re-runs the sign-in on the same host and the same volume, and snapshots under `fsfreeze`. A second `signed-out` of one account within a day adds the hint "This account seems to allow one sign-in: set exclusive or add an account."
- **Limits stay per account.** A limit-hit signal marks the account limited as v0.1.2 §3.13 decides, on every host and on the Mac; there is still no rotation across accounts. A provider's per-IP limit can look like an account limit: the free OpenCode model refused turns per egress IP, and the hub's limited mark then held launches on every host.
- **Operations** (Q-1520 §5): `cland login add <harness> [--name] [--pool]`; `cland login list` with name, harness, account, exclusive, state, host, region and last sign-in, and the capacity per pool and harness; `cland login signin <name>`; `cland login remove <name>`, which deletes the volume and its snapshots and is refused while the login is in use; `cland login snapshot <name>`. The same on the web's hosts view (§3.9), and the add, sign-in and "create one?" flows as cards in Telegram and Discord. A login card is a card the hub raises; answering it acts as the human through the hub, and the remotes' authority table of v0.3 §3.1 gains no request (assumed).
- **Reconciliation at start.** The hub lists the provider's volumes at start and frees a login whose host died, for instance at the watchdog's deadline, rather than leaving it `in-use` (inferred in Q-1518, not tested; verified in the live run).
- **Open points for the live run** (Q-1520 §3): whether a live Claude Code or Codex process picks up re-signed tokens without a relaunch; if not, `cland login signin` relaunches that host's sessions of the harness in their worktrees.

### 3.8 Users and sign-in modes

Decided in Q-1527 §1 to §7.

- **Two modes.** `[auth] mode = "single" | "users"` in `.cland/config.toml`, default `single`, chosen at setup. Single mode is today's, unchanged: one human identity, the one-time web link, the cookie. Switching from single to users creates the first user from the current identity, named from git's `user.name`; the only way back is `cland auth reset`. The `[auth]` table of `config.toml` is not the `[auth]` section of `secrets.toml` (§3.7).
- **A user** is a row of a `users` table in `hub.db`: id, name, display name, role, state and creation time; `admin` is the only role. Everything that says "the human" today gains a `user_id`: the human's messages, ask answers and approvals (the outcome records who answered), Telegram and Discord pairings, web sessions (a cookie maps to a user), and artifacts a human created. Deliveries to agents carry the author's name, so the Coordinator can tell people apart.
- **Creating and signing in.** An admin creates a user with `cland user add <name>` or from the web and gets a one-time invite link (assumed lifetime 24 hours). The user registers a passkey (WebAuthn) as the primary method, with a password as the fallback for devices without passkeys; both are built on Node's own crypto, since no dependency is added without the human's approval (assumed: WebAuthn verification and password hashing with `node:crypto`'s scrypt, no library). OIDC (Google, GitHub) and SSO wait for 0.4.x.
- **Neovim and the CLI** stay local trust through the hub socket. In users mode the CLI acts as the first user by default, and an admin can pass `--as <user>`; the stand-in `--as` that `cland topic answer` already takes then names a user (assumed).
- **Remotes in users mode.** A pairing is made by one user: the code from `/start` or `/cland pair`, approved by an admin from the inbox as today; one chat is one user. General is mirrored to every paired user, the Coordinator's asks reach everyone, the first answer wins, and the outcome shows who answered. Several people in one Discord channel are told apart by their Discord user ids; unpaired ones are ignored, as in v0.3.
- **Room for roles.** A `roles` table holds the one role `admin`. Permission checks happen in one place: the web edge's authority table (`hub/src/hub/web-authority.ts`) gains a user-role column, so that `viewer` or `operator` later are rows, not a refactor. For now every user may do everything. The hub journal records the `user_id` of every human action.
- **Deferred:** roles other than admin, per-user notifications and inboxes (one inbox serves all), personal settings, OIDC and SSO, deleting a user with a transfer of their pairings, and user management from Telegram.
- **Why in 0.4.0.** The users epic is independent of hosts and runs in parallel: shape B is pointless without it, since a web behind an Ingress must admit more than one person, while shape A can live without it.

- **The Hosts row.** The web's Sessions area and Neovim's sessions panel get a Hosts row beside Remotes, one line per pool: "agents 2/4 hosts · 7/16 slots · logins claude 2/3, codex 1/1". It turns red at once for an unreachable host or a provider failure, and expands to the host list: id, size, region, uptime, sessions, price per hour and spend today. In the web the expanded row is the hosts view, which also lists the logins with their actions: add, sign in again, remove and snapshot (assumed: a view inside the Sessions area, not a new rail area).
- **Session rows** name their host. Waiting launches show as status lines in both inboxes with their current reason (§3.5). A host session's attach in Neovim runs the `ssh -t` attach of §3.2.
- **Commands.** `cland host list`, `status`, `stop <id>`, `destroy <id>` and `prepare [<pool>]` on the hub's machine, beside `cland login` (§3.7) and `cland user` and `cland auth` (§3.8). `destroy` deletes a host at once, for a host the hub cannot reach; `stop` releases its logins first (assumed distinction).

In users mode it reports the mode and the number of users and admins (assumed).

Both default to No with `--yes`, as the remote step does.
- **The onboarding tour** gains a stage on agent hosts (assumed).
- **Docs.** Pages on hosts, pools and logins, and on users and sign-in modes; a multi-user section in the web-and-phone page; a price table in the docs with the date it was checked; and the Kubernetes install page in 0.4.x with shape B.

### 3.10 Shape-B readiness in 0.4.0

Decided in Q-1521 §7 and Q-1522 §1; the hazards come from Q-1516.

0.4.0 carries only the hub changes shape A needs and shape B must not contradict:

- **The hub lock gains a host identity and a heartbeat.** `.cland/hub.lock` stores a pid and its `ps` start time (`hub/src/hub/lock.ts`); a second container on the same volume cannot see that pid in its own PID namespace and would break a live lock, and two hubs would then share one SQLite file. The lock records the hostname and the boot id beside the pid, and refreshes a heartbeat; a lock written by another host identity is never broken while its heartbeat is fresh. On the Mac nothing changes for the human.
- **PVC-safe HOME and paths.** Everything the hub keeps under `HOME`, the spend ledger first, resolves through `XDG_STATE_HOME` or `HOME` so that both can sit on one volume, and no path the hub writes assumes macOS. `procps` stays a declared dependency, since the lock calls `ps`.
- **Secure cookies under an https origin.** The web edge marks the session cookie `Secure` whenever `[web] origin` is `https` and the Host matches it, not only when `/auth` carries a matching `Origin` header, which browsers omit on a top-level GET navigation.
- **The transport layer with `ssh` only.** Providers and pools name their transport; `ssh` is the only value 0.4.0 accepts, and `outbound` is refused with a message naming 0.4.x. A transport contract test runs against `ssh` and the fake transport, and names the four host-side sockets as the contract, so a second carrier can pass the same test (assumed split: the SSH carrier itself is built in §3.2's epic).
- **The executor's DELETE 404 fix** of §3.4.

### 3.11 Shape B in 0.4.x

Decided in round 1 (decision 11, amended to a StatefulSet), Q-1516 and Q-1521 §1 to §6, with the image audit's amendment.

- **The hub in a cluster.** One replica of a StatefulSet, never a Deployment (which starts the replacement while the old pod is still terminating), with no multi-tenancy. A ReadWriteOnce block-storage PVC at `/cland` holds `.cland/`, the project root, the territory and the hub's `HOME`; SQLite stays unchanged and never sits on a network filesystem. Readiness comes from `cland hub status`. No PodDisruptionBudget: a node drain is a short planned outage.
- **The distributable.** One Helm chart, `cland`, in the repository under `deploy/helm/`, published with each release as an OCI artifact in GHCR beside the multi-arch (amd64 and arm64) image `ghcr.io/kealman/cland`. Values: the image, the PVC size, the Ingress host, the host pools and the secret names. No kustomize. The image follows the one recipe of §3.4: Node 24, git, procps, the harnesses, and nothing project-specific; Neovim and Chromium are not in it (the image audit amends Q-1521 §1, which listed both). A project that needs its own packages in the cluster builds an image from the published one with its `[verification] provision` hook (assumed).
- **Agent pods.** A `kubernetes` host provider creates one bare pod per host from the same image, with the host agent as its entrypoint, no systemd and no sidecar. The hub's ServiceAccount has a namespace Role on pods, pods/exec and pods/log only. No fixed pool is declared in the chart, since a StatefulSet scales down from its highest ordinal regardless of live sessions. Login disks are one PVC per login, ReadWriteOnce giving `exclusive` naturally.
- **The `outbound` transport.** Kubernetes uses it from the start: the host agent connects to the hub's in-cluster Service and relays the four host-side sockets over that connection; `ssh` stays for VM providers. This amends Q-1516's SSH to the pod IP, and needs an ADR 0003 amendment in 0.4.x for an in-cluster listener reachable from agent pods only.
- **Reaching the hub.** The web through an Ingress with TLS from cert-manager and Let's Encrypt, behind Traefik or another maintained controller (ingress-nginx was retired in March 2026), with one-time links; `cland web` in a cluster prints the Ingress host. Telegram and Discord as today. The Neovim workbench stays a local client: `cland attach-cluster <context>` holds a `kubectl port-forward` to a new, optional loopback TCP listener of the hub's CLI protocol in the pod and starts the human's local Neovim against it; the Mac's `cland` CLI uses the same listener. Session attach runs through `kubectl exec -it`. The docs list what does not work against a cluster hub: `hub start` and `stop`, a laptop's `init` and `setup`, opening a browser, and localhost OAuth callbacks.
- **Secrets and tests.** A Kubernetes Secret holds `secrets.toml` (the messengers, speech, the `[auth]` store key and key logins) and another the DigitalOcean token for test droplets. The droplet executor runs from the cluster as today, with egress to the DigitalOcean API and SSH out; there is no in-cluster executor on a node group in 0.4.x. The hub pod runs no suites. The droplet watchdog dies with the hub's container, so the hub re-arms it on restart, and it may become a Job.
- **Backup and upgrade.** PVC snapshots on the chart's schedule where the CSI driver supports VolumeSnapshot; a `cland backup` to object storage is deferred. `helm upgrade` with a new image is a hub restart, which agent pods and their connections survive; `cland update` runs in the pod.
- **The first live run of shape B** is on DOKS, whose token and region exist; Hetzner follows when it can be ordered.
- **Cost per month** for the hub at 1 vCPU and 2 GiB, two agent pods at 1 vCPU and 2 GiB each, and a 20 GiB PVC (Q-1516, checked 2026-10-31, without VAT; the agent pod sizes were assumptions before the Linux measurements of §3.4):

### 3.12 Security and secrets

Decided in round 2 (decision 9), round 4 (decision 6), Q-1515 §4, Q-1520 §4 and Q-1521 §5; the ADR amendments follow from them.

- **What never reaches a host:** the host provider's token and the DigitalOcean token, the Telegram, Discord and ElevenLabs keys, the project's hub secret, GitHub credentials, the `[auth]` store key, `hub.db`, and the human's own Mac logins. A provider token never leaves the hub's machine.
- **What a host gets:** its lease SSH key and pinned host key through user-data; its per-host secret in its remote `hub.json`; its bound login disks, mounted, unread by cland; and the value of a `key` login only in the spawn environment of the harness that uses it. In shape B only public keys go into pod specs; the rest travels over the transport after connect, since anyone who can read a pod can read its environment.
- **ADR 0003 amendment** (in the transport epic). The hub gains a spoke edge on a Unix socket under `.cland/run/` and a per-host git socket; hosts reach the hub only through these sockets and `hub.sock`, forwarded over the hub's own SSH connection. Nothing new binds a network address on the hub's machine; the web edge stays the only one.
- **ADR 0004 amendment** (in the transport epic). The territory is served to hosts by `git daemon --inetd` through per-host sockets; a host may push only to task branches leased to its sessions, never delete a ref, and never move `dev` or `main`; item branches are created in the territory. The bare repository stays local.
- **ADR and spec v0.1.2 §3.13 amendment** (in the logins epic): cland stores the keys the human enters through stdin and the metadata of `disk` logins (names, volume and snapshot ids, states); it never reads the contents of a login disk and never keeps a harness's session tokens. The local registry stays names and paths only. §3.14's provider-agnostic interface holds: the host provider interface is not built on SSH, and the transport is a separate layer.
- **Shape B:** hub secrets in a Secret created by the human, never in the chart's values; k3s installs use `--secrets-encryption`; agent pods get no ServiceAccount token and no Secret access; a NetworkPolicy admits the hub's listener from agent pods only (assumed for `outbound`).

### 3.13 Hygiene

From the prototypes' rules and the standing preferences of the map.

- **Tests on fakes.** Every epic's tests and QA demo run on a fake host provider and a fake transport in the suite: the same interfaces, with hosts as processes on the same machine in their own directories and sockets, and a fake harness whose login is a file it rotates on every turn (Q-1518). No test creates a real droplet, volume or key, so the suite runs on droplets as it is.
- **One live run** before the release, with the human (§4).
- **Secrets.** A token or key never appears in argv, where every session can see it, in a frame, a log line, an error, a journal record or an artifact; the v0.3 redactor covers host and login output.
- **Reaping.** Keys and volumes carry the same tags as hosts (§3.4), and the hourly lost-work check reads them.
- **The Mac's Codex login.** The docs warn that `codex login` on the Mac over existing credentials may sign out the account's hosts.
- **Branches.** `research/*` and `prototype/agent-host` stay on `origin` and are never merged; the build may read the prototype's code and follows this spec test first.
- **Kill nothing outside cland's own.** A host's release ends processes on that host's login disks; nothing on the Mac is signalled for a remote row.
