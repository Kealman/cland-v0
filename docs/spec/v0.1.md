# cland v0.1

Status: complete (2026-10-09). Planned by the v0.1 wayfinder map (tracker item T-81): each section is one resolved ticket. The epics are tracker items labelled `v0.1` (section 4).

## 1. Purpose

v0.1 makes cland scale past one Coordinator over a flat crew and makes the workbench show less at once: a release above epics, explicit item status and order, a session hierarchy with crew configuration and event subscriptions, an epic plan, visibility levels, a session for the human, and the panel, palette, thread and graph work the v0 run asked for. The human's notes behind it are summarised in the map's Notes.

## 2. Vocabulary

Terms are defined in `GLOSSARY.md`. v0.1 adds or changes: Release (now an item as well as the act), Unscheduled, Status, Rank, Aide, Criterion, Layer, Artifact (a file or a folder), Lead, Coordinator (the lead of the root), Crew, Pool, Event, Subscription, Plan, Stage, Lane, Palette.

## 3. Decisions

### 3.1 Item hierarchy: a release above epics

Decided in map ticket T-87 on 2026-10-09.

- **Levels.** Container kinds come from `levels` in `.cland/config.toml` (`[tracker] levels = ["release", "epic"]` by default), ordered top-down. Leaf kinds stay fixed: `task`, `question`, `spec`. `map` stays outside the ladder. A map's children are questions and wayfinder tasks (`wayfinder:task`, kind `task`); the hub refuses any other kind under a map (decided during T-118).
- **Parenting rule**, enforced by the hub on create and on link: a container's parent is the container one level above it (an epic under a release) or none; a leaf's parent is any container or none. Any item may have no parent. A parent that breaks the rule is refused.
- **The release item.** Kind `release`. Frontmatter `version` (semver without the `v`): optional at creation, required to release. Body: the goal, and a `## Notes` section whose text opens the release notes. Its children are its contents; there is no separate list.
- **Releasing.** `cland release` takes an optional `--item T-n`. With an item: the tag is `v<version>`; the notes are the item's notes section, then its epics with their one-line deliverables, then the commit subjects as today; on success the hub comments the tag on the item and closes it. It refuses when the item has open children or no version. Without an item, today's behaviour stays, so a hotfix needs no planning.
- **Closing a container.** A release or an epic with open children cannot be closed: the hub refuses, without a force flag; close or move the children first. T-19 stays open as the parent of the v0 follow-ups.
- **Tree and scope.** The items panel folds by level: closed releases and epics are folded, the current release is unfolded. The current release is the open release with the lowest version unless the human picks another; the choice persists in `.cland/ui.json` and its name shows in the top bar. The items panel, the board and the task graph show the current release. Items that belong to no release form the "unscheduled" group at the bottom of the panel; the "all" filter shows everything.
- **Tools.** `cland task create --kind release --version 0.1.0`; `--parent` is validated by the hub; `cland task list --under T-n` lists a subtree; `cland task view` shows the path release › epic › task in its header. The MCP task tools mirror the CLI. The set of container kinds is no longer hard-coded; the leaf kinds are.
- **Migration.** The first build ticket of v0.1 creates the v0.1 release item; the epics labelled `v0.1` are re-parented under it. No release item is made for v0.0.1; the v0 epics stay unscheduled.
- **Not a level.** Sprints and milestones are groupings across the tree, not tree levels; they stay outside v0.1 unless the cut ticket says otherwise.

### 3.2 Item status and order

Decided in map ticket T-88 on 2026-10-09.

- **Status is explicit.** A task carries `status` in its frontmatter: `backlog` (the default at creation), `planned`, `in progress`, `review`, `qa`, `ready` (the verdicts the gate needs are in, the merge has not happened) or `done`. State stays `open` or `closed`; done tasks are closed. Containers have no status: the panel shows their children's progress. Questions and specs have none. "Blocked" is a glyph derived from open blockers and sits over any status.
- **The hub moves it on events.** A claim by an Implementer sets `in progress`. A Reviewer or QA does not claim: it takes a verifier hold on the item, beside the Implementer's claim and tagged with its role; a Reviewer's hold sets `review`, QA's sets `qa`. The merge gate refuses a verdict only from the holder of the Implementer's claim (decided on 2026-10-09 with T-98). A verdict that is not clear sets `in progress`. When the verdicts the merge gate needs are all clear, the hub sets `ready`. A merge or a close sets `done`; a reopen sets `backlog`. The Implementer sets `review` when handing the item over (the role clause says so). The Coordinator and the human may set any status with `--status`; a manual status edit by any other session is refused.
- **Rank orders siblings.** A task or an epic carries `rank`, a sparse integer (10, 20, 30) that orders it among the items with the same parent. `cland task rank T-n --top`, `--before T-m` or `--after T-m` renumber only what they must; the items panel moves an item among its siblings with keys the panels prototype picks. Lists sort by rank, then id. The Coordinator's clause reads: the next item is the lowest-ranked unblocked `planned` task in the current release. There is no priority flag: marking an item as a priority is moving it to the top. The `high` label retires.
- **Filters and columns in these terms.** "In work" is `planned`, `in progress`, `review`, `qa` and `ready`. "Needs you" is unchanged. "Done" is the done tasks of the current release. The board's columns are the statuses. The vertical board in the items panel (prototype T-99) shows the sections in progress, review, qa, ready and planned, folds backlog and hides done.
- **The merge gate is unchanged.** It still requires the clear verdicts it requires today; `ready` only reports that they are in.
- **Bug T-80.** Fixed by the "in work" definition above. Until status exists, a stopgap that also shows items with a pending verdict or the `qa-required` label is acceptable.
- **Records.** GLOSSARY gains Status and Rank. ADR 0002 stands: the two fields live in the item file, the hub indexes them.

### 3.3 The human's own session: the Aide

Decided in map ticket T-92 on 2026-10-09.

- **A role, not a special case.** `Aide` is a non-exclusive role: a session that works for the human alone, and there may be several. Role broadcasts and `all` never reach an Aide; it is addressed by name only. An Aide is never a Coordinator: it cannot launch, stop or resume sessions, merge, hand over, resolve a topic's wait, or ask the human.
- **Tools.** The tracker in full (`task.create`, `task.edit`, `task.close`, `task.link`, `task.comment`, `task.claim`, `task.view`, `task.list`), artifacts (`artifact.create`, `artifact.promote`), `send` to any session by name and to topics, `topic.create`, `history`, `who`, `status`. No `ask`, `resolve`, `session.*`, `merge`, `role.handover`, `release`, `sync` or `push`. A claim is allowed: when the human tells an Aide to take an item, it works like an Implementer, in that item's worktree.
- **Its voice is the human's.** Its messages go out as the session (`aide-1 [Aide]`). The crew's role clauses say that an Aide speaks for the human, decisions included: the human puts an Aide into context deliberately so that it can decide on their behalf. Approvals inside a harness TUI and asks in the inbox are still answered by the human, because an Aide cannot reach them.
- **What it receives.** Deliveries addressed to it by name, and its role clause; no broadcasts, no Agents notices, no asks. It reads topics and history on request with `history`.
- **Launch and place.** One palette action and a key (chosen by the panels prototype) launch an Aide with the defaults of `[roles.aide]` in `roles.toml` (Claude Code and the human's model by default), the project root as its working directory and an optional brief. It shows in the sessions panel in a "yours" group at the top and attaches in the centre like any session. There is no cap on the number of Aides.
- **Records.** GLOSSARY gains Aide. ADR 0001 covers it: a role held by the hub and delivered as an event.

### 3.4 Acceptance criteria that live

Decided in map ticket T-93 on 2026-10-09.

- **Format.** Criteria stay a list under `## Acceptance criteria` in the item file, but structured: each has a stable id and carries its marks as sub-items. The hub parses the section, returns `criteria` in `task view --json`, and writes the marks itself; the checkbox mirrors the done mark. The file stays the source of truth (ADR 0002).

  ```
  - [x] C1. The clause arrives again on reconnect
    - done: impl-57 · 2026-10-09T10:00Z
    - verified: qa-12 [QA] · run q-0117 · 2026-10-09T11:00Z
  ```

- **Marks and who sets them.** `done` is set by the Implementer holding the claim, or by the Coordinator, the human or an Aide. `verified` is set by a Reviewer or QA, either on its own (`task.criterion verify C1`) or inside a verdict (`--verified C1,C3` or `--verified all`). `failed` is set by a verifier with a note; it removes the done mark and returns the task to `in progress`. The Coordinator, the human and an Aide may add, edit and remove criteria; ids are never reused.
- **The merge gate.** It refuses while any criterion is not done, or not verified by at least one verdict. A clear review with `--verified all` is the usual path. The epic plan may require that specific criteria are verified by QA.
- **Display.** The item view lists the criteria with glyphs: ○ open, ◐ done, ● verified, ✗ failed, and their marks. The items panel row and the board card show "verified/total" for tasks in work.
- **Migration.** Existing checkboxes read as criteria without marks; ids are assigned the first time the hub touches the section (a first mark or edit).
- **Records.** GLOSSARY gains Criterion. No ADR.

### 3.5 Visibility levels

Decided in map ticket T-94 on 2026-10-09.

- **Four layers.** Everything the workbench shows sits in one of four layers: `now` (needs the human, or changes their plan), `watch` (worth seeing, can wait: one key away, or folded with a count), `background` (agent-to-agent traffic and bookkeeping: shown only when unfolded on purpose, or in the Agents log) and `archive` (closed and old: only on an explicit request, through the palette or an "all" filter).
- **Default placement.**

  | Surface | now | watch | background | archive |
  |---|---|---|---|---|
  | Messages | addressed to the human; asks | the Coordinator's reports to the human | agent to agent | older than 7 days |
  | Inbox events | ask, approval, a topic waiting for the human, a verdict not clear, a session died | a clear verdict, a release, an import, a long idle | everything else, in the Agents log only | |
  | Sessions | waiting, busy; the human's Aides always | idle | stopped | |
  | Items | the current release's tasks in work (in progress to ready) | planned | backlog, unscheduled, done | closed releases |
  | Artifacts | | the human's own; sent to the human by the Coordinator | agents' reports (author Implementer, Reviewer or QA) | archived |

- **How surfaces show them.** Every surface shows now and watch. Background sits behind a fold ("more (12)") or an unfold key; archive appears only on an action. The top bar counts now only. The inbox never shows background: its home is the Agents log. In a thread, a run of agent-to-agent messages folds into one line ("impl-3 → rev-1 · 3 messages") that opens as a fold. The items panel's filters are expressed through the layers.
- **Overrides.** The human may pin (raise to now) or mute (lower by one layer) a topic, a session or an artifact; the choice persists in `.cland/ui.json`. Agents raise a thing to now only by addressing the human or asking; there is no "important" flag. The defaults can be overridden per project by a `[visibility]` table in `config.toml`.
- **Boundaries.** This section decides the layers and the rules. The thread prototype (T-97) and the panels prototype (T-99) decide how folds, counts and colours look.
- **Records.** GLOSSARY gains Layer. No ADR.

### 3.6 Artifacts as a workspace

Decided in map ticket T-95 on 2026-10-09.

- **File or folder.** An artifact is a file, or a folder with an entry file (the first `.md`, or one named at creation). Both carry an `A-<n>` id. Files inside a folder are not artifacts: the hub does not index them and lists them on request. A prompt the human prepares over days is one folder artifact.
- **Lifetime.** Artifacts authored by the human or an Aide are never archived or deleted automatically; for them, archive is a layer, not a deletion. Agents' artifacts live with their topic and are swept after the retention period as today, unless kept: the `kept` flag exempts an artifact from the sweep and raises it to the watch layer.
- **The browser.** A centre view "Artifacts": a tree with the sections mine (the human's and Aides', folders first), this topic, kept, by role (Coordinator, Implementers, Reviewers, QA; folded as background) and archived (folded). Keys: Enter opens a file or unfolds a folder; `n` creates a file or a folder with a kind; `m` moves into a folder; `s` attaches to the composer; `p` promotes into the repository; `k` keeps; `d` archives; `x` deletes after confirmation, the human only. The `␣a` picker and the palette's `~` prefix stay for quick opening.
- **Tools.** `artifact.create` accepts a directory path or `folder: true`. New: `artifact.keep`, `artifact.move`, `artifact.archive`. The CLI gains `cland artifact new | open | keep | move | archive | promote`. Agents may read any artifact; they cannot change the human's or an Aide's.
- **Editing in place.** An artifact opens in a buffer and saving the buffer is the artifact; the files of a folder likewise. Edits made with another editor are fine: the index does not depend on them.
- **Records.** GLOSSARY rewrites Artifact. No ADR.

### 3.7 The hierarchy of sessions: leads on the item tree

Decided in map ticket T-89 on 2026-10-09, from the research of T-82 (the v0 journal), T-83 (harness teams) and T-84 (prior art).

- **One tree.** The management hierarchy is the item tree of §3.1. Sessions attach to its nodes as leads: the Coordinator leads the root (the project), a session of the role `Lead` leads an epic or a release, and an Implementer that claims an item leads that item implicitly. There is no separate tree of sessions and no launched-by link; pooled Reviewers and QA serve many nodes.
- **Routing.** An event or a report about an item goes to the nearest lead up its chain: the item's lead, then the epic's, then the release's, then the Coordinator, then the human. A message with no item goes to the Coordinator. The address `@lead T-n` resolves to the current lead of that node. The human addresses the Coordinator by default and may address any lead directly.
- **Asks go up one level.** A lead answers an ask from below, or forwards it up unchanged with one call; only the lead of the root asks the human.
- **Permissions by level.** A Lead plans its epic (the epic plan section), launches and stops sessions for its items, requests review and QA from the pools, and merges its epic's items. The Coordinator keeps releases, sync and push, the merge of unscheduled items, and the launch of Leads. An item's lead requests review and QA itself and reports ready or blocked. A handover moves the lead of a node together with the handover note.
- **Growth.** The crew configuration (the crew section) names the levels that get dedicated Leads, for example `leads = ["epic"]`; an empty list is today's flat shape. Item leads are always implicit. A project starts flat and adds a level when its Coordinator saturates: in the v0 run, 740 deliveries landed on one Coordinator and an item lead per item would have taken up to 87% of them.
- **Regardless of hierarchy** (inputs to the event subscriptions section): progress notes fold into the next turn instead of starting one; subscriptions replace polling and pure relays; idle and death notices reach the node's lead, not only the Agents log.
- **Names.** Lead is both the role and the claim on a node ("the lead of T-12"); the Coordinator is the lead of the root; the route is the lead chain. Not manager, supervisor or commander.
- **Records.** GLOSSARY gains Lead and rewrites Coordinator. ADR 0006 records that the hierarchy is the item tree and leads are hub-held claims on nodes.

### 3.8 Crew configuration and session reuse

Decided in map ticket T-90 on 2026-10-09, from the research of T-83 (harness teams) and the hierarchy of §3.7.

- **Home.** `.cland/crew.toml`, committed: the staffing policy and nothing else. `roles.toml` keeps what a role is: its clause, skills, exclusivity, launch defaults (harness, model, effort, sandbox) and permissions.
- **Shape.** At the top, `leads` names the levels that get dedicated Lead sessions (§3.7); an empty list is the flat shape. Per role, a table `[crew.<role>]` with `policy`: `per-item` (a fresh session per item, which leads that item), `per-group` (one session per group of items named by the epic plan), `pool` (up to `size` sessions, reused) or `singleton` (one per machine); `keep_context` (reuse a session across items, or stop and relaunch); `stop_after` (`merge` or `never`); `subagents` (whether the role may delegate inside its harness; the role clause enforces it, and the sub-agents' cost counts to the session). Harness and model stay in `roles.toml`.

  ```toml
  leads = ["epic"]

  [crew.implementer]
  policy = "per-item"
  stop_after = "merge"

  [crew.reviewer]
  policy = "pool"
  size = 2
  keep_context = true

  [crew.qa]
  policy = "singleton"
  ```

- **Enforcement.** The hub checks the policy at launch: `session.launch` refuses a launch beyond `size` or a second singleton; for a `pool` role with `keep_context`, a launch request for an item returns an idle pool member instead of a new session; `per-item` sessions stop as `stop_after` says. Within those bounds the Coordinator or a Lead decides.
- **Editing and display.** The Coordinator, a Lead and an Aide edit the file directly after talking to the human; the hub reloads it on change and refuses a broken file with a notice, keeping the last good version in force. The CLI gains `cland crew show` and `cland crew set <role>.<key> <value>`. The sessions panel header shows a one-line summary ("impl per item · rev pool 2 · qa 1 · leads: epic"). There is no editing UI.
- **Defaults from `cland init`.** `leads = []`; implementer `per-item` stopping after merge; reviewer `pool` of 1 with `keep_context`; qa `singleton`; aide unlimited; `subagents` allowed for the Coordinator and Leads only.
- **Records.** GLOSSARY gains Crew and Pool. No ADR.

### 3.9 Event subscriptions

Decided in map ticket T-91 on 2026-10-09, from the v0 journal (T-82) and the hierarchy of §3.7.

- **Tools.** `subscribe` takes a subject (a session, an item, a topic, a role, or a node of the item tree with its subtree) and a list of events; `unsubscribe` removes one; `subscriptions` lists the caller's. Events: `session.state` (idle, busy, waiting for human, waiting for approval, died, launched, stopped), `task` (status changed, claimed, verdict posted, criterion marked, closed), `topic` (waiting for human, closed), `usage` (a threshold crossed), `artifact` (created, shared). Messages are not events: they are deliveries already.
- **Delivery.** An event arrives as a delivery from `hub` with a one-line body ("event · session.state · impl-3 idle 30 min · T-58"), through the same queue, stages and injection as a message. A subscription's `digest` is `turn` by default: events accumulate and arrive as one message when the session's next turn starts; `now` delivers at once, by steering where the harness can.
- **Progress notes.** `send` gains a `kind`: `progress` never starts a turn, waits for the next one and arrives in one digest; `report`, `question` and `decision` start a turn. Role clauses tell agents to mark progress notes. In the v0 run this would have removed up to 59% of the Coordinator's turn starts without touching the adapters.
- **Defaults from the hierarchy.** A lead is subscribed to its node's subtree, less the subtrees that have their own lead: the states of the sessions working on its items (died, waiting for approval, idle longer than `idle_minutes`) and the task events of its items (verdict, status change, closed). Explicit subscriptions widen this. A session's death or long idle therefore reaches its lead, not only the Agents log.
- **Hygiene.** Equal events on one subject within 60 seconds coalesce into one with a count; a digest holds at most 10 events and summarises the rest ("and 12 more"); subscriptions die with their subscriber; a subject's death closes the subscription with a final event; events have their own limit and do not count against the 30-messages limit.
- **The human.** The inbox shows nothing of subscriptions (background layer); `cland hub subscriptions` lists them; the journal records event deliveries like messages.
- **Records.** ADR 0007: events reach sessions as deliveries, digested at turn boundaries. GLOSSARY gains Event and Subscription.

### 3.10 The epic plan

Decided in map ticket T-96 on 2026-10-09, on top of status and rank (§3.2), the crew (§3.8) and the criteria (§3.4).

- **Shape.** A plan is an ordered list of stages. A stage holds parallel lanes; a lane is an ordered list of items that one session takes (with the crew policy `per-group`) or one session per item. The QA policy sits on the stage: `scope` `none`, `affected` or `full`, and `when` `per-item` or `after-stage`; an item may override it. With `after-stage`, the stage's items merge on review alone and one QA run on `dev` after the stage closes it. Review is always required.
- **Home.** A `## Plan` section in the epic's item file holding a YAML block that the hub parses and validates; a broken plan is refused and the previous one stays in force. The file stays the source of truth (ADR 0002).

  ```yaml
  stages:
    - name: schema and CLI
      qa: { scope: affected, when: after-stage }
      lanes:
        - [T-55, T-57]
        - [T-58]
    - name: panels
      qa: { scope: full, when: per-item }
      lanes:
        - [T-63, T-68]
  ```

- **Author and approval.** A `plan-epic` skill, run by the Coordinator or the epic's Lead before the epic starts. Every epic has a plan, even one stage holding everything. Human approval is configured in `config.toml`: `[plan] approval = "none"` (the default; the human is notified at the watch layer) or `"human"` (the Lead launches no session for the epic until the human approves in the plan view).
- **Tools.** `task.plan set T-<epic> --file plan.yaml` validates and writes the section; `task.plan show`; `task.plan approve` (the human or an Aide only); the CLI mirrors them as `cland task plan`. The `qa-required` label retires: an item's QA policy comes from its plan, and an item outside any plan takes `[plan] qa_default` from the config.
- **Enforcement.** The merge gate reads the item's QA policy from the plan; with `after-stage` an item merges on review and the stage closes with a QA verdict on the stage. The order of stages guides launches through the role clause; the hub does not block it. Criteria the plan marks for QA must be verified by QA (§3.4).
- **Display and change.** The plan view (mockup T-100) opens from the epic's item view, the graph and the palette; the items panel and the graph show the stage on each row ("S2"). A plan changed mid-epic goes through the same tool; the hub journals the change and notifies the human at the watch layer; merged items are not touched.
- **Records.** GLOSSARY gains Plan, Stage and Lane. No ADR.

### 3.11 The workbench panels

Decided in map ticket T-99 on 2026-10-09: the mockups `ItemsBoard`, `SessionsPanel` and `Palette` on the design canvas (mirrored in `docs/design/main-screen/`) and the Neovim prototype on branch `prototype/panels`, never merged. The human accepted the mockups.

- **The items panel as a vertical board.** Scoped to the current release, whose name sits in a chip in the top bar; `e` and `E` cycle the open containers, and only a container can be the scope. Sections in order: in progress, review, qa, ready, planned, each with its count; backlog and unscheduled are folded (`za`); done is hidden and counted in the header ("board · 12 in work · 6 done"). A row shows the status glyph, the id, a dim parent prefix ("E-5 ›"), the title, the claim or the verdict mark (✗ when the last verdict is not clear; "for Reviewer" while a review is awaited), the "verified/total" fraction (dim; green when complete; shown on planned rows too) and the blocked glyph ◌ over a planned item with open blockers. The first unblocked planned row carries a teal "next" mark. Rows sort by epic rank, then task rank. The tab row under the header filters by epic and names the epics; `1` to `5` and `f` keep the v0 filters. Keys: `K` and `J` move an item among its siblings, `T` to the top; Enter opens; `gi`, `gt` and `gs` as everywhere. An item is unscheduled when its parents reach no open container.
- **The sessions panel.** Groups yours (the Aides), waiting, busy and idle, each with its count, then one folded line "stopped (N)" (`za`). One line per session: glyph, name, role, item; the selected row expands to harness, model, state (with the command a pending approval waits on) and usage. Keys: Enter attaches, `C-v` attaches in a split, `l` launches, `a` launches an Aide (`␣A` from anywhere), `x` stops, `c` shows capabilities. The sessions chip in the top bar counts now-layer sessions only, plus the waiting count.
- **The palette.** `␣p` opens it. Without a prefix it searches objects and actions together, grouped in a fixed order (actions, items, sessions, artifacts, topics) with the cursor on the best match; the prefixes `>` actions, `#` items, `@` sessions, `~` artifacts and `/` topics narrow it to one kind; `␣a` opens it on `~`. Every action shows its key and, for a panel-local key, where it works; an action with no key says so; answering an open ask is one action per option. Enter runs or opens, `C-v` opens in a split, Tab moves to the next kind, Esc closes. Matched characters are blue; background and archive hits are dimmed.
- **Glyphs.** ◐ in progress; ◉ amber for review and qa; ◉ green for ready; ○ planned and backlog; ● done; ◌ blocked; ✗ a failed verdict; ? an open ask; ▲ waiting for approval.
- **Until the status field exists**, the prototype derives status from claims, verdicts and labels by the rules in its `vboard.lua`; the build replaces them with the field of §3.2 and the rank of §3.2 (the prototype keeps rank in a scratch file).
- **Records.** GLOSSARY gains Palette. The mockups and the prototype are the references, in the order the design README gives.

### 3.12 Focus and keys

Settled while charting, with the bindings from the research of T-85; the human accepted them on 2026-10-09.

- **Focus moves.** `C-h`, `C-j`, `C-k` and `C-l` move focus between windows in every mode, Terminal mode included, so leaving a session is a move. They reach Neovim intact from Ghostty in both of its encodings and through tmux with or without extended keys. Inside a harness's input this takes `C-j` (newline) and `C-k` (delete to the end of the line) from all three harnesses, and `C-h` and `C-l` from Claude Code and Codex; a newline is typed with Shift+Enter (cland's `<S-CR>` mapping) or Alt+Enter.
- **Leaving a terminal.** A lone `C-\` leaves Terminal mode: no harness, Ghostty or tmux binds it, and Neovim never forwards it; `C-\ C-n` keeps working. Esc always goes to the harness; no cland binding involves Esc. Meta chords are not used: through tmux they arrive as Esc-prefixed sequences that collide with Esc timing, and Option is not Alt in Ghostty by default.
- **Local conditions.** `cland doctor` warns about a Ghostty `keybind = shift+enter=text:\n` line, which turns Shift+Enter into the same code as `C-j`, and about a tty erase character of `^H`; both must go for the focus keys to work.
- **Keyboard layouts.** Normal-mode keys work in any layout through Neovim's `langmap`: cland sets it for the layouts named in `config.toml` (`[keys] layouts = ["ru"]`), one option string per layout, no per-key duplicates; typing in the composer and in a terminal is untouched. The four Ctrl chords arrive as Cyrillic letters in the kitty encoding under the Russian layout; cland maps no Cyrillic duplicates. The build checks once whether Neovim can take the kitty protocol's base-layout key for Ctrl chords; if it can, the chords become layout-independent, otherwise they stay English-only, by the human's choice.

### 3.13 The plan view

Decided in map ticket T-100 on 2026-10-09: the mockups `PlanBefore` and `PlanMidway` on the design canvas, mirrored in `docs/design/main-screen/`. The human accepted them. The plan itself is §3.10.

- **Where it opens.** `gp` on an epic, next to `gi`, `gt`, `gs` and `gb`; from the epic's item view, from a stage in the graph, and from the palette. The centre shows the plan; the items panel is filtered to the epic, with a stage tag ("S2 ›") in place of the epic prefix and an epic row on top carrying the Lead and the done count.
- **Layout.** A header with the path (release › epic › plan), the Lead (session, harness, model, state) and the plan's author and time. Then the stages top to bottom, each a box with its number and name, its QA policy line ("qa: affected · after stage · items merge on review, one qa run closes the stage"), what it delivers, and its lanes side by side as columns of item rows (glyph, id, title, claim or verdict mark, fraction; a per-item QA override under its row, "qa none · override: review is enough"). Between stages, a line saying what starts the next one; at a stage's foot, what closes it ("qa after S1 · affected · one run on dev once all three merged · qa-12").
- **Before the start.** With `[plan] approval = "human"`, an amber card "awaiting your approval · since 16:40 · no session launched" with `a` approve, `d` discuss with the Lead (writes to the Lead in the epic's topic) and `e` edit plan. The right column: the state, what approval triggers (the Lead launches one session per lane of the first stage), items and stages, implementers per stage at most, the review and QA policy in words, the QA runs and their count, an estimated QA cost placeholder, items waiting outside the epic, and an excerpt of the plan's YAML.
- **Mid-way.** Closed stages keep their marks: done items with fractions, the QA run's id and result, a progress bar. The stage in work is outlined; its lanes name the sessions and their state; a not-clear verdict shows the round. Planned stages are dimmed. A change since the human's last look is marked at the watch colour on the stage and on the item ("changed 12:40 by lead-6: T-73 moved from stage 2 · qa runs 2 → 3", with the reason) and stays marked until the human opens the view. The right column: progress (done, in review, in progress, planned; stage N of M), the gate of the stage in work, QA runs so far and to come, the plan's approval and change history, the sessions, and cost so far across the epic. Actions: `e` edit plan, `gt` topic, `gs` lead.
- **Vocabulary.** The watch colour `#c2a15e` (muted amber, with a hollow triangle for a change mark) joins the visual vocabulary.
- **Records.** The two mockups are the reference, in the order the design README gives.

### 3.14 The thread

Decided in map ticket T-97 on 2026-10-09: the mockup `Thread` on the design canvas (mirrored in `docs/design/main-screen/`) and the Neovim prototype on branch `prototype/thread`, never merged. The human accepted both.

- **Messages.** Each message has a header "sender [Role] → addressees HH:MM" with the delivery stage or the waiting state at the right. A gutter bar in the role's colour runs down every row of the message, wrapped rows included. A band sits behind the human's and an Aide's messages, the ask card and code blocks. A date line appears when the day changes. Continuation rows align with the text (`breakindent`); lines break only at spaces (`breakat` without the hyphen, so ids like T-58 stay whole).
- **Markdown per message.** Each message is parsed on its own with the bundled tree-sitter Markdown parser and conceal: headings, inline code, fenced code blocks (fences hidden, a faint language label on the first row, the block inset inside the band), lists aligned under the bullet text, links shown as underlined text. An unclosed code block cannot spill into later messages; plain text is the fallback where the parser fails.
- **Roles and layers.** Role colours: the human blue, the Coordinator teal, an Aide the human's blue as a dashed bar, Implementer violet, Reviewer pink, QA sky; amber, red and green keep their meanings. Now messages at full brightness; watch messages (the Coordinator's reports, a clear verdict) softer with a dimmed bar; a folded run is one faint line. A verdict shows its result in red or green, the criteria marks and a failed criterion's note; a clear verdict takes one row. An ask is an amber band with numbered keys and a free-answer hint; the Coordinator's ask and the artifact chip it posts next share one header. Item ids in bodies are blue, as `gi` targets.
- **Folds.** A run of consecutive agent-to-agent messages folds into one line ("impl-58 → rev-6 · 4 messages"); asks, verdicts, answers and anything to or from the human or an Aide never fold; `zo`, `za`, `zR`, `zM` and Enter open and close them. The folds are manual, because automatic folds do not update while the human types in the composer. An agent's artifact post with no addressee folds into the run around it (background layer).
- **Cost.** A new message is appended without rewriting the thread (under 1 ms at 200 messages); a full redraw costs 7 to 9 ms; the window of the last 200 messages stays.
- **Records.** The mockup and the prototype are the references, in the order the design README gives; the colours violet, pink and sky are in the design vocabulary.

### 3.15 The task graph, experimental

Decided in map ticket T-98 on 2026-10-09: the Neovim prototype on branch `prototype/graph`, never merged. The human tried it on the v0 epic and kept it as an experiment: the board stays as it is on `␣b`, the graph is an additional view, and its legibility is revisited in the next version.

- **Layout.** The items of one parent (an epic; a release once it exists) as a layered graph by `blocked_by`, layers top to bottom (a node's layer is one past its furthest blocker), parallel items side by side within a layer, edges downward with box-drawing characters, each edge on its own track, no `┼`; `o` turns the layout left to right. Edges implied by a longer path are hidden (`r` shows them). Items with no edge sit in a tray; done items fold (`d`). Node width fits the window (`+`/`-`); a layer that does not fit continues on rows marked `↳` in the gutter.
- **Nodes.** The status glyph (as §3.11; ready in green ◉), id, stage when the epic has a plan (`s` groups by stage), ◌ when blocked, the title, the claim, the latest verdict and the verified/total fraction; done nodes dimmed.
- **Keys.** `␣G` and `:Cland graph [T-n]` open it; `j`/`k` move between layers, `h`/`l` within a layer, `^`/`$` to a layer's ends, `gg`/`G` to the first and last layer; Enter opens the item; `gi`, `gt`, `gs` from a node; `p`/`P` cycle the parent; the cursor stays on its node through hub updates.
- **Known limit.** At the density of the v0 epic (22 items, 36 edges) the crossing edges read badly; what to do about it (hiding transitive edges by default, bundling, collapsing done layers, a different projection) is fog for the next version.
- **Cost.** On the v0 epic: layout 2.8 ms and draw 4.2 ms at 200 columns, 5.8 ms layout at 120 columns.
- **Records.** The prototype is the reference; the board scoping of the map Notes stands.
