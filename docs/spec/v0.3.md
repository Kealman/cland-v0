# cland v0.3: remote control through Telegram and Discord

Status: complete (2026-10-25). Grilled with the human in the cland-design session over the map M-1286 (research Q-1287 to Q-1290, the sandbox bots T-1291, prototypes Q-1292 and Q-1293, grilling Q-1294 to Q-1297); release item R-1278.

The epics are tracker items labelled `v0.3`, children of R-1278 (section 4). The earlier specs stay in force where this one is silent.

## 1. Purpose

v0.3 lets the human steer a project from a phone. A gateway inside the hub mirrors General and the inbox's needs-you rows into messenger chats paired with the project, the remotes: the human's private chat with the project's Telegram bot, and one channel in the human's own Discord server. From a remote the human writes to the Coordinator, answers asks, approves commands, and sends photos, files and voice notes; voice is transcribed through a provider seam. Planning, plan approval and every topic beyond General stay in the workbenches, and pairing approval stays in Neovim and the terminal.

Section 4 lists what waits for 0.3.x. Out of scope (the map): other messengers, speech synthesis, item topics opened from the chat, and hub, release and configuration control from the chat.

## 2. Vocabulary

New terms in `GLOSSARY.md` (Q-1294 §7, Q-1296 §13): Gateway, Remote, Pairing, Remote card, Transcript, Gap line, Outbox. Amended: General (mirrored into the remotes) and Setup (its optional remote step, §3.11). The card is a Remote card because the glossary's Card is the item's picture in the Explorer; in this spec "card" alone always means a remote card. A notice is a needs-you row shown in a remote without buttons, marked 📥.

## 3. Decisions

### 3.1 The gateway edge and its authority

Decided in round 1 (decisions 4 and 5), Q-1294 §2, §5 and §6, and Q-1296 §11, all on 2026-10-25; the prototypes Q-1292 and Q-1293 built it.

- **An edge inside the hub.** The gateway runs in the hub process, as the web edge does (v0.2 §3.7), and holds one conversation with the hub's dispatcher: it receives the frames a client receives (messages, the inbox, asks, approvals, delivery stages) and sends the requests a client sends, as the identity `human`. It is an edge of the one frame protocol (ADR 0003): no new protocol, socket or listener, and no hub secret. ADR 0003 gains an amendment that names it.
- **Outbound only.** Telegram by long polling, Discord by its gateway websocket and HTTPS; no webhook, tunnel or public address.
- **The remote's authority** is a deny-by-default table like the web's, checked before dispatch, and narrower: exactly `topic.send` (into General, or as a reply into the topic of the message replied to), `topic.answer` and `approval.answer`, plus the reads `/status` and `/inbox` need (`hub.status`, `task.list`, `inbox.list`). No session launch or stop, release, push, sync, configuration, artifact action or pairing approval. This narrows round 1's "the web table plus answers and approvals", which the prototypes used.
- **Media are the hub's own act.** The gateway turns a remote's photos, files and voice notes into artifacts through `artifact.upload` inside the hub, attributed to the human (§3.6); for the remote's authority this counts as a send.
- **`via`.** Every message, answer and approval from a remote records `via = "telegram"` or `"discord"`, which also keeps the mirror from echoing it back, and the workbench shows "via Telegram". An ask's outcome records `via` as an approval's already does, so every copy of a card names where it was answered.
- **Approvals.** Codex and OpenCode approvals are answered from a card as from the web and recorded with `via`; the inbox row shows "approved via Telegram". The card truncates the command to a safe length with "full command in the workbench". No second confirmation for dangerous commands in 0.3.
- **Failure stays in the gateway.** A remote that cannot start, or must stop, disables only itself, as a taken web port does: the hub and the other remote run on, and the reason goes to the log, `cland remote status`, doctor and General (§3.9). A bad command definition once crash-looped BCAS's hub (Q-1290).
- **State in `hub.db`**: the pairings, the waiting codes and the replies counted per stranger, the cursors (Telegram's offset, Discord's last message id and resume data), the poller lease, Discord's identify count, the outbox, and the map from chat messages to cland messages, topics and asks. Discord ids are stored as TEXT: they exceed JavaScript's safe integers, and `node:sqlite` reads 64-bit integers back lossily (Q-1293). No separate state file.

### 3.2 Remotes, pairing and identity

Decided in round 1 (decisions 6, 7 and 16), Q-1294 §1 and §9, which reversed the pairing direction to the one every messenger bridge uses (Q-1290), and Q-1296 §13; the prototypes added the details.

- **At most two remotes.** One Telegram chat and one Discord channel per project, for one human; both may be paired at once, and the mirror goes to both. A newly approved pairing replaces the old one and tells the old chat, and approving clears every other waiting code of that messenger.
- **Telegram.** One bot per project, created by the human through BotFather; the remote is the human's private chat with it. `cland remote status` prints the bot's `t.me/<bot>` link; the human opens it and presses Start.
- **Discord.** One application and bot per project, in the human's own server; the remote is the channel where the human runs `/cland pair`. Other members may read it; their messages are ignored and their clicks refused privately. Two hubs on one token would both receive every click and race to answer it, and would share the identify budget, the rate limits and every token reset (Q-1288, Q-1293).
- **The code comes from the chat.** On Start, or on `/cland pair` without an argument (answered ephemerally, so only the human sees it), the bot replies once with an 8-character code drawn without 0, O, 1 and I, the sender's numeric id, the approve command ready to copy, and "ask the project's owner to approve". A Telegram code lives one hour; a Discord code lives 15 minutes, the life of the interaction's token, so that its private reply can turn into "Approved". At most three codes wait at once, and a stranger gets at most two replies, then silence.
- **Approval in Neovim or the terminal.** A waiting code is a pairing row in the inbox ("Pair Telegram user 12345 (Name)? code …"). Approving it grants new access, as `web.link` does, so the hub accepts it only from Neovim's inbox card and from `cland remote approve <messenger> <code>`, which prints the paired name and id. The web shows the row with "approve in the terminal or Neovim"; a remote never sees or approves one. This supersedes round 1's code minted by the CLI and redeemed in the chat, where whoever redeems a leaked code first is paired.
- **Identity by numeric ids only.** Telegram: `from.id` with the `chat.id` of a private chat. Discord: the guild, channel and user ids of the pairing interaction. Usernames never identify. The ids stay in `hub.db`, never in committed configuration. `cland remote unpair <messenger>` forgets a pairing.
- **Everything else gets silence.** An update from another chat, sender or update type is dropped before any work, downloads included, and only logged. A Telegram bot the human blocked learns it from its membership update and a 403, stops sending and reports it.

### 3.3 Configuration and the secrets file

Decided in Q-1294 §3, §4 and §8, which replaced round 1's `cland remote token` with `cland secret`.

- **The keys**, in `.cland/config.toml`, rendered with their defaults by `cland init` and added to existing projects by `cland update`:

  ```toml
  [remote]
  mute_default = false      # the state a new pairing starts in

  [remote.telegram]
  enabled = false
  format = "rich"           # "rich" | "entities"

  [remote.discord]
  enabled = false

  [speech]
  provider = "elevenlabs"   # "elevenlabs" | "command" | "" (off)
  model = "scribe_v2"
  language = ""             # empty detects
  max_seconds = 600
  command = []              # the command provider's argv
  ```

- **Active** means enabled with a token present. Every key reloads on `cland hub reload`; enabling or disabling connects or disconnects that messenger. `cland config set remote.<messenger>.enabled true` enables one.
- **The secrets file** `.cland/secrets.toml` is git-ignored through the managed `.cland/.gitignore`, mode 600, checked and tightened at hub start and refused as a symlink:

  ```toml
  [telegram]
  token = "…"

  [discord]
  token = "…"

  [speech]
  elevenlabs_key = "…"
  xai_key = "…"             # waits for an xAI provider
  ```

- **`cland secret`**: `set <name>` reads the value from stdin or a hidden prompt, never from argv; `list` prints names and SHA-256 fingerprint prefixes only; `unset <name>` removes one. A name is the file's dotted key, as `cland config set` names keys (`telegram.token`).
- **Environment overrides** `CLAND_TELEGRAM_TOKEN`, `CLAND_DISCORD_TOKEN`, `ELEVENLABS_API_KEY` and `XAI_API_KEY` win over the file, and all four join the sessions' environment deny-list beside `DIGITALOCEAN_TOKEN`: no session and no speech command inherits them.
- **Validation.** A Telegram token must match `^[1-9]\d{0,16}:[A-Za-z0-9_-]{24,}$` within 80 characters before any URL is built, since a failed URL parse echoes it. A Discord token is opaque. Doctor and `cland remote status` show presence and a fingerprint, never a value.
- **Rotation.** A new token from BotFather's `/token` or Discord's Reset Token goes in with `cland secret set`, followed by `cland hub reload`; the pairing survives because it keys on ids.

### 3.4 The mirror

Decided in round 1 (decisions 2, 3, 10 and 14), Q-1294 §10, Q-1295 §9 and Q-1296 §4, §5 and §10. On the phone the human tried both prototypes' mirrors and kept Rich Messages, the header line, silent progress notes and the 👌/👀 reactions (Q-1292, Q-1293).

- **What is mirrored.** General in both directions, and the inbox's needs-you rows from any topic as cards and notices (§3.5). Item topics and the Agents topic are not mirrored. A reply to a notice goes to its topic, but the remote does not follow that thread: later messages there reach it only as cards and notices.
- **Out.** Every General message opens with a header line, "author · kind". Not mirrored as messages: what the human sent from this remote (a reaction confirms it), answers (their cards show them) and asks to the human (they are cards). What the human wrote in a workbench arrives with the author "you", and what they wrote in the other remote with "you (Telegram)" or "you (Discord)". A message's artifacts follow it, each exactly once (§3.6).
- **Telegram rendering.** A Rich Message (GitHub Flavored Markdown with tables and lists, up to 32768 characters, entity detection off) by default; plain text plus an entities array the gateway computes when `format = "entities"`, and as the fallback after any rejection. Never MarkdownV2. Link previews off.
- **Discord rendering.** Discord's Markdown, with tables as code blocks and deep headings, rules, task boxes and `||` rewritten (Q-1293); embeds suppressed; no mention parsed (every create and edit sends an empty `allowed_mentions`).
- **Splitting.** Telegram's plain path splits at 4096 code points and before the 101st styled entity, at block boundaries and never inside an entity; the rich path never needs to, since the hub caps a message at 8 KiB. Discord splits at 2000 code points and re-opens code fences. Parts are numbered "n/m". A conversion error never drops a message: plain text is the last resort.
- **Silence.** Progress notes and hub notices, the gap line among them, arrive without a notification; everything else notifies.
- **In.** Free text is the human's message in General to the Coordinator, kind `message`, with its `via`. `/decision <text>` and `/question <text>` send the other kinds, on Discord as subcommands of `/cland` (§3.10). Mentions resolve as in the workbench (`@<session>`, `@<role>`, `@lead T-n`). There is no `@aide` mention, in a remote or in the web: the Aide is addressed by its name (`@aide-1`), and launching one is a request to the Coordinator.
- **Outbound replies.** An agent’s General reply targets the mapped native message in each paired chat, including human input and its cross-remote copy. Telegram allows sending without the reply target; Discord uses `fail_if_not_exists: false`. An unmapped or deleted target delivers once as a plain message.
- **Replies.** A reply to a mirrored message goes to its topic as a reply to it; a reply to a notice goes to the notice's topic; a reply to a card answers its ask (§3.5).
- **Plain text in.** The human's own Telegram formatting (bold, links, code) is dropped on the way in, and General receives plain text.
- **Feedback by reaction.** 👌 on the human's message once General has it or its answer is recorded; 👀 once the addressee's session has it, delivered or injected. The reactions replace an echo.
- **Mute.** `/mute` silences the General stream in that remote, while cards and notices still arrive; `/unmute` turns it back on with one line, "N messages arrived while muted". Mute belongs to one remote; `[remote] mute_default` sets the state a new pairing starts in.

### 3.5 Remote cards and notices

Decided in round 1 (decision 9), Q-1294 §6 and §9 and Q-1296 §1 and §5; the details come from the prototypes' cards, which the human tried on the phone and in Discord and accepted (Q-1292, Q-1293).

- **Cards** are asks to the human and Codex and OpenCode approvals. An ask's card names who asks and in which topic, then the question, one button per option (at most nine), "Other answer…" when the ask takes a free answer, and "Decline…". An approval's card names the session, the harness and the command or the files, with the choices the harness offers (once, always, deny), coloured on Telegram.
- **Notices** are the other needs-you rows, marked 📥 and without buttons: a plan waiting for approval (approved in the workbench only; the notice carries the web link), a request for a review, a QA run or a handover, a message to the human in an item topic, and a Claude Code approval, answered in its harness's TUI (v0.2 §3.8).
- **One gate.** The first answer from any client or remote wins (v0.2 §3.3) and is stored in the hub before the platform is acknowledged. Every copy of the card, in every remote, is then edited into its outcome and loses its buttons: the choice or the reason, who, where and when. A withdrawn or cancelled ask's card says so.
- **Stale and foreign taps.** A tap on a closed card gets "Already answered" and changes nothing; a tap from anyone but the paired human is refused privately and changes nothing. Button data is an opaque key checked against the hub's record, never trusted.
- **Late input never answers.** A message that arrives late (§3.9) answers no ask by itself; a reply answers only its own card, and only while the ask is open.
- **Free answers and declines.** On Telegram both buttons send a separate prompt with the reply field open (ForceReply); the next text, or a reply to the prompt, answers, and `/cancel` keeps the ask open. A card never carries ForceReply itself, because a message that ever did can never be edited. A typed or voice reply to the card also answers it. On Discord both buttons open a modal that shows the question above one paragraph field of up to 4000 characters, so Discord needs no reply mode and no `/cancel`.
- **Telegram cards** are plain text with entities, not Rich Messages, so their edits stay simple: one button per row (the server silently drops buttons past 12 per row and 300 in all), callback data within 64 bytes, every press answered at once, and the outcome by editing the text, where "message is not modified" counts as success and a failed edit becomes an outcome reply.
- **Discord cards** are legacy messages: content with at most three rows of buttons, the options five to a row, labelled with their text when every option fits in 34 characters and numbered otherwise, then "Other answer…" and "Decline…"; labels within 80 characters, custom ids such as `ask:<id>:<option>` within 100. The paired human's click is answered within Discord's 3 seconds by one update that turns the card into its outcome without buttons (0.42 to 0.69 seconds after the click in the prototype); work that needs more than 2 seconds is deferred and the card edited afterwards. An ask answered elsewhere edits its card over REST.
- **Order.** One inbox publication sends its cards oldest first, so the newest sits at the bottom of the chat. `/inbox` re-sends every open card at the bottom.

### 3.6 Media and voice

Decided in round 1 (decisions 10 to 13), Q-1289, Q-1294 §3 and §5, and Q-1295. ElevenLabs returned a 30-second note's transcript in about 1.6 seconds, with correct Russian punctuation (Q-1292).

- **One frame to upload and attach.** Today an artifact comes only from a local path or from text, and posts its own ▣ message. The protocol gains `artifact.upload`: files as bytes, each with a name and a MIME type, the topic and an optional caption. It creates the artifacts and attaches them to one new message of the human's, without a ▣ post. The gateway calls it inside the hub. The web composer gains file attachments through it, its bytes going to an HTTP endpoint on the web edge's own listener, since a frame is capped at 1 MiB. A size limit in `[artifacts]` bounds it; the epic names the key and its default.
- **Inbound files.** Photos and documents from a remote become the human's artifacts on the human's message, and a caption becomes its text. An album, the items sharing one `media_group_id`, is one message with every attachment, and the group is stored before the update offset is confirmed. A file over Telegram's 20 MB download cap gets a reply saying so; a Discord attachment is fetched from its signed URL at once, without the token.
- **Outbound artifacts.** On Telegram an image up to 10 MB goes as a photo and any file up to 50 MB as a document; on Discord a file goes up to 20 MiB, at most 10 per message and 25 MiB per request. Each artifact of a message goes exactly once per remote, captioned with the message's header, and a single artifact with a short text goes as the file captioned with the header and the text. A larger file goes as a line naming the artifact and its path; HTML and diagrams go as files. Telegram captions go without formatting in 0.3, because a multipart upload turns newlines into CRLF and Telegram counts the CR in entity offsets.
- **Images in the workbenches.** The web's artifact viewer renders PNG, JPEG, GIF and WebP inline under a size cap, and every other type as today; Neovim opens an image in the system viewer.
- **What is transcribed.** Voice notes always; audio files and Telegram video notes within the same duration cap; videos and documents never.
- **Bytes, untouched.** The gateway downloads a voice note itself and uploads the original bytes with their MIME type (Telegram's sender-declared type, Discord's content type, `audio/ogg` when absent) and a matching file name. OGG/Opus goes to every cloud provider as it is: no transcoding and no ffmpeg in the hub. A messenger URL never reaches a provider, since Telegram's embeds the token. Batch only, no streaming.
- **Limits.** The length is checked before download from the messenger's duration: `[speech] max_seconds` (10 minutes) and Telegram's 20 MB. One deadline of 90 seconds per note; retries only for rate-limited, unavailable and timed-out attempts, at most two, with backoff and `Retry-After`.
- **The transcript message.** Its text is the transcript after a 🎤 marker, with the audio attached as the human's artifact; the language comes from `[speech] language`, empty to detect. Without a key the message is "🎤 not transcribed" with the audio, and the chat gets one line saying how to enable transcription. When the provider fails, the message still reaches General with the audio and "🎤 not transcribed: <reason>", and the chat gets one line. An empty transcript is "nothing recognised", with the audio attached.
- **The echo.** The bot echoes the transcript into the chat after a 🎤, with the note's length, the download and transcription times and the provider's name. A correction is the human's next message; a transcript is never edited afterwards. A voice reply to a card answers its ask.
- **The speech seam**, in the research's shape (Q-1289):

  ```ts
  transcribe({ audio, mime, filename, languageHint?, durationSec?, signal })
    → { text, language?, durationSec?, segments? }  // language: lower-case ISO 639-1
  ```

  A failure carries one of nine kinds: not-configured, auth, bad-audio, too-long, quota, rate-limited, unavailable, timeout, command-failed. Keys are redacted from every error, and provider requests refuse redirects, as the DigitalOcean client does.
- **Providers in 0.3**: `elevenlabs` (Scribe v2, about $0.0018 per 30-second note; the free plan's 4.5 hours a month carry no commercial licence) and `command`. xAI fits the seam and waits, since it no longer gives free credits; `provider = ""` turns transcription off. No cost accounting in 0.3.
- **Data use.** Setup and `cland remote status` show one line on the provider's data use with where to change it: ElevenLabs may train on audio outside enterprise plans until "Improve the models for everyone" is turned off under Terms and privacy, Data use, and it stores transcripts.
- **The `command` provider** is an argv array, never a shell string. It gets the original bytes on stdin and `CLAND_SPEECH_MIME` and `CLAND_SPEECH_LANGUAGE` in an environment free of remote secrets, and prints the transcript on stdout. A non-zero exit or a signal is `command-failed`, with the tail of stderr, bounded and redacted; the deadline kills it.

### 3.7 Telegram

From the research Q-1287 (Bot API 10.3, 38 rules) and the prototype Q-1292.

- **Polling.** `getUpdates` with a timeout of 30 to 50 seconds (the server caps it at 50) and an HTTP timeout above it, and an explicit `allowed_updates` (messages, edited messages, callback queries, the bot's membership). The offset is confirmed only after an update is handled and stored. While offline the gateway polls with a zero timeout, so it sees recovery at once.
- **One poller per token.** A 409 means another consumer; the lease of §3.9 rides it out and reports it, never in a tight loop.
- **What Telegram keeps.** Messages for 24 hours and button presses for 150 seconds; a bot reads no chat history (§3.9).
- **Pacing.** One queue per chat with one request in flight, about a message a second, cards first; a 429 makes the whole bot wait its `retry_after`; HTTP timeouts of 30 seconds or more, since the server absorbs up to 8 seconds of flood wait. No limit beyond the documented ones is hard-coded.
- **Sizes.** Text 4096 code points after entity parsing, entity offsets in UTF-16 units, 100 styled entities, captions 1024, Rich Messages 32768; uploads 10 MB for photos and 50 MB for documents; downloads 20 MB through a URL that contains the token and never leaves the hub; a file's name and MIME type come from the incoming message.
- **Commands** are registered for private chats only when the list differs (§3.10). Every command is untrusted text whose sender is checked, whatever the menu shows.
- **The client** is plain `fetch` on Node 24 with hand-written types and no runtime dependency (grammY's errors carry the token-bearing URL).
- **Superseded research rules.** Pairing by `t.me/<bot>?start=<code>` gives way to the code from the chat (§3.2); `cland remote token telegram` to `cland secret set`; doctor's check with `getMe` moves to `cland remote test`, since doctor reports presence only (round 1 §8).

### 3.8 Discord

From the research Q-1288 (36 rules), Q-1296 §3 and §12, and the prototype Q-1293, which the human tried in their test server and on the phone and accepted.

- **The application.** One per project. A new application starts with Public Bot on, so setup has the human set its Install Link to None and turn Public Bot off. The invite asks for `scope=bot&permissions=117824`: view channel, send messages, embed links, attach files, read message history, and add reactions for the 👌/👀 feedback, which the research's 117760 lacked. Never Manage Messages: the bot edits only its own messages. The Interactions Endpoint URL stays empty, so interactions arrive over the gateway; the hub checks it and the Message Content flag at start.
- **The connection.** On the pinned `ws` package, API v10, JSON, no compression, no shard, intents 33281 (guilds, guild messages, message content). The Message Content intent is a portal toggle for an app under 10,000 users; without it every text, attachment and voice message arrives empty. Heartbeats start with jitter; a missing acknowledgement ends the socket and resumes.
- **The identify budget.** 1000 identifies in 24 hours end every session and reset the token, and every session of the bot counts against them. Identify therefore waits at least 5 seconds after the previous one, resumes first whenever it can, backs off with jitter only after identifies that never reached READY (backing off after every drop delayed a recovery by 33 seconds in the prototype), refuses below a floor of the remaining session starts, and warns the human at 500 in a day.
- **Close codes.** 4004 and 4010 to 4014 stop the remote and surface in doctor and General: 4004 asks for a new token, and 4014 gets a plain explanation of the Message Content toggle. A 4003 gets one fresh identify.
- **Resume.** A hub stop closes the socket resumably, with a code other than 1000, which would end the session; the bot may therefore look online for a while after a stop. A start within about 90 seconds resumes (the prototype resumed after 60 and 90 seconds and was refused after 120, 150 and 180): the replay carries the messages and clicks made meanwhile, the clicks too late to answer, so only the pressed cards are re-sent. A later start identifies afresh, reads the channel history and re-sends every open card (§3.9).
- **REST.** One lane per bucket and channel, following the `X-RateLimit-*` headers and `retry_after`, with no hard-coded limit; a 401, 403 or 404 is never repeated, and a 401 stops the remote. Interaction callbacks bypass the lanes and the outbox, being due within 3 seconds. Every send carries a nonce with `enforce_nonce`, and its returned id is stored before the send counts as done.
- **The command.** One global `/cland` with subcommands (§3.10), visible to the server's administrators, usable in servers only, written on the first start and afterwards only compared, and overwritten when it differs. The hub checks the paired user on every interaction.
- **Inbound** counts only from the paired channel and user, never from a bot or a webhook, and only ordinary messages and replies; a reply maps through its message reference. A voice message is a flagged message with one audio attachment, OGG/Opus of up to 20 minutes.
- **History catch-up.** After a fresh identify the hub compares its stored last id with the channel's last message id, pages back with `before` to it (listings come newest first, and `before` pages continue exactly) and posts what it finds in order: at most 500 messages, and past the cap one line saying the older ones were not passed on. Edits and deletions made meanwhile do not come back.
- **The client** is hand-written on `ws` and `fetch`, with the few API v10 shapes it reads vendored as types; ids stay strings throughout.
- **Superseded research rules.** `/cland pair code:<string>` gives way to `/cland pair` without an argument (§3.2), the invite's 117760 to 117824, and the close with 1000 on a hub stop to a resumable close.

### 3.9 Delivery, catch-up and failure

Decided in round 1 (decision 15), Q-1294 §2 and Q-1296 §1 to §9, after the prototypes (Q-1292, Q-1293) and the prior art (Q-1290): bridges die quietly, and loss sits at the acknowledgement.

- **Store, then confirm.** An update is handled and stored before its offset advances (Q-1287). Updates are deduplicated by update id and by chat and message id on Telegram, and by message and interaction id on Discord, and the bot's own messages are dropped.
- **The catch-up order:**
  1. What the messenger kept (Telegram's update queue; Discord's resume replay or channel history), each late message marked with the time it was written ("written on Telegram at 13:20; the hub was down until 13:24").
  2. One gap line, "N General messages missed since 13:20", only when N is above 0.
  3. The cards of open asks the chat never received, and the outcome edits that did not go through.
  4. After an outage longer than 150 seconds on Telegram, or a failed resume on Discord, every open card re-sent at the bottom ("a button pressed then may have been lost; press again"), its old copy marked "↓ Re-sent below". After a Discord resume, only the cards pressed meanwhile.
- **The gap line** matters for network and messenger outages while the hub runs; after a plain hub restart it is almost always 0, since nothing posts to General while the hub is down (Q-1292).
- **The outbox** is a durable queue per remote in `hub.db`. It records an attempt before each send and resends only what provably never left (Discord's enforced nonce, Telegram's message map); it merges edits; it drops a job whose source closed, such as the card of an answered ask. During an outage a General job is not dropped but marked missed and counted in the gap line. A job queued while the outbox drains goes out in that drain: the prototypes' race left a 👌 waiting for over a minute (Q-1293). A `retry_after` wait is capped at 5 minutes, and reconnection backs off with jitter and a cap.
- **One poller.** A lease in `hub.db` with the pid and start time. A 409 at start is ridden out for up to 60 seconds and nothing is killed; a lasting 409 shows as "another consumer of the token" in doctor, General and `cland remote status`.
- **Liveness from traffic.** Telegram: a poll that has not returned within its timeout plus 15 seconds restarts the loop. Discord: a missed heartbeat acknowledgement terminates the socket and resumes. A remote shows as connected only after a recent successful exchange.
- **Telling the human.** After 3 minutes offline the hub writes one line to General ("Telegram remote offline since 13:20: <reason>") and one on recovery; the workbench's Remotes row turns red at once, doctor shows the state, and the chat gets the gap line on recovery. A wrong or revoked token (401), a blocked bot (403) and Discord's fatal close codes stop that remote, which writes the cause and the fix to General.
- **Hub restarts.** The gateway starts with the hub from its cursors and lease in `hub.db`, and Discord resumes while its window holds (§3.8). A restart posts nothing in the chat except a gap line above 0 and the re-sent cards.

### 3.10 Commands

Decided in round 1 (decision 14), Q-1294 §4 and §8 and Q-1296 §3 and §12; the prototypes added `/cancel` and the replies' layout, which the human asked for on the phone (Q-1293).

- **In a Telegram remote**: `/status`, `/inbox`, `/mute`, `/unmute`, `/decision <text>`, `/question <text>`, `/cancel` (after "Other answer…" or "Decline…", keeps the ask open) and `/help`; `/start` in a paired chat names the project. The menu is registered for private chats only when it differs from what Telegram holds; registering at every start cost other bridges waits of up to 490 seconds.
- **In a Discord remote**: `/cland` with the subcommands `pair`, `status`, `inbox`, `mute`, `unmute`, `decision`, `question` and `help`, answered ephemerally. `decision` and `question` take a text field, since Discord takes a message that starts with a slash as a command.
- **`/status`** answers with the hub's version and uptime, the Coordinator and the needs-you count, up to six sessions, the queues, the open release and the remote's own state. **`/inbox`** re-sends every open card, or says "Nothing needs you". **`/help`** says what the remote does.
- **Laid out for a phone.** A reply opens with a title line, then groups separated by blank lines, each under a bold label (Hub, Coordinator, Sessions, Queues, Release, This chat or This channel), with one fact per line and the sessions as bullets; the gateway's own numbers come last as small text. `/help` is short headed sections with the commands as a bullet list and the trust lines last. A reply is never a run-on line of facts joined by middle dots. Telegram sends replies as text with entities.
- **`cland remote`**: `status` (per messenger: token present with its fingerprint, paired with whom, connection state, last inbound and outbound, outbox depth, mute, the bot's link, and the speech provider's data-use line); `approve <messenger> <code>`; `unpair <messenger>`; `test <messenger>`, which checks the token with the platform and sends one line to the paired chat.
- **`cland secret`**: `set`, `list` and `unset` (§3.3).

### 3.11 Setup, doctor, onboarding and the workbenches

Decided in round 1 (decision 17), Q-1294 §10, Q-1295 §6 and §10 and Q-1296 §8 and §13.

- **Setup** gains an optional remote step after the hub and before the Aide, which stays last because it opens the workbench. It offers Telegram, then Discord: how to create the bot (BotFather; the Discord application with its Install Link at None, Public Bot off, the Message Content toggle and the invite with 117824), the token through a hidden prompt as `cland secret set` reads it, enabling, then the pairing: the human presses Start or runs `/cland pair`, and setup approves the code on the human's yes. For Discord it checks Public Bot, the Message Content flag and the empty Interactions Endpoint URL. It offers the speech key with the provider's data-use line. Without a terminal the step reports what is open; a declined messenger is `skip`.
- **Doctor**, per messenger: the token's presence with its fingerprint, the connection state and the pairing, and the cause of a stopped remote with its fix (a new token for 4004 or 401, the Message Content toggle for 4014, the blocked bot for 403, another consumer for a lasting 409). For speech: a cloud provider's key presence, and whether the `command` provider's argv[0] resolves. Doctor reports presence only and makes no platform or paid call; `cland remote test` checks a token.
- **The onboarding**: the tour gains a stage on remote control.
- **The workbenches.** A Remotes row in the web's Sessions area and in Neovim's sessions panel: connected or not, paired with whom, mute, outbox depth, last error, red at once on a failure. Pairing rows in both inboxes, approved from Neovim (§3.2). Messages from a remote carry a source mark ("via Telegram"), and voice messages their 🎤 marker. The web shows images inline, and Neovim opens them in the system viewer (§3.6).

### 3.12 Hygiene

From the prior art (Q-1290), the research and the rules the prototypes ran under.

- **Sandboxes.** Live runs use real bots only against a sandbox project on this Mac, never this project's hub, and real tokens never go to droplets. Only the human creates bots and places their tokens (T-1291); the sandbox secrets file is read by path, never printed, copied or deleted. Tests run on fake platform servers reached through an API-root override in each client.
- **One redactor.** Every log line, error, journal record and artifact that the gateway or the speech seam writes passes one redactor for tokens and keys. A secret never appears in argv, where every session can see it, or in a frame.
- **No messenger URLs to sessions.** A Telegram file URL embeds the token: the gateway downloads the bytes, and sessions see artifacts only.
- **Known hosts.** The clients talk only to the messengers' and the speech provider's hosts and refuse redirects.
- **Kill nothing.** A conflict over a token is reported, never settled by stopping another process.
