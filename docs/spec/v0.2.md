# cland v0.2: the web workbench

Status: draft (2026-10-14). Charted by the v0.2 wayfinder map (tracker item M-399) in the cland-design session from the human's direction of 2026-10-14; each resolved ticket adds or rewrites its section. It becomes complete when the map's cut ticket closes and the v0.2 epics are published under the release item R-377. The v0.1 and v0.1.2 specs stay in force where this one is silent.

## 1. Purpose

v0.2 brings the web workbench: everything the Neovim workbench shows and does, in the browser, more convenient and without the limits of a console interface. The hub is the single source of truth; the web and Neovim are two clients of one protocol. Neovim stays as the alternative: good for a fast start, for setting up the process and for driving the harnesses; once a project's work has settled and scaled, the human moves to the browser to watch, plan and steer.

## 2. Vocabulary

New terms land in `GLOSSARY.md` as they are decided (candidates: Web workbench, Client, Snapshot, Delta, Rail, Drawer).

## 3. Decisions

Settled while charting, on 2026-10-14 (two grilling rounds; the map's tickets refine them).

### 3.1 Clients and transport

- **Two clients, one hub.** The hub serves the web client itself: HTTP for the static bundle and a WebSocket carrying the same frame protocol the Neovim client speaks (the Q-400 research: one dispatcher already serves the spokes' WebSocket, the unix socket and stdio; the 37 requests and 21 pushed frames Neovim uses carry over as they are), with the identity `human`. The browser's entry is a one-time token printed by `cland web`, exchanged for a cookie; the hub's secret never leaves the machine's own processes (corrected on 2026-10-14 by the research: the spokes' port refuses client hellos on purpose). No separate backend, no database of the web's own.
- **Several human clients at once.** The hub accepts several `human` connections (Neovim and any number of browsers; the research found nothing limits them today); all see the same state. The web keeps its own interface state in the browser; `ui.json` stays Neovim's.
- **Where it runs.** Localhost and the local network first, phones and tablets included; remote access through the human's own tunnel or VPN, never a cloud service.

### 3.2 The shell

A persistent left rail of areas (Inbox, Explorer, Board, Sessions, Topics, Plan, Graph, Events, Artifacts, Accounts); a main area that can split into two panes; a drawer on the right for the card or a thread. Keyboard first, as in Neovim: the palette on ⌘K, the same letters where they fit, `?` shows the keys.

### 3.3 The live model

On connection the hub sends a snapshot, then deltas with sequence numbers so that a reconnecting client catches up instead of re-reading everything; the history of threads and events is served in pages. This is a protocol extension Neovim may use later: today pushed frames carry no sequence numbers, nothing is replayed, Neovim re-reads eight lists and every open thread after a drop, clients have no ping and the edge cuts a socket silent for 60 seconds (Q-400). The research sizes the pieces at about nine sessions (the web edge on a stable port with server pings, the token and cookie with Origin and Host checks, frames serialized once, the snapshot, deltas with `seq` and an epoch, history pages, static serving, artifact files over HTTP) plus three for fields both clients need computed in the hub (unread counts, merged session rows, explorer roll-ups and the summary rule, the events filter) and read marks held in the hub instead of `ui.json`. The grilling ticket Q-407 decides the shape.

### 3.4 Threads and actions

Markdown, role colours and folded agent runs as v0.1 §3.14; artifacts inline, HTML in a sandboxed iframe; asks and approvals as cards with buttons; a composer with the send kinds; the same addressing rules as Neovim (the Coordinator through the item's topic, General for a selection).

### 3.5 Editing: parity with Neovim

In 0.2.0 the web edits nothing by hand that Neovim does not: the explorer's action is the message to the Coordinator, plan approval, the criteria edits of the item view. Dragging rank or moving items between epics with the mouse is fog for 0.2.x.

### 3.6 Notifications and the phone

The needs-you count in the tab title and browser notifications while the page is open; at phone width the inbox, the sessions, the threads and answering asks work; the planning views are desktop first; a PWA manifest so the page installs on a phone.

### 3.7 Serving and security

A `web/` workspace built into `web/dist`, served by the hub on a stable loopback port (one canonical origin; the cookie named per project, since cookies are not isolated by port); `cland web` prints a link with a one-time token and opens the browser, a cookie afterwards; the network only through `[web] bind` (an amendment of ADR 0003, with Origin and Host checks against cross-site WebSocket hijacking); the web phase of the suite as its own shard in headless Chromium. Open for Q-407: a web cookie carries the human's full authority today (`hub.stop`, release, artifacts from any readable path) and may need an allowlist; an HTTP origin on the LAN is not a secure context, so the phone's notifications and the PWA (§3.6) need HTTPS or localhost.

### 3.8 Scope of 0.2.0

Watching, planning and steering through messages: every area of §3.2 including writing to a session or the Coordinator, answering an ask, approving a command or a plan, reading a verdict and an artifact. A harness terminal in the browser (xterm.js) is not in 0.2.0: a session in the web is its thread, what the hub knows; the terminal is a later theme the protocol must not preclude. Approving a command from the browser has no frame today (approvals belong to the attached TUI, Q-400): whether 0.2.0 relays approvals is decided in Q-407 after a look at each harness.
