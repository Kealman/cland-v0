# cland v0.1.4: cland on a new project

Status: complete (2026-10-16). Grilled with the human in the cland-design session over the map M-591 (research Q-592 to Q-595, prototypes Q-596 and Q-597, grilling Q-598 to Q-601); release item R-577.

The epics are tracker items labelled `v0.1.4`, children of R-577 (section 4). The v0.1, v0.1.2 and v0.1.3 specs stay in force where this one is silent.

## 1. Purpose

v0.1.4 is "cland on a new project": a human with cland on their machine goes from an empty folder, or an existing repository, to a working crew with two commands of their own. `cland init` stays deterministic; `cland setup` readies the harnesses, the accounts and the favourite harness and opens the workbench on the Aide, which leads the onboarding from a skill: who decides what, a first plan the human sees, the crew, the Coordinator's start, and a tour on request. The curated skill set replaces the vendored lock, verification takes the commands of any stack, and the hygiene epics carried over from v0.1.3 come along. It ships after v0.1.3 and before v0.2 (D48, D49).

## 2. Vocabulary

New terms in `GLOSSARY.md`: Favourite harness, Setup, Onboarding, Tour, Curated skill set, Welcome note. Amended: Aide (it launches, stops and resumes sessions on the human's word, §3.5) and Crew (the Aide records it during the onboarding). There is no "wizard" term (map M-591, settled answer 3).

## 3. Decisions

### 3.1 The install, deferred

Decided by the human on 2026-10-16 while charting (map M-591, Out of scope), on the research Q-592; the version rule decided in Q-599 on 2026-10-16.

- **Deferred.** 0.1.4 assumes cland installed from the checkout on the human's machine, where the human tests first. The one-command install on a fresh machine waits for a later release; the research stands for it: `docs/research/install-from-github.md` on `research/install-from-github` (87b77611).
- **What works today**, verified on v0.1.2 with a local URL standing in for GitHub (credentials are needed while the repository is private; `cland --version` says 0.1.0):

  ```sh
  git clone --depth 1 --branch v0.1.2 https://github.com/Kealman/cland-v0.git ~/.local/share/cland && npm --prefix ~/.local/share/cland ci --omit=dev && npm install -g ~/.local/share/cland
  ```

- **The seven fixes, for later.** No `npm install -g` form works today; with no root workspaces or install-time scripts, a type-stripping launcher at every spawn site, the hub's dependencies at the root, a root version and a `files` allowlist, a per-user Neovim cache, a public repository (or documented credentials) and the sh wrapper off `bin`, a prototype installed from a git URL in 7 s, and `npm install -g github:Kealman/cland-v0#vX.Y.Z` becomes the first page's line.
- **The package version, taken now** (Q-599 §7). The root `package.json` version is the only source of cland's version (the spoke's hard-coded 0.1.0 goes) and equals the tag. `cland release` refuses a mismatch; the bump is an ordinary commit merged before the dry run, never written by the release. v0.1.4's own release is the first to carry it.

### 3.2 Init

Decided in Q-599 and Q-600 on 2026-10-16, on the setup prototype (Q-597, `prototype/setup`) and the HOME incident (T-609).

- **Roots.** `cland init` and `cland update` serve the current directory or the directory they are given (the positional directory argument, `cland init <dir>`; Q-599 wrote `--dir`), never one found by walking up: when the root they discover differs, they refuse and name both paths. HOME is never a project root. The hub's per-user state moves from `~/.cland/executor` to `~/.local/state/cland` (§3.8), since a prototype init took HOME for a project because of `~/.cland/`.
- **The first commit.** An empty folder, and a folder of the project's own files without Git, get `git init -b main`; they and a repository without commits get a first commit holding only cland's files (`AGENTS.md`, `.cland/`, `.agents/`, `.claude/`, `docs/agents/`), and the human's files stay as they were. Without a Git identity, init commits as `cland <cland@local>`. A repository with history keeps its default branch, `master` or any other (map M-591, settled answer 8).
- **The territory** follows as before (ADR 0004): the local bare repository becomes `origin` and an existing `origin` is renamed `github`; a folder init has just made a repository ends on a clean `dev`. A shallow clone is refused with the line "the territory needs the full history".
- **What comes next.** Every `cland init` ends with the line `next: cland setup` (`--json`: `next`). `cland` in a folder without `.cland/` prints "not a cland project: run cland init" and starts no hub; `cland open` in a project initialised but not set up prints "next: cland setup" in one line and opens the workbench as usual.
- **Sessions edit the working copy.** Claude Code 2.1.143 and later refuse a background session's Edit and Write in the main checkout until EnterWorktree. `cland init` and `cland update` therefore write `"worktree": {"bgIsolation": "none"}` into the project's `.claude/settings.json` as a managed key beside the hooks, and the hub's Claude Code launches carry the same key in `--settings` only for a project whose `.claude/settings.json` lacks it (launch settings outrank every settings file in Claude Code, so the fallback must not defeat the override below): cland controls a session's reach at the hub and role level, never through harness isolation. `update` restores `"none"`; a human who wants isolation back sets it in `.claude/settings.local.json`, which takes precedence and which cland never touches (Q-599 §5). The Coordinator's detached-worktree route for docs commits goes.
- **Categories.** Init seeds the four categories, Bugs, Tech debt, Follow-ups and Ideas, which every clause files into; until now only `task migrate` seeded them (v0.1.2 §3.10).
- **The templates** it writes take the defaults of §3.5.

### 3.3 Setup

Decided in Q-599 on 2026-10-16, on the research Q-593 (harness facts) and Q-594 (prior art) and the prototype Q-597 (`prototype/setup` at 3b2eabfe), accepted after the human ran it in a fresh folder.

- **The shape.** Ordered, idempotent steps: each detects, offers what is missing, acts on the human's yes and detects again; the re-check decides, never an exit code. A step already true prints `ok` and asks nothing, so a second run converges. Each step prints one line: `ok`, `done`, `skip`, `open` or `fail`, the detail and the fix.
- **The eight steps**, in order:
  1. **The project**: `.cland/` exists, or setup stops with "run cland init first".
  2. **The harnesses**: Claude Code, Codex and OpenCode through doctor's own probes (the binary, also in the installers' folders; the version; the login). A missing harness's official user-level installer is shown and runs in this terminal on yes, then the harness is detected again. A declined install is remembered in `config.toml` and not offered again until `cland setup --install <harness>`. cland needs at least one harness.
  3. **The logins**, offered for every harness a template role uses: the harness's own blocking login (`claude auth login`, `codex login`, `opencode auth login --standalone` against cland's OpenCode database) runs in this terminal, in the environment the hub launches with. OpenCode's is optional: its free model needs none.
  4. **The accounts**: the signed-in profiles not yet in `~/.config/cland/accounts.toml`, each shown with who it is signed in as (never written). The question defaults to No, because the file is machine-wide; setup says when Yes is worth it: several accounts per harness, limits. Only names, harnesses and paths are written (v0.1.2 §3.13).
  5. **The favourite harness**, the one the human talks to: written as `[aide.launch] harness` in `.cland/roles.toml`, marked as the human's choice, with an effort that harness takes.
  6. **Trust** for every installed harness, without a question, deterministic per harness, reported in one line ("trusted for …"). Claude Code: `projects["<realpath of the root>"].hasTrustDialogAccepted = true` in the launch profile's `.claude.json`, under Claude Code's own `<file>.lock`, covering subfolders and task worktrees. Codex: `projects."<folder>".trust_level = "trusted"` through a short-lived app-server's `config/batchWrite`; Codex never blocks a launch and asks only at the first remote attach in a folder. OpenCode has no trust gate.
  7. **The hub** starts and outlives setup.
  8. **The Aide**: `aide-1`, launched through the hub on the favourite harness with the brief `Run the onboarding skill; project: empty | existing; harnesses: <installed>; human's harness: <favourite>` (`existing` when the folder holds a file beside cland's own). Setup then opens the workbench as `cland open` does, downloading the pinned Neovim, with the Aide's terminal in the centre, so the human sees the items appear and the Coordinator start (Q-599 decision 11, superseding the map's settled answer 6). `--attach`, for a machine without the pinned Neovim, runs the harness's own attach command in this terminal instead (Ctrl+Z there suspends setup with it: accepted). The closing line says that the Aide may still be running and how to stop it; after `--attach`, "open the workbench: cland". The Aide is never a harness started by hand with the spoke's environment: that is no session, and nothing confirms, tracks or resumes it (Q-593).
- **Without a terminal.** Setup asks, installs, writes and launches nothing: it prints each open step with its exact command and exits 1 while any step is open or failed. `--yes` answers only the harmless questions; an install needs `--install <harness>`; a login and the Aide need a terminal. `--json` prints the steps in doctor's style (`{root, version, interactive, steps, summary, next}`). Also `--harness <h>`, `--no-accounts`, `--no-aide` and `--attach`.
- **Doctor's strictness.** A harness is required only when a role uses it, `gh` only with a `github` remote. Harness versions are neither pinned nor judged (the amendment to Q-599 §4): harnesses update themselves, setup offers no pin, doctor prints each version for information without a verdict, and the tested ranges become informational or go, including E-424's release-time OpenCode range check and its newer-than-tested and 3.x notes (E-424 C3 amended). Doctor stops counting OpenCode's environment keys as credentials.
- **The prompter, without a library.** `confirm`, `choose` and `pause` over `node:readline/promises`, one interface per question, closed before a child runs, since an open one takes the keys meant for the installer or the login; `@clack/prompts` can go behind the same seam later. The flow is tested with a fake prompter and fake harnesses on the PATH.

### 3.4 The onboarding

Decided in Q-596 and Q-600 on 2026-10-16, after two live runs in an empty sandbox; the skill `.agents/skills/onboarding/` on `prototype/onboarding` at 0ff421f8 is the accepted wording.

- **A skill.** `onboarding` belongs to the curated set (§3.6), edited in place like the others: `SKILL.md` holds the flow, `EMPTY.md` and `EXISTING.md` the two scenarios, `WELCOME.md` the welcome note, `TOUR.md` the tour. It starts from setup's brief; the Aide finds a missing field itself.
- **The principles.**
  - *The human never runs commands.* After `cland init` and `cland setup`, a session acts for the human, the Aide or the Coordinator, and asks permission when needed: "when you say ok, I will launch…", never "run this in your terminal" or "press l to launch", unless the human asks for the commands.
  - *Sessions act, the human decides.* The Aide works in rounds as the `grilling` skill does, each question with a recommended answer that "yes" accepts, and says what it will change before doing it on yes.
  - *The onboarding teaches.* Each cland word is explained in plain terms the first time it comes up, and each tour stage says what it means in practice, what the human will see and do, and who acts. This overrides the rule against explanatory prose (v0.2 §3.2) for the onboarding.
  - *Language.* The Aide speaks the human's language. Rules, items and briefs stay in English, which it says once; the welcome note and the tour are in the human's language.
- **The order.**
  1. *A silent check*: the hub, the project's kind, the harnesses. On an existing project the study starts now, with sub-agents that read and report, run no `cland` and change no file.
  2. *The human's role* (round 1): developer-architect, designer, product owner or a mix, recommended only from evidence such as their commits.
  3. *What the human decides* (round 2). The answers become rules in the rulebook, never a config field, and later questions follow them. The recommendation follows the role: a developer-architect keeps the stack, architecture, test strategy and releases; a designer the flows, look, copy and releases; a product owner what to build, priorities, acceptance and releases; a mix the parts they named; the crew decides the rest and explains it in the human's terms. Whatever the role, the Aide recommends "Decisions, not keystrokes": "Sessions run commands for the human; the human is asked for a decision, never for a keystroke." Each rule is recorded with `rule.add` and read back; "I approve epic plans" also sets `[plan] approval = "human"` (§3.5).
  4. *A visible first plan.* Planning stays with the Aide and the human: the Coordinator runs the work but never decides what to build. On an empty project: what to build (a small first version the human can try soon), then fog or not. Without fog, the first release as a table to accept: its goal and three to six tasks in order with sizes, blockers and acceptance criteria (an epic under it when the first version is one larger feature), filed, set to planned and shown in the items panel. With fog, a map (the `wayfinder` skill's "Chart the map") with research sub-agents, and the Coordinator waits for the first epic. On an existing project: the study's report in ten lines at most; the cland tracker becomes the only source of work; the open GitHub issues are imported on confirmation with `cland task import-github` (closed issues and pull requests stay on GitHub; another tracker is only named); then "what next" becomes the first release, filed and shown the same way.
  5. *The categories*: the four init seeded (§3.2), one line each on what they hold.
  6. *The stack as a rule*: "Build with <stack>; checks: <commands>", proposed with its reason when the rules give the stack to the crew, asked when they give it to the human, taken from the study on an existing project. Its commands go into `[verification]` (§3.7).
  7. *The crew round.* First the roles, one line each, then the crew as one table (harness, model, count, how it works) from the installed harnesses and the rules. Recommended: the Coordinator on the human's harness with a heartbeat of 1h; Implementers per item, stopping after merge; a Reviewer pool of 1 keeping context, on another harness than the Implementer's when one is installed; QA as a singleton once there is something to run; no Leads yet; the Aide with sub-agents. A model is named only when `cland models <harness>` lists it, else the harness's default; one harness is a valid crew. The permissions offer: Claude Code roles run in auto mode by default, and the Aide offers to turn the prompts off (`skip`) explicitly, with its trade-off, and records the answer. All of it goes through `cland crew set` and `cland role launch`; the Aide applies its own change last, effective at its next launch.
  8. *The welcome note*: `WELCOME.md` filled in the human's language and posted with `artifact.create` as the note "Welcome aboard" in General: who is who, the rules, the first release, how to reach the Aide.
  9. *The commit*: the Aide commits on `dev` everything `cland init` and the onboarding wrote, and runs `cland push` (Q-600 §2).
  10. *The start*, only when work is ready, the first release's tasks filed and planned: "Ready to start? When you say ok, I launch the Coordinator with this brief: Work release R-<n>." On ok the Aide launches it (§3.5) and says when it runs. With only a map, the Aide says that the Coordinator waits for the first epic and goes on with the map.
  11. *The tour, on request*, once the Coordinator runs (with only a map, once the research runs): "Do you want to learn everything cland can do?" On yes, the eight stages of `TOUR.md`, one per round, tied to what is on the human's screen: the workbench; items, the explorer and the card; topics, General, the inbox and asks; sessions, roles and the crew; the life of a task; artifacts; the rulebook; growing the crew. Each stage ends with its "look now" and one question: the next stage, or stop here.
  12. *The end*: the onboarding is done; the Aide says what runs now and that the human can ask it anything.
- **The accepted wording.** `WELCOME.md` and `TOUR.md` are this spec's source for the welcome note and the tour; the accepted run is kept at `/Users/evgeniyivanov/Projects/cland/sandbox-empty/onboarding.txt`. Where the skill's text predates Q-600 (a Coordinator brief that commits, launches and the import refused to the Aide, `skip` recommended, launch fields edited by hand, npm checks, the welcome note's line on prompts), this spec follows Q-600.

### 3.5 The Aide's reach, the settings commands and the defaults

Decided in Q-600 on 2026-10-16.

- **The Aide's reach.** On the human's word the Aide may launch, stop and resume sessions of any role (`session.launch`, `session.stop`, `session.resume`), the Coordinator first of all; it may import issues (`task.import`) and push the onboarding's commit (`push`). During a build the Coordinator keeps the crew's staffing, and the Aide launches only when the human asks. These are hub permissions, not skill wording: a `cland` call from a session's shell carries that session's identity, so the hub refused the Aide in its terminal as in its tools. This amends v0.1 §3.3.
- **Settings through commands**, never by hand for sessions that lack the tools:
  - `cland role launch <role> --harness … --model … --effort … --account … --permissions …` writes a role's launch fields (`cland role set` already assigns roles to sessions);
  - `cland config set <section.key> <value>` writes `config.toml`: the verification commands, the plan approval;
  - `cland models <harness>` probes the harness's model list and caches it, for the crew round and the launcher's model field (`opencode models` printed nothing in the live run);
  - `cland task import-github` without `--repo` reads the `github` remote, then `origin`.
- **Template defaults**, written by `cland init`; an update never changes an existing `roles.toml`.
  - `crew.toml` gives the Aide sub-agents (`aide.subagents = true`).
  - The roles template is built from the installed harnesses: a project on Claude Code alone is valid.
  - Permissions are never off by default: that is the human's conscious choice. A new `permissions = "auto"` launches Claude Code with `--permission-mode auto` and is the Claude Code roles' default (today only `""` and `"skip"` exist); `skip` (`--dangerously-skip-permissions`) comes only from the human's explicit choice. Codex roles keep `approval = "never"` with the per-role sandbox as the guard: the Reviewer read-only, the Implementer `workspace-write`, QA `danger-full-access` (T-65, 2026-10-09: it runs the product), an Aide moved to Codex `workspace-write`; the crew round names these per role. OpenCode keeps its own settings.
- **Plan approval.** "I approve epic plans" in the rules round sets `[plan] approval = "human"` through `cland config set`.
- **T-603.** An unpinned Claude Code launch passes `CLAUDE_CONFIG_DIR` only when the hub inherited it or the account names a directory: Claude Code treats any explicit value as a separate profile, so the explicit `~/.claude` ran sessions signed out and untrusted (the cause of D36), as did a path-less claude-code account. A prototype fix is on `prototype/onboarding` at 7acc4890; sessions recorded before the fix still carry the value on relaunch.
- **T-608.** A rule's title is cut at 80 characters without a word, and `rule.edit` cannot change a title: the limit is announced or lifted, and `rule.edit` changes titles.
- **Risk: the classifier and the Aide's own role.** In the live run Claude Code's auto-mode classifier refused the Aide's own `cland role list` after the Aide had set `skip` for its own role ("self-modification"). With auto as the default, the Aide's changes to its own launch settings go through `cland role launch` and may still be flagged, so the crew round applies them last. An Aide cannot relaunch itself, so setup launches it with the permissions its role holds.

### 3.6 The curated skill set

- **No lock, no patch file.** `skills-lock.json` and `skills/PATCHES.md` are deleted (16 copies differed from upstream; PATCHES.md recorded 4). Each kept vendored skill carries a metadata header in its frontmatter: the origin commit in `mattpocock/skills`, the MIT notice, one line of cland's changes.
- **The Codex listing.** Each `agents/openai.yaml` flag follows the frontmatter, which lost `disable-model-invocation` in this repository's first commit while the flag stayed: Codex then lists implement, to-spec, to-tickets, triage and wayfinder.
- **The fallback lines.** The five skills that send the user to `/setup-matt-pocock-skills` (code-review, to-spec, to-tickets, triage, wayfinder) point at `cland update`, which provisions `docs/agents/`.
- **`cland update` with hashes.** The manifest keeps the SHA-256 of every file as cland wrote it, and update decides per skill:
  1. an untouched copy is refreshed;
  2. a copy edited in the project is kept and reported "edited in the project";
  3. a skill new to the set is added, unless the project already has a folder of that name;
  4. a dropped skill is removed when untouched, and handed to the project when edited.
- **Old manifests.** A manifest without hashes gets one last overwrite at the first `cland update` of 0.1.4, with a warning line; no table of past hashes ships.
- **Around it** (from the research): `docs/agents/domain.md` and its template stop naming grill-with-docs and improve-codebase-architecture; the init and doctor tests that sample `grill-me` take a kept skill.

### 3.7 Verification for any stack

Decided in Q-600 on 2026-10-16; the human raised it during the live try.

- **The problem.** `cland verify` runs this project's npm scripts by name: `npm run typecheck`, then `npm test` (`--workspace hub` or `npm run test:nvim` in the hub and Neovim modes); the droplet's prepare runs `npm ci` and seeds the Neovim pin; the host gate runs the typecheck again; coverage selection assumes `node --test`; `[verification]` in `config.toml` names no command. A project not on Node has no verification, and the onboarding Aide chose a stack to fit verify, with a `pretypecheck` running `npm ci`.
- **The commands.** `[verification]` in `config.toml` gains `prepare`, `check` and `test`; the droplet executor runs the same `prepare`; coverage selection applies only to cland's own node commands; the onboarding records the commands with the stack (§3.4) through `cland config set`.
