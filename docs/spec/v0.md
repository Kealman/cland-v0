# cland v0 specification

Status: complete (2026-10-08). The wayfinder map https://github.com/Kealman/cland-v0/issues/1 is closed; this document is the destination.

## 1. Purpose and destination

cland is a terminal IDE for running and coordinating AI coding-agent harnesses: one person drives many sessions of Claude Code, Codex and OpenCode from one place, one instance per project. This spec is the destination of the wayfinder map [#1](https://github.com/Kealman/cland-v0/issues/1): the v0 architecture and the first two slices, ready for `/to-tickets`; the slice cut answers [#18](https://github.com/Kealman/cland-v0/issues/18). Where a later ticket refines an earlier one, the spec follows the later ticket.

## 2. Principles settled at charting

- Single-user tool, one cland instance per project, started from the repo root.
- Neovim is the engine: the leading candidate at charting, locked by ADR 0005 after a prototype.
- v0 harnesses: Claude Code, Codex (as a full interactive harness, not only `exec`), OpenCode; one adapter layer designed for more.
- Role is first-class: assigned to a session, independent of harness and model, movable mid-project.
- The process layer (Matt Pocock's skills, adapted) is part of cland.
- The reusable core of the BCAS driver hub (`tooling/driver-hub` in the BCAS repository) is the starting codebase for the hub, not only inspiration.
- cland must know each session's state (idle, busy, waiting for the human, waiting for approval) from a reliable source, not from the model's self-report.

## 3. Vocabulary

[`GLOSSARY.md`](../../GLOSSARY.md) defines the terms used here. A **harness** runs **sessions**; a session holds at most one **role**, which carries a **role clause** and moves with a **handover note**. Sessions reach the **hub** through a **spoke**, and an **adapter** drives each harness. The human talks with agents in **topics**, **General** and **Agents** among them, and answers the Coordinator's **asks**. Tracker **items** carry **claims** and **verdicts**; tasks and epics are **units of work**. Agents work on the **territory** in **task branches**, and a **release** ships to GitHub. An **artifact** is a file shown or handed to the other side.

## 4. Architecture

### 4.1 Engine

Sources: [#11](https://github.com/Kealman/cland-v0/issues/11), [ADR 0005](../adr/0005-neovim-is-the-host.md), research [#4](https://github.com/Kealman/cland-v0/issues/4).

- cland runs as Lua inside a standalone build of the official Neovim release (0.12.5 at the decision), pinned to a `vX.Y.Z` tag and started with its own `NVIM_APPNAME` and `--clean -u <init>`, in that order, so no user configuration loads.
- The chat panel is built from Neovim's own UI primitives.
- Session terminals only attach to sessions the hub owns.
- Rejected: Neovim embedded in a host we write.

### 4.2 Hub

Sources: [#13](https://github.com/Kealman/cland-v0/issues/13), [ADR 0003](../adr/0003-hub-is-a-per-project-daemon-from-the-bcas-core.md) with its stdio addendum, research [#2](https://github.com/Kealman/cland-v0/issues/2).

- A per-project daemon, started by `cland` from the repo root, that outlives the UI: the extracted BCAS core (Node 24, TypeScript by type stripping, `node:sqlite`, `ws`) and its test harness.
- It owns the session registry, store-and-forward routing, topics, messages, asks, role state and per-call permission checks, the tracker and artifact indexes, claims, item writes, the journal and an audit log; decisions, the UI, git operations and artifact files stay outside.
- Spokes keep the BCAS protocol: an MCP stdio server with one WebSocket to 127.0.0.1. The UI uses the same frames as JSON lines over a Unix socket in `.cland/`, and sandboxed QA runs use them over the stdio of a child hub or hub stub.
- Clients find the hub through `.cland/hub.json` (socket, port, secret, pid); `cland` starts the hub when it is absent.
- Delivery stages: `queued`, `delivered` (spoke accepted), `injected` (adapter confirmed the turn).
- Session state: `idle`, `busy`, `waiting for human`, `waiting for approval`, `unknown`, from adapter signals, never from the model's self-reported `status`.
- State persists in SQLite, `.cland/hub.db`, hygiene counters included.
- Spoke tools: `send`, `ask`, `resolve`, `history`, `who`, `status`, `topic.create`, `task.*`, `role.handover`, `session.launch`, `artifact.create`, `merge`.

### 4.3 Harness adapters

Sources: [#12](https://github.com/Kealman/cland-v0/issues/12), research [#3](https://github.com/Kealman/cland-v0/issues/3). No ADR.

- TypeScript modules in the hub; harness processes sit in the hub's process table, rediscovered after a restart. Spoke MCP configuration is injected at spawn, never committed.
- Mandatory: `spawn(name, role, model, cwd)`, `attach_command`, `inject` (confirming `injected`), a `state` stream, `stop`, `resume`. Optional, declared and never emulated: `history`, `usage`, `set_model`, approval relay. Each state signal is published as `reliable`, `heuristic` or `none`.

| | Codex | OpenCode | Claude Code |
|---|---|---|---|
| spawn | `codex app-server --listen unix://…` per session, `thread/start`; the first turn carries the clause | session on the OpenCode server | `claude --bg --model …` |
| attach | `codex resume --remote unix://… <threadId>` | `opencode --server <url>` | `claude attach <session>` |
| inject | `turn/start` or `turn/steer` | prompt API, `steer` or `queue` | cland mod `$.prompt.submit()`, inbox socket fallback |
| state | `thread/status/changed` (reliable) | SSE; waiting via `permission.asked`, `form.created` (heuristic) | hooks and mod `turn.complete` (reliable); polled `claude agents --json` |

- Failures never block the queue: an unconfirmed inject stays `delivered` and retries at the next `idle`; a dead process is `unknown` until `resume`.
- Approvals stay in the harness TUI in v0. Reconnect identity is the name plus the harness's own id.

### 4.4 Roles

Sources: [#10](https://github.com/Kealman/cland-v0/issues/10), [ADR 0001](../adr/0001-roles-are-hub-held-state.md).

- Coordinator (one holder or vacant), Implementer, Reviewer and QA (many holders); at most one role per session; roleless sessions stay off the hub.
- A role carries a clause, skills, permissions and launch defaults, set in `.cland/roles.toml`. Defaults: Coordinator, Claude Code, Fable, effort max; Implementer, OpenCode, a free model to pick; Reviewer, Codex, gpt-6.1-sol, high; QA, Codex, gpt-6-astra, high.
- The hub delivers the clause as an event at assignment and on every reconnect; `AGENTS.md` holds only the generic part.
- Permissions, as spoke tools:
  - Coordinator: `send` to anyone, `ask`, `topic.create`, `task.claim` and assigning tasks, `session.launch`, `role.handover`, `resolve`, `merge`.
  - Implementer: `send` to the Coordinator and mentioned parties, topics bound to its task, `task.claim` on its task.
  - Reviewer and QA: `send` (verdicts and messages to the Coordinator), `history`, `who`, and verdict comments on items through `task.comment`, which the merge gate (4.7) checks.
  - All roles: `artifact.create`. Only the Coordinator asks the human.
- The Coordinator and the human create items, the Coordinator edits and closes them, an Implementer comments on and claims its own item, Reviewer and QA write only verdicts (addendum on #10).
- The human assigns and revokes roles; the Coordinator may request role sessions and hand over its own. A dead holder leaves the role vacant; a vacant Coordinator raises "no coordinator".
- Handover moves state, never the transcript: the clause, a note (goals now, work in flight, open decisions, waiting on) that is mandatory when the holder hands over, and context on demand.
- Names match `[a-z0-9-]`, never change, and show with the role: `reviewer-1 [Reviewer]`.

### 4.5 Topics and asks

Sources: [#7](https://github.com/Kealman/cland-v0/issues/7). No ADR.

- One flat list per project, sorted by activity, with topics waiting for the human on top.
- A topic has a title, a status and at most one bound unit of work, which has at most one topic. Init creates General, for talk with the Coordinator, and Agents, a read-only record of agent-to-agent messages and lifecycle events.
- Human messages address the Coordinator; `@role` and `@session-name` pull others in. Topics bind to roles, never sessions.
- Statuses `open`, `waiting for human`, `waiting for agent` and `closed` follow message direction, `ask` and `resolve`. The human closes topics, and so does closing the bound unit of work, which cancels open asks; a new message reopens the topic, never the unit of work.
- An ask is a message with options and a free answer; the answer carries `answer_to`.
- Agents have no current topic: every delivery carries the topic id, title and binding, agents reply with `send(topic, text)`, and history is pulled on demand.
- Agents open topics with `topic.create`; a task's topic appears with its first message.

### 4.6 Task tracker

Sources: [#8](https://github.com/Kealman/cland-v0/issues/8), [ADR 0002](../adr/0002-tracker-files-are-the-source-of-truth.md).

- cland's own tracker is the source of truth; no GitHub sync in v0.
- One entity, Item: a `kind` (epic, spec, task, question, map), GitHub-shaped fields (`id`, `title`, `state`, `labels`, `assignee`, `parent`, `blocked_by`), `topic` and `branch`.
- One committed Markdown file per item, `.cland/tasks/T-123-short-slug.md`, with YAML frontmatter and sequential ids. The hub keeps the index and the live claims.
- Comments go under `## Comments`. Verdicts are comments headed `verdict: review | qa`, `result: clear | not clear`, `by: <session> [<role>]`, `run: <id>`.
- Writes go through the hub; hand edits are re-indexed, last writer wins.
- `cland task` (create, view, list, comment, edit, close, link, claim) mirrors the `task.*` tools for the skills' "other" mode.
- cland never commits tracker files; the Coordinator commits them with the work.

### 4.7 Git strategy

Sources: [#14](https://github.com/Kealman/cland-v0/issues/14), [ADR 0004](../adr/0004-agents-work-on-a-local-git-territory.md), research [#5](https://github.com/Kealman/cland-v0/issues/5).

- Plain git and a cland-owned layer, no forge. `origin` is the territory, a bare repository at `.cland/territory.git`; GitHub is the remote `github`, touched only by releases and the human.
- `main` mirrors GitHub; `dev` integrates. Task branches `t/T-123-short-slug` start from `dev` in worktrees `.cland/worktrees/T-123/`, made at claim time, removed after the merge, and used as the Implementer's `cwd`.
- `cland merge T-123`, a Coordinator hub tool, lands one squash commit on `dev` after a `clear` review verdict from a Reviewer session, a `clear` QA verdict from a QA session where the item requires QA, and a rebase on `dev`. Merges are serialized; no commit signing in v0.
- `cland release` fast-forwards `main` to `dev`, tags `vX.Y.Z` with notes from item titles and pushes both to `github`: one commit per task, no pull requests.
- `cland init` re-points a GitHub-origin repo (territory as `origin`, GitHub as `github`, `dev` from `main`), pushes nothing and has `--undo`.

### 4.8 Artifacts

Sources: [#9](https://github.com/Kealman/cland-v0/issues/9). No ADR.

- Plain files `.cland/artifacts/A-123-short-slug.<ext>`, indexed by the hub, committed only when promoted into the repo.
- Kinds `prompt`, `note`, `page`, `diagram`, `file`. Markdown and Mermaid render in Neovim; HTML and images open in the browser. Long prompts are drafted as `prompt` artifacts, then sent or attached.
- `artifact.create(kind, title, path | content, topic)` registers a file and posts it into the topic; clauses require it instead of tmp files.
- Statuses `draft`, `sent`, `shared`, `archived`. Closing a topic archives its artifacts, deleted after a configurable 30 days unless promoted. Artifacts bind to topics, never sessions.

### 4.9 Process layer

Sources: [#17](https://github.com/Kealman/cland-v0/issues/17). No ADR.

- `cland init` provisions, idempotently: skills in `.agents/skills/` with `.claude/skills` symlinked; `docs/agents/*`; `AGENTS.md` with the generic part (obey hub events, use `cland task` and hub artifacts, never push to `github`); `.cland/roles.toml`; Claude Code hooks (`UserPromptSubmit`, `Stop`, `PermissionRequest`, `SessionStart`) calling `cland hook`, and the cland mod; the General and Agents topics. The territory (remotes, bare repository, `dev`) is set up by `cland init` from slice 2 on. In slice 1, `cland init` provisions only the folder skeleton, managed files, topics and roles config.
- Until slice 2 re-points the remotes, `origin` is GitHub and the rule reads: push to GitHub only on the Coordinator's explicit decision, as today; slice 2 changes it to: only `cland release` pushes to `github`.
- cland never creates `CLAUDE.md`, which stops Claude Code from reading `AGENTS.md`; an existing one gets `@AGENTS.md`.
- Files carry a "managed by cland" mark; `cland init` and `cland update` touch nothing else. `cland doctor` checks the harnesses, `gh`, Neovim and the hub.
- Skills: the Matt Pocock set vendored with cland's patches, plus `qa`, `release`, `merge` and `handover`.
- `.cland/` commits `tasks/`, `roles.toml` and `config.toml`, and ignores `artifacts/`, `worktrees/`, `territory.git/`, `hub.db`, `hub.json`, `secret`, `journal.jsonl` and `log/`.

### 4.10 Review and QA process

Sources: [#6](https://github.com/Kealman/cland-v0/issues/6), [#16](https://github.com/Kealman/cland-v0/issues/16). No ADR.

- Review and QA go through the hub to the Reviewer and QA roles: the Coordinator sends the request to a Codex session holding the role, which writes its verdict on the item. `/codex:rescue` is the fallback and the manual path: review with `/codex:rescue --wait --fresh --model gpt-6.1-sol`, read-only; QA the same with `--model gpt-6-astra`.
- Computer use blocks terminal apps and rescue runs decline every approval, so QA has three lanes: by default a headless Neovim fed by `nvim_input` and read with `screenstring()` through `cland --headless --qa`, needing no grant; tmux `capture-pane`, needing grant 2; ttyd on `127.0.0.1:47614` in Chrome, needing grant 1.
- Grant 1 pre-allows that origin in `~/.codex/browser/config.toml`; keep it. Grant 2, `network_access = true` in `~/.codex/config.toml`, widens every `--write` Codex run; enable it only for tmux runs.
- Long rescue runs go `--background`, then `/codex:status` and `/codex:result`. Briefs are repo files. Each run ends in a verdict on the item and one `runs.jsonl` line per case.

## 5. Main screen layout

Decided with the design canvas (https://claude.ai/artifact/PMVXaxAkQJQ6mSNEo3k7eB) and the workbench prototype (branch `prototype/workbench`, ticket https://github.com/Kealman/cland-v0/issues/15). One shell; nothing is a mode. The human accepted it for v0 on 2026-10-08 as the skeleton, noting it feels dense at first; tuning happens in use.

- **Shell.** A top bar (project, centre view title, the Coordinator chip with its state, the "needs you" count, the sessions count), implemented as the tabline. A status line at the bottom with the centre view's context, hub state and key hints.
- **Centre view**, one at a time: a topic thread with the composer (a prompt buffer; Shift+Enter inserts a newline; delivery stages on the human's messages; asks as cards with numbered options and a free answer; artifact chips); the board (backlog, planned, in progress, review, qa, done); the item view (the item file, a fields column, verdicts, comments); an attached session terminal; the Agents log; the inbox full width.
- **Left panel: items.** A tree of epics and items with status glyphs, the claim and an ask badge. Filters: all, in work, needs you, done, map (the wayfinder grouping: decided, frontier, in work by sub-agents, blocked). Toggled with `␣i`; Enter opens the item in the centre.
- **Right panel**, one of three: the inbox (`␣n`: asks answerable inline with 1-9 or a free answer, approvals that open the session, topics waiting for the human, dismissable notifications), sessions (`␣s`), topics (`␣t`, grouped needs you, open, closed). Pressing the active key hides the panel. `␣N` opens the inbox full width; `␣T` docks topics above the inbox.
- **One floating picker** (`␣p`; `␣a` opens it on artifacts) over items, topics, sessions and artifacts; Tab switches the kind.
- **The three motions** `gi`, `gt`, `gs` work from every panel and view, on the reference under the cursor or on the current context; `␣␣` returns to the previous centre view. They make every panel optional.
- **Stage presets are examples, not modes**: `charting` (items as the map, one thread, right panel hidden), `watch` (items in work, the thread, topics docked above the inbox), `steady` (the board, the inbox). The human toggles anything from there.
- **Colours and glyphs**: a dark ground; amber for what needs the human; teal for in progress and agent activity; green for done; red for died and not clear; monospace glyphs, no emoji.

## 6. Slice 1: the daily driver

Decided with the human on 2026-10-07 for #18.

- (a) The Neovim shell: standalone build, screen layout per #15, session terminals attaching to external sessions. The layout is the workbench of section 5; the inbox is a right panel and a full-width centre view in slice 1.
- (b) The hub: the extracted BCAS core, spoke, SQLite, routing, topics and asks, session state, delivery stages.
- (c) Adapters for all three harnesses: spawn, attach, inject, state, stop and resume (the mandatory set of #12).
- (d) Roles: the four roles, clause by hub events, permissions, handover with a note and the `handover` skill.
- (e) The tracker: files in `.cland/tasks`, the `cland task` CLI, the index, the skills in their "other" mode.
- (f) The process layer: `cland init`, `AGENTS.md`, skills, Claude Code hooks, the mod, `cland doctor`.
- (g) Review and QA through the roles: the Coordinator sends a review or QA request through the hub to a Codex session holding the Reviewer or QA role, which writes its verdict on the item; `/codex:rescue` stays the fallback. QA in slice 1 checks what it can without the QA lane: shell-level checks, the `cland task` CLI, and a headless Neovim driven by `nvim_input` with `screenstring()`.

**Tracer-bullet order**, thin end-to-end path first; each step ends in something the human can use:
1. Hub, spoke, Claude Code adapter and the General topic in the Neovim UI: the first "hello" from the Coordinator in the chat.
2. Codex and OpenCode adapters.
3. Roles, clauses, handover.
4. The full topic model and asks.
5. The tracker and the skills.
6. `cland init` and provisioning.

**Definition of done and dogfooding.** The human runs a real task of the cland project inside cland: Coordinator in Claude Code, Implementer in OpenCode, Reviewer in Codex, conversation through topics, items in `.cland/tasks`, review by a Codex session holding the Reviewer role through the hub, with `/codex:rescue` as the fallback. cland is built with cland from slice 1 on.

**Tracker bootstrap.** Until `.cland/tasks` exists, the tasks for building cland live in this repo's GitHub Issues and `/to-tickets` writes there. When the slice-1 tracker works, one script migrates open items to `.cland/tasks` and `docs/agents/issue-tracker.md` switches to the "other" mode.

**Repository layout.** One repo: `hub/` (TypeScript: the hub, the adapters and the `cland` CLI, which runs on Node and starts the hub and Neovim), `nvim/` (Lua: the standalone build and the UI), `skills/` (vendored and cland's own), `docs/` (ADRs and this spec). Research and prototypes stay on their branches.

## 7. Slice 2

- (a) The git territory: `cland init` for the remotes, a worktree per task, `cland merge` with verdict gates, `cland release`, with the `merge` and `release` skills.
- (b) Artifacts: folder, index, `artifact.create`, prompt drafting, promote, cleanup.
- (c) The QA lane infrastructure: the Lua QA API for scripted cases, the brief format, the `qa` skill, the hub's stdio transport for sandboxed runs.
- (d) Agents-topic filters and the topic's artifact list in the UI.

## 8. Outside v0

Out of scope, from the map:
- Multi-user mode, accounts and permissions.
- A GUI outside the terminal.
- Cloud hosting of cland.
- Remote access (from a phone or another machine) for v0.

Fog that stays outside the spec, verbatim from the map's "Not yet specified":

> Chat: message rendering (Markdown, code, artifacts inline); searching history.

> Ideas to revisit: a sessions board (role, harness, model, state and current task of every session at a glance); cost and usage per session, role and model; crew presets (launch a standard set of sessions for a task type in one command); a unified event journal across sessions for retrospectives and recovery.

- Change tour per item: a way to look at what an item changed as the project is now, navigated by file structure, with new or changed places marked in the gutter rather than a red and green diff, to understand how a task was done; and spawning a session on the item's worktree or in the item's context to ask for a diagram or an explanation. Parked by the human on 2026-10-08.

The hub's journal is in v0; its use for retrospectives and recovery is not. Undecided by any ticket and left to implementation: the "distribution format of the standalone build; keymap scheme", "message rendering", artifact "versioning", "an ingress for automation".

## 9. Risks and mitigations

- **Terminal key fidelity.** Shift+Enter arrives as plain Enter without kitty "disambiguate" mode; map terminal-mode `<S-CR>` to `ESC[13;2u` (#11).
- **Pastes.** The default `'termpastefilter'` drops TABs, so set `BS,ESC,DEL`; an Enter right after a paste can overtake it (#11).
- **Scrollback cap.** Terminals created at startup get a 1,000,000-line cap, 33 times slower under heavy output; set 10,000, tile no session below three rows, take full-screen history from the harness (#11).
- **Restart and external session ownership.** Neovim-owned terminals die on `:restart`; attach to hub-owned sessions from string commands, which `:restart` re-runs intact (#11).
- **UI updates while input is pending.** Callbacks wait during counts, mapping prefixes and "Press ENTER" prompts; avoid hit-enter prompts and update through `vim.schedule` (#11).
- **Codex embedded-mode trap.** `-c` or `--profile` on the Codex TUI removes its external surface; `resume --remote` needs a first turn; key status by `threadId` (#3, #12).
- **Channels still preview.** Claude Code channels fail on the v2 MCP runtime; inject through the mod, with the inbox socket, whose message format is undocumented, as fallback (#3, #12).
- **Approvals auto-declined in rescue runs.** Rescue threads use `approvalPolicy: "never"`: briefs must be self-contained and grants set beforehand (#16).
- **Unix sockets blocked in the Codex sandbox.** The sandbox blocks sockets while network is off: QA uses stdio, spokes run outside the sandbox, but a `cland` CLI call from a sandboxed Codex shell fails (#16).
- **Rate and loop hygiene.** Keep BCAS's message cap, rate limit and loop breaker, with thresholds in `config.toml` and counters persisted (#2, #13).
- **Sub-agents sharing a spoke.** Not enforceable in v0: the clause forbids hub calls from sub-agents, and the audit log shows violations (#2, #13).
- **Per-task PR volume on forges.** Merges slow down at hundreds of open PRs; irrelevant with no forge and serialized merges (#5, #14).
- **GitHub personal-account limits.** No merge queue, no counted self-approval, about 500 content requests per hour; bulk `/to-tickets` runs during the bootstrap count against it (#5).
