# cland v0.1.2: Working with items

Status: draft (2026-10-12). Grilled with the human in the cland-design session, breadth-first on the release as a whole (tracker item T-228, "Release: v0.1.2"); each decided ticket adds or rewrites its section. The explorer cluster is charted as a wayfinder map; the spec becomes complete when the map closes and the v0.1.2 epics are published. The v0.1 spec (`docs/spec/v0.1.md`) stays in force where this one is silent.

## 1. Purpose

v0.1.2 is "Working with items": the human works with items in cland as a full planning and tracking tool, not only watches status in the side panel. The core is the item explorer (T-243) with the human's item card (T-244), the release scope by epics (T-237, T-238), categories outside epics (T-245), id prefixes by kind (T-241) and done items distinct in the graph (T-242). Everything else is around that core.

## 2. Vocabulary

New or changed terms land in `GLOSSARY.md` as they are decided (candidates: Category, Explorer, Card, Summary, Events view).

## 3. Decisions

### 3.1 Id prefixes per kind

Decided in T-241 on 2026-10-12.

- **The number is the identity, the prefix follows the kind:** `R-` release, `E-` epic, `T-` task, `Q-` question, `M-` map, `S-` spec, `C-` category once categories are a kind. One shared counter, so a number is unique across kinds and an item keeps its number when its kind changes.
- **Any prefix resolves.** The hub finds an item by its number whatever prefix is written, so `T-107` in the journal, in artifacts, topics and documents still leads to the epic the workbench draws as `E-107`. The CLI, the panels and the `gi` targets accept any prefix and display the kind's own.
- **Migration** is one command: it renames the item files and rewrites the references in frontmatter (`parent`, `blocked_by`); nothing else is rewritten.

### 3.2 Planned derives from the plan

Decided in T-238 on 2026-10-12.

- **With a plan** (v0.1 §3.10), the items of the epic's current stage are `planned` and the rest of the epic stays `backlog`; when the stage completes, the hub moves the next stage to `planned`, as it moves the other statuses on events.
- **Without a plan**, `planned` is set by hand by the Coordinator or the human, as before.
- **The release scope shows only the release's own items.** Other containers and unscheduled items are reached through the `all` filter and one count line at the bottom of the release scope.

### 3.3 Done items distinct from backlog

Decided in T-242 on 2026-10-12.

- **A done node** in the graph keeps its title readable: a green filled glyph and the title in a done colour (green-tinted, dimmer than live text), not the backlog grey; no strikethrough.
- **Container nodes** (epics in a release graph, releases) carry `done/total` of their children and the count in work where task nodes carry the criteria fraction.
- **The same colour rule** applies to done rows in the items panel and on the board wherever done items are shown.

### 3.4 The verifier's item in the sessions panel

Decided in T-239 on 2026-10-12. The panel shows a verifier's held item with its role (built as T-168). When a verifier holds several items, the column shows the latest hold and `+N`. Before a hold exists, the item named by the latest review or QA request delivered to the session shows dimmed, until the hold replaces it.

### 3.5 Stopped sessions: resume, archive, cleanup

Decided in T-257 on 2026-10-12.

- **Resume.** `r` on a stopped row and the palette action "Resume session" relaunch the same harness session through the harness's own resume, keeping the cland name, role and claim; for this the hub records the harness session id at launch. When the harness cannot resume, the action says so and offers a fresh launch with the same brief.
- **Archive.** `d` on a session row archives it; `A` keeps showing or hiding the archive section. An archived session leaves every group and the default `session.list`; the journal keeps it.
- **Cleanup.** A stopped crew session (Implementer, Reviewer, QA) is archived automatically one hour after its item merged or closed, otherwise 24 hours after it stopped. The human's own sessions (Aides) never archive automatically. The background "more" fold shows the latest 20 stopped sessions and a count of the archived. `cland session prune --older-than <duration>` deletes the hub's records of archived sessions, never the journal.

### 3.6 The verification queue as the human sees it

Decided in T-246 on 2026-10-12. v0.1.2 adds no general queue API: `cland verify` (v0.1.1) is the queue for the suite, merges are serialized by the hub, and other resources wait for a need. The human-facing part: the `verify:` line in the sessions panel header becomes a one-line summary of the queue (who runs and for how long, how many wait) and opens the queue view (holder, waiters in order with their wait, the admission ETA from the median run). The human's own `npm test` goes through the same queue: the local runner does not start while the hub's queue is busy unless `--force` is given.

### 3.7 The inbox principle

Decided in T-247 on 2026-10-12. The inbox holds the now layer only: sections by kind (asks and approvals, requests addressed to the human, direct messages, plan approvals), each newest first, showing the last N with a folded "N more". Notifications and events leave the inbox for a separate events view, newest first, capped. The chip equals the inbox count (v0.1.1, T-235). The form is decided by a mockup in the explorer map.

The sections for the explorer, the item card, the release scope rows and categories arrive from the map.

## 4. The release

Decided on T-228 on 2026-10-12 (round 1).

- **Goal.** As section 1; the release is named "Working with items".
- **Scope.** Everything under T-228 is in v0.1.2. T-248 (the key-encoding matrix in the human's terminals) is the human's own task, not crew work, and does not hold the release.
- **Lanes.** Workbench: the core, the inbox (T-247), the sessions panel (T-239), stopped sessions (T-257). Hub: remote executors (T-256), the queue UX (T-246), accounts and limits (T-240), per-model performance (T-255), the tech debt T-253 and T-254.
- **Order.** The hub lane starts with T-256 so the rest of the build runs its suites on cloud VMs; the workbench lane starts with the explorer core.
- **Fog and AFK work.** One wayfinder map for the explorer cluster (mockups on the canvas and a Neovim prototype, as in v0.1). In parallel, AFK: a prototype run of the suite on a DigitalOcean 8 vCPU VM (T-256, branch `prototype/remote-executor`), research on harness limits and account selection (T-240, `research/account-limits`), research extracting per-model task data from the journal (T-255, `research/model-performance`).
- **Secrets.** The DigitalOcean token lives in the human's shell environment (`DIGITALOCEAN_TOKEN`); the prototype reads it and never stores it; its VMs are tagged and swept.
- **D23 accepted.** Detection and the bounded stop stay as shipped in v0.1.1; the fail-fast exit is T-253, ordinary tech debt, not raised.
- **Crew.** As in v0.1.1: Implementers on Codex gpt-6.1-sol, Claude Code roles on sonnet, Reviewer pool 2; plan approval `human` for the explorer epic only, `none` for the rest.
- **Definition of done.** As v0.1.1 (D16, D19 of v0.1 §4): each epic's demo run by QA on `dev` with a clear verdict, v0.1.2 released with `cland release --item T-228`, a retrospective artifact of the run.
