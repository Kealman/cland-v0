# hub/test/case-deadlines.test.ts

The two `suite case retains roots and native denial until rejected resource close
is repaired` cases enter their whole-case supervisor before acquisition.
They register the rejecting close on the outer context and on the distinct
fixture proxy, respectively; both cleanup identities must be fenced.
Each invokes the registered cleanup hook with an injected close rejection and
checks the literal error identity (inside the existing case-hook wrappers for
the proxy), retained scratch root and installed native
guard. Repair exercises that same cleanup owner, confirms close before root
removal, then observes guard restoration. Work counts prove the failed close
runs twice and a confirmed close is never replayed; there is no elapsed-time
assertion. Setup and proof observations use shared load-scaled bounds.
The two runner-case close controls use the shared durations-runner fixture
with an injected execFile boundary and a positively controlled native guard.
Their stageCase supervisor owns every hold before acquisition, with independent
fallback release and named entry/drain observations. Closing the nested case
must fence a held configuration continuation before launch (zero native effects).
For an already acquired fake child, closing must request stop before joining
its held completion. The root and inner guard stay retained until the producer
emits close and completion settles; real registered cleanup then removes the
root and restores the outer guard. Both controls assert work counts and final
closure/removal facts, with no subprocess or network call.

The two generated `stage case TestContext abort fences held writer` cases drive
a real AbortController supplied as a controlled TestContext.signal. Before any
normal hook runs, abort must synchronously refuse new admission. The original
held filesystem writer then completes; the next step stays fenced. Real fixture
cleanup observes the root removed only after positive resource close. The
rejected-close variant exercises the actual removal guard, retaining the root,
installed native guard and seam until a successful cleanup retry. These cases
prove stageCase ownership boundaries; stage-closure-component covers stage data.

Whole-case users supply the shared beforeDirectories and guardDirectoryRemoval
adapters. Enrollment happens before acquisition; `run` refuses without it.
Each acquisition callback calls adoptRoot before returning, so even a late
result attaches the positive join guard. Normal and signal cleanup call the
same owner: fence admission, release held controls, join whole sequences and
named waits, then invoke captured teardown. Guard failure retains storage/root.
Wait-only T1 users retain raw-after behavior and import no native cleanup module.
The registration control checks the injected shared path without sending a
signal; held controls release through that same owner and preserve their final
completed-write, fenced-step, adopted-root and removed-root assertions.

`caseDeadlines.run` admits an entire asynchronous case before its first resource
acquisition. Each `step` checks the shared fixtureWork fence before admission;
late acquisitions are adopted by the same proxied teardown hooks. Cleanup closes
that owner and joins the entire continuation before invoking resource/storage
teardown, then drains the existing named waits. The fixtureWork implementation
is unchanged.

Held acquisition and writer controls arm an entry receipt before triggering
cleanup. A separately bounded setup observation precedes release. They retain
the final assertions that the admitted write completed, later admission was
fenced, late roots were adopted and root removal followed the join. Fake-clock
startup/teardown deadline controls retain their previous assertions. No cloud,
browser or worker process is required; projectHub writers stay in-process.

The default `fixtureNativeGuard` and fake `receiptFixtureCase` regressions use
an injected resource whose close rejects with an exact error identity. Both
assert the positively controlled native launch guard remains installed after
rejection, then repair the close and observe successful closure before native
restoration. They use no subprocess, network, clock delay or live database.
The complete callbacks run under stageCase before guard acquisition, with named
load-scaled setup and proof observations. The supervisor joins the original
continuation before fallback repairs/drains. Both controls invoke the registered
outer cleanup hooks for rejection and repair; the receipt case never bypasses
the outer owner to drain nested fixtures. It also checks successful hooks and
resource closure are not replayed. Existing lease/deadline tests remain intact.

`caseDeadlines.close` retains its in-flight cleanup across observation expiry.
A settled rejection clears the attempt cache for retry, keeping original work
joined and admission fenced. Successful hook receipts survive the retry, while
failed hooks run again. Previously the rejected promise was cached permanently.
Fake receipt cases fence their outer process-cleanup owner as well as their
nested guard owner, so the normal outer hook can reach the repaired closer.

`fixtureNativeGuard` defaults to fenced resource, hub and directory cleanup.
Failed steps retry; completed steps do not rerun. Explicit `fenced: false`
retains the legacy catch-and-continue path and requires a caller-specific
ownership justification. There are no such callers in the audited tree.
`receiptFixtureCase(..., true, ...)` remains a native fixture choice and does
not install this fake guard.
