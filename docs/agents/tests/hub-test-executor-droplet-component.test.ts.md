# hub/test/executor-droplet-component.test.ts

The uploaded tier-status VM case uses `guardedLeaseCase`: ownership is enrolled
before guard setup, dynamic import has its own named setup wait, and each VM
evaluation is an admitted step. The shared sequence fences before joining on
normal or signal teardown; the launch guard verifies only after callback and
cleanup drainage. Preserve native-exit, metadata, byte-bound and descriptor-close
assertions while testing entirely through in-memory VM I/O.

The loader control positively observes a pool-image import before trapping all
synchronous filesystem exports. Recovery with no hosts directory must complete
without requesting that module or reaching a provider. The serving-path trap
is shared with session-credential-io; it is restored only after original work
settles, and the loader hook is then deregistered.

Four held-index controls cover direct startup and periodic reconciliation with
the project retained or deleted. Hold the demo-directory mkdir before closing,
then require reconciliation completion before close permits storage disposal.
The deletion cases deliberately remove the root beneath that held writer with
three bounded native removal retries (1 ms retry delay), release it, join close,
call close again, and require `stat(root)` ENOENT plus the structured
`run-directory-missing` diagnostic. Retained controls require the durable index.
Whole-case ownership and the native launch
guard remain active through the original work and cleanup.

guardedLeaseCase lives in executor-lease-fixture.ts and owns manual filesystem
patches until the original callback and writers join. Holds register their
release before admission. Cancellation controls execute the registered cleanup
hook while root setup, mkdir or rename is held; they require late root adoption,
native write completion before removal, and seam retention through the resumed
writer boundary. The guard positively checks callback/custom-promisify/native
spawn routes and verifies no unexpected launches before restoration.

Each synthetic-context control pre-enrolls its real test's fallback before
acquisition. The fallback always begins the captured synthetic cleanup, releases
both holds and bounds the join of original producer plus disposal; cleanup
failures propagate. Happy-path and fallback calls share one disposal promise.
The early-setup-failure control skips body-triggered disposal, invokes this same
fallback and requires root ENOENT plus restored rename and native spawn globals.

The two repair-to-maintenance cases are T2, moved here from the T1 maintenance
policy matrix. They retain the original no-prune and exact-id report assertions;
their earlier T1 runs do not count as T2 proof. The two compaction-fault cases
check both confirmed-deletion and already-released paths, preserving returned,
durable lease and ledger accounting while retaining hot membership and a
secondary maintenance diagnostic.

These four cases enroll caseDeadlines before any acquisition, separately bound
guard and fixture setup, adopt each root and fence every caller continuation.
The shared fakeNativeGuard positively exercises callback, custom-promisify and
prototype launch routes. Its verification/restoration waits until fixture-work
drainage and teardown complete, including executor close before root removal.

Three additional held-directory cases exercise writeLease, executor saveRecovery
and pool saveRecovery independently. Each starts below an existing run anchor,
holds its final directory mkdir, deletes its root with the same bounded retries,
then resumes and joins the writer. Require its native ENOENT rejection and the
root's ENOENT stat receipt. Restore the filesystem mock only after the writer
settles. All three fail under their old recursive mkdir implementations.

T2 status regressions inject Machine's native execution callback and provider
lookup, with a fake clock and disposable lease storage. No SSH binary, droplet,
user lookup or machine service runs. User lookup, private-key format/permissions
and spawn failures must retain unknown status with the local-client cause past
300 seconds, clear an older durable unreachable timestamp, then recover to the
remote running receipt. Keep the prior unknown reply without cause in the
ordinary connection-timeout control, followed by lost at exactly five minutes.
Provider absence (404 or null resource) and expired lifetime still win; provider
lookup failure alone remains unknown. CLI role controls use the in-process hub.

Each status scenario enrolls caseDeadlines with beforeDirectories and
guardDirectoryRemoval before acquiring its root. The whole admitted callback
joins status and lease I/O before root disposal; each continuation enters
through the shared step fence. Executor teardown is registered through the
owner's fixture hooks. Do not use a cancellation experiment on the live project.

Status tests call the production DropletExecutor repeatedly, retaining its
DropletRun observer. Capture its structured LogFn sink before the first poll.
Each hold emits one enter event and one leave event, with run id, cause and the
bounded transport error retained on leave; repeated held/recovered polls emit
no duplicate. Provider-loss exit also retains the original diagnostic.

The uploaded status-program regression runs the production generated JavaScript
in a VM with fake filesystem/process boundaries and a positively controlled
native-launch guard. It rejects whole-file cause reads, counts at most4096bytes
plus one oversize sentinel across short reads, and observes descriptor close.
Valid, oversized, missing, failed-read and failed-close receipts preserve the
recorded exit, including a green exit with unavailable cause metadata. The
bounded reader implementation is shared with local commands and embedded by the
hosting source, so production activation still requires a hub restart.
The VM case registers teardown before guard acquisition and captures its restorer
through the same pre-mutation owner callback as the fake command matrix.
