# hub/test/discord-pairing.test.ts

T2 on Node v24.21.0. Run this file alone with
`node --test hub/test/discord-pairing.test.ts`. No browser, native harness or real
platform. tempProject/projectHub and cland seal HOME/XDG/Git and credentials;
syntheticRemoteSecrets supplies the made-up Discord token through the daemon
environment. The in-process loopback fake owns its HTTP and gateway shutdown.

The production factory/frame test observes global GET/PUT receipts: one eight-
subcommand definition on first start, no write after restart, one repair on drift.
Writable-field comparison ignores Discord-owned ids and optional defaults. A
metadata-only restart writes nothing; an unexpected required option on pair is
removed by exactly one overwrite.

Native INTERACTION_CREATE via control/interact drives private pair callbacks.
The fake clock proves code expiry at 15 minutes and the per-stranger third-request
silence; an observed later callback is the ordered-dispatch receipt. Code replies
retain the numeric user id and approve command. Actual CLI approval must print
the stored name/id and produce the native @original Approved edit. Refusals cover
a member, another administrator and the paired user in another channel. The
paired user's pair there moves the binding only on approval and sends one line
to the captured old channel. Hub restart plus real remote status --json and SQL
TEXT/value assertions preserve ids above 2^53. After hub stop, scan database,
log, journal, captured frames and status for bot and interaction credentials.

The fake contract control accepts a callback at 2999ms, refuses its second
acknowledgement with 40060, refuses a first at 3000ms with 10062, accepts an
original edit at 899999ms and refuses it at 900000ms with 10015. Tokens are never
returned in control receipts. The fake records only callback type/data and edits.
Existing pairing-approval and remote-cli prior-wire tests cover optional callback
and old-hub compatibility; Telegram has no pairingApproved implementation.
