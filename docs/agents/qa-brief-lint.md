# QA brief lint

Run `cland qa lint <brief>` from the build under test before requesting item or stage QA. In this repository use `node hub/bin/cland.ts qa lint qa/briefs/T-957.md`. Drafting ends when **qa lint passes at the build**. The command reads the brief and this executable’s help and built-in permissions. Source references read Git blobs from HEAD of the current repository, or `--commit <sha>` (also `--commit=<sha>`); run from the build’s repository root. It ignores uncommitted source. Keep the executable on the build being tested so its help and roles also match. It never executes a command from the brief, needs no running hub and runs in production installs with development dependencies pruned. Its verification checks use the same dependency-free policy as runtime admission.

Exit codes: 0 has no findings; 1 prints one `file:line: finding: command` per finding (the command is omitted for record metadata); 2 is a usage, file-read or build-source read error. A clean source check prints the resolved full SHA. A brief without source references needs no Git repository unless `--commit` is supplied. `cland qa --help` prints the synopsis.

Use a Markdown check table with `id` or `case`, plus `command` and `expected` columns. `check` and `check id` also identify check IDs. IDs are unique across these tables, including case and manual tables. A `surface` column accepts `headless-grid`, `tmux`, `web-terminal`, `hub-api` or `real-browser`; executor names such as `droplet` belong in a separate `where` column. Record real-browser computer-use cases with `qa-record.sh note` and screenshot evidence; acceptance by lint grants no browser access. The qa skill’s “Web briefs” section defines the QA-only launch, normal HOME/keychain with a dedicated cland profile, page/permission scope, Cancel-only system dialog handling and tab cleanup. Commands may also appear in `command and expected outcome`, `method`, `action` or `note` columns. Wrap commands in backticks; a plain command cell works too. Escape a shell pipe as `\|` in Markdown.

Assign the responsible role with a `role` or `actor` column, a `Role: Implementer` line, or a heading containing only the role name. Supported roles are Coordinator, Lead, Implementer, Reviewer, QA, Aide and Human. A row assignment overrides the section or brief assignment. A role-specific heading applies until the next heading. A brief-wide `Role:` applies through sections. Without an assignment, only syntax and record checks run. Use explicit Human rows for commands in a sealed scratch project that act as its human.

The linter checks the build's built-in role grants, including scoped task operations. Verification uses its separate CLI report/mode policy, matching scheduler admission rather than requiring built-in `verify` tool grants; adding the custom `verify` grant to the known-tool table does not change that policy. It rejects an Implementer's submitted verification without a report topic (a dry-run may omit it), a report to `general` or `agents`, and reserved full verification from Implementer, Lead or Reviewer. Use the item's topic, for example `cland verify --report "$TOPIC"`. An Implementer topic command needs a nonempty item option, for example `cland topic create "QA checks" --item T-957`; the title is not an item binding. Aide verification uses the same report-grant and mode/occasion decisions as runtime: explicit report topics may have no addressees or named sessions (`--to <session-name>`); role addresses, `all`, globs and lead addresses are refused. A literal `--report` value that resolves as a recipient follows the same named-send rule; for example `--report reviewer` is refused, while `--report <session-name>` is allowed when the hub can resolve a report topic. Explicit `--to` overrides that fallback. With no report, the CLI defaults to Agents addressed to the Coordinator role, so an Aide must override `--to` with a session name or supply `--report <topic>`. Report-free `--dry-run` skips publication grants; a preview with `--report` checks them. Aide `all`/`--all` and integrated occasions are refused. The hub still checks the live claim, actual topic ownership, topic/recipient existence, configured grants (including custom role names) and authorized verification occasions. Lint does not grant permission.

Every variable `rm` operand in check commands or shell (`sh`, `bash`, `shell`, or unlabelled) fences is a finding, even after a path guard. Replace it with the literal scratch path. Single-quoted dollar signs and escaped dollar signs are literal. Lint does not remove any path or certify that a literal path is safe.

This is a mechanical preflight, not a shell interpreter: it checks literal `cland` invocations and executable paths in check command columns, stops cland flags at `--` or a help-declared forwarded argv boundary such as `open [dir] [nvim args…]`, and does not expand helper functions, variables or dynamic argument lists. Expected-output prose and non-shell fences are not commands. Probe design, exact receipts, load restrictions, isolation and measured timing still follow the QA skill's “Probes that mislead” and project rules.

## Trust model

The Coordinator writes QA briefs, and lint reads the project's own test sources. This is a drift detector, not a security boundary; adversarial decoys in test sources are out of scope. The title-check bar is the project's real `test(`/`it(`/`describe(` calls with plain string or static template literal names. Where the bounded lexer cannot distinguish regex from division or a block from an expression, an unmatched name is **unresolved**, fails lint, and points to generated cases; it is never silently accepted as passing or asserted absent. TypeScript remains a development-only dependency used by the corpus test oracle, not by the shipped command. T-1264 tracks a proper parser if real briefs require unsupported source syntax.

## Build references and counts

Name test files by repository-relative path, such as `web/test/inbox.test.ts`; a bare basename works only when unique at the selected commit. Literal `.test` and `.spec` files with JavaScript/TypeScript extensions are checked everywhere in the brief, including fenced probes. A missing file or ambiguous basename fails lint.

Name a title as `test: ` followed by a backtick-quoted title, `test title: `, or prose such as test `the exact title`. Use `Tests: ` followed by comma-separated backtick-quoted titles for a list. A title on a line with file paths must be declared in one of those files; otherwise it uses the files named elsewhere in the brief, or all test files if none are named. The dependency-free source scanner reads literal `test`, `it` and `describe` call titles (including skip/todo/only and static template strings); comments and unrelated strings do not declare a test. The offline CLI works in release installs with development dependencies pruned. Literal `--test-name-pattern` values must be valid regular expressions matching a declared title in that scope. Computed/generated titles require the generated cases at the build: lint cannot certify a runtime-generated name and a zero static match fails rather than passing silently. An ambiguous source scope reports unresolved instead of absent.

Name a selector as `Selector: ` followed by a backtick-quoted CSS selector, or use a literal argument to `locator`, `querySelector` or `querySelectorAll` in a probe. Lint checks simple tag, class, id and attribute atoms against `web/src` at the commit; source outside that directory does not satisfy them. Attribute values must occur together with their attribute name. This checks source presence, not DOM structure, visibility or relationships. Dynamic selectors, pseudo-classes and computed attributes require separate build-specific evidence; use simple literal selectors for this preflight.

Literal totals such as “23 tests”, “twelve members”, “4 items”, `# tests 23`, `Members: 12` or `item count = 4` fail lint with a replacement hint. Derive required test names and totals from generated cases at the build; derive current membership with `cland task plan show <item>`. Keep assertions on those derived identities. Deadlines, viewport sizes and item ids are not membership counts.
