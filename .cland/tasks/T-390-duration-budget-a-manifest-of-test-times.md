## Summary

New tests average 2.74 s against 1.69 s for the suite, and nothing pushes back, so the full suite grows by about 2.4 minutes of wall time a day. This ticket records each test's and file's time in `hub/test/durations.json` and adds a budget check to the runner. An unlisted test over 5 s or file over 60 s fails its run, and the suite report names the top regressions. It saves nothing today. It stops the drift and provides the balancing data that sharding and coverage selection in v0.1.3 need.

## Parent

"Test speed: quick wins" (R-228), tracer bullet 5; research #3 (`docs/research/test-speed.md` §3.7; §1 "Trend and queue").

## What to build

**The manifest, `hub/test/durations.json`**, versioned like `hub/test/shards.json`:

```json
{ "version": 1, "source": { "artifacts": ["A-…"], "commit": "…" },
  "budget": { "testSeconds": 5, "fileSeconds": 60 },
  "files": { "hub/test/suite.test.ts": { "seconds": 242, "tests": 61 } },
  "allow": { "hub/test/executor-safety.test.ts": { "file": true, "seconds": 117, "reason": "…" },
             "nvim/test/thread.test.ts::generated live appends…": { "seconds": 33.1, "reason": "…" } } }
```

`files` holds every test file's test-time. `allow` holds the tests and files over budget at generation time, each with a reason, which the Implementer writes for the initial set from the research's top-30 table and the file table. The Neovim files (`nvim/test/**`) are included.

**The generator, `hub/test/durations.ts`.**

- `node hub/test/durations.ts refresh <log>…` reads one or more integrated suite logs, takes the median per test over the logs, and writes `files` and the timing fields of `allow`.
- It keeps existing reasons, adds new over-budget entries with reason `TODO` (which the check refuses), and drops entries for tests that no longer exist.
- Per-test timing comes from the runner's per-test records (below), with the spec reporter's top-level `✔ … (ms)` lines as fallback for older logs, the way the research parsed them.
- `npm run test:durations` runs the refresh, beside `test:shards`.

**The check, in `hub/test/run-suite.ts`.**

- The runner adds a second `--test-reporter` with a file destination. It emits one record per top-level test (file, name, duration) per phase.
- At the end of a phase it compares the executed tests against the manifest. A test absent from `allow` over `testSeconds`, or a file absent from `allow` over `fileSeconds`, prints `duration budget: <file>::<test> <s> s > 5 s (add to hub/test/durations.json with a reason)` and makes the run's exit code non-zero.
- A missing manifest disables the check, as a missing `shards.json` disables sharding.
- A `TODO` reason fails the check at admission, through the same path as `lintHubShards` / `lintHubShardTree` in `hub/src/suite-shards.ts`.

**Regressions in the report.** The runner prints up to five `duration regression <file>::<test> <before> s → <now> s` lines: tests at least 1 s and 50% slower than the manifest. `suiteSummary` in `hub/src/hub/suites.ts` (line 64) keeps them among its timing lines, so the posted result shows them.

**The refresh routine.** The Coordinator refreshes the manifest from the latest green integrated log at each stage close and commits it on `dev` like a docs change. `docs/agents/tests.md` says how a session adds an allowlist entry with a reason in its own branch.

**The initial manifest** is generated from the integrated run that closes stage 1 of this epic, after the selection and timing tickets, so the timer-bound tests have already dropped under 5 s.

### coord · 2026-10-15T03:27:21.199Z

Decision (human, ask 225afa4b, 2026-10-15 03:27Z): the duration budget fails a run only for a test or file that is new to the manifest, absent from both `files` and `allow`, over 5 s or 60 s. A known test or file that runs over budget, or slows down, produces a `duration regression` line in the report and does not fail the run.
