---
name: release
description: Publish dev to GitHub with a version the human chooses, or recover a pending cland release.
---

The Coordinator performs this skill from its own shell. **Never delegate a release to a sub-agent:** a sub-agent in the Coordinator's shell inherits its authority. The human may also run `cland release` from their own shell.

1. Work in the project root on `dev`. Read the current release item with `cland task view T-n --json` and use or open its bound topic. The current release is the open top-level item with the lowest semver version. Commit outstanding tracker and docs changes on `dev`, keeping unrelated staged work out of that commit, and publish them to the territory with `cland push` from your own shell. Resolve any fast-forward refusal before releasing. Release includes all committed work in `main..dev`; a project version bump is an ordinary item reviewed and merged before release.
2. Read the item's version and the human's recorded version decision. When a recorded decision exists, ensure the item's version matches it before previewing. If the version is missing, ask the human to choose it, then record it with `cland task edit T-n --version X.Y.Z`. Before the dry run, ensure the root `package.json` version equals the release's through an ordinary commit reviewed and merged onto `dev`. Release reads the committed `dev` version and refuses a mismatch with `release-version`; it never writes the bump. Projects without that file or its `version` key release as before. Before the dry run, when releasing cland itself (the repository containing `hub/bin/check-opencode.ts`), complete the [OpenCode compatibility check](OPENCODE-CHECK.md). Run `cland release --item T-n --dry-run`. Resolve every refusal before continuing: close or move open descendants; when GitHub has commits dev lacks, run `cland sync` from a clean root, then preview again. Share the resulting notes, version, commit and refs in the release topic through `artifact.create`.
3. Ask through the Coordinator's `ask` in that topic: show the preview's notes and version and request approval to release that build, allowing a free answer (`free: true`). Wait for approval. The version comes from the human. An Aide or a stand-in named by the human may relay approval and the version only when the human has recorded that version decision; cite the record (for this project's v0.1, D18 in docs/spec/v0.1.md records v0.1.0). A stand-in never invents a version; an unrecorded version needs the human's decision. Follow the project's recorded acceptance policy: D19 uses QA's clear T-117 walkthrough instead of a separate human acceptance pass, and the notes retain T-109 C1 and T-111 M7 as verified in v0.1.1.
4. If the approved version differs, record it on the item, run `cland release --item T-n --dry-run` again and show the resulting notes and version in a fresh approval ask. If dev or the notes changed, preview and obtain approval for that build again. Once the preview is approved, run `cland release --item T-n` yourself. It prepares an annotated tag with the item Notes, epic deliverables and commit notes, pushes main and the tag atomically, advances main locally and in the territory, then comments the tag and full commit on the item and closes it. The next open release becomes current. It makes no GitHub API calls.
5. Report the returned version and full commit in the release topic. If it says `released; follow-up failed`, GitHub already accepted the release: preserve `.cland/release.tmp`, repair the named local, territory or item obstruction, and retry **the same item and version** with `cland release --item T-n`. The receipt pins the published item, tag, commit and notes, so a restart or later dev commit cannot publish a different release on that retry. A failed push can also have lost its reply; retry the same item and version to let cland check the receipt against GitHub. With a pending sync, preserve `.cland/sync.tmp` and finish `cland sync` before releasing.

For a project without a release item, `cland release <chosen-version> [--dry-run]` retains the version-based flow: run the same applicable preflight check, preview the notes, ask for approval with a human-chosen version, then publish from your own shell. It does not comment on or close tracker items.

`cland sync` fetches GitHub and prepares a replay of dev's unreleased commits. Finish any pending `cland merge` follow-up first: sync refuses to rewrite a merge whose checkout, item, claim or topic completion is still pending. A dirty root refuses; a conflict names the files and leaves main, dev and the root untouched. Reconcile the conflicting work on dev, then retry. Sync publishes only to the local territory, never to GitHub. If it says `synced locally; follow-up failed`, preserve its receipt, repair the named obstruction, and retry sync; it finishes the same prepared replay.
