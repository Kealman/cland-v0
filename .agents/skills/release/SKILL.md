---
name: release
description: Publish dev to GitHub with a version the human chooses, or recover a pending cland release.
---

The Coordinator performs this skill from its own shell. **Never delegate a release to a sub-agent:** a sub-agent in the Coordinator's shell inherits its authority. The human may also run `cland release` from their own shell.

1. Work in the project root on `dev`. Read the tracker and commit its outstanding changes on `dev`, keeping unrelated staged work out of that commit. Release includes all committed work in `main..dev`; it never edits package or other version files. A project version bump is an ordinary item reviewed and merged before release.
2. Read the latest `vX.Y.Z` tag with Git. From `vX.Y.Z`, propose the next patch `vX.Y.(Z+1)`, minor `vX.(Y+1).0`, and major `v(X+1).0.0`; with no version tag, use `v0.0.0` as the starting point. Run `cland release <next-patch> --dry-run`. Resolve any refusal before continuing: when GitHub has commits dev lacks, run `cland sync` from a clean root, then preview again. Share the resulting notes and refs in the release topic through `artifact.create`.
3. Ask the **human** through the Coordinator's `ask`, in that topic: give the three concrete version options in patch, minor, major order and allow a free answer (`free: true`). Wait for that human's answer. The human's stand-in cannot choose or authorize the version; if an answer comes from the stand-in, ask the human directly and keep the release pending.
4. Run `cland release <chosen-version> --dry-run` when the answer differs from the preview or dev changed. Once the chosen version's notes and refs are reviewed, run `cland release <chosen-version>` yourself. It fetches GitHub, prepares an annotated tag with the notes, pushes main and the tag atomically, then advances main locally and in the territory. It makes no GitHub API calls.
5. Report the returned version and full commit in the release topic. If it says `released; follow-up failed`, GitHub already accepted the release: preserve `.cland/release.tmp`, repair the named local or territory obstruction, and retry **the same version**. The receipt pins the published tag and commit, so a restart or later dev commit cannot publish a different release on that retry. A failed push can also have lost its reply; retry the same version to let cland check the receipt against GitHub. With a pending sync, preserve `.cland/sync.tmp` and finish `cland sync` before releasing.

`cland sync` fetches GitHub and prepares a replay of dev's unreleased commits. Finish any pending `cland merge` follow-up first: sync refuses to rewrite a merge whose checkout, item, claim or topic completion is still pending. A dirty root refuses; a conflict names the files and leaves main, dev and the root untouched. Reconcile the conflicting work on dev, then retry. Sync publishes only to the local territory, never to GitHub. If it says `synced locally; follow-up failed`, preserve its receipt, repair the named obstruction, and retry sync; it finishes the same prepared replay.
