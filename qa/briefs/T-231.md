**Criterion ids.** The two checkboxes have no ids in the file, so `task view T-231 --json` shows `"id": null` for both. That is expected and is not a finding. A structured verdict stamps ids positionally on first touch (`docs/review-and-qa.md`, "Criteria in a verdict"):

After the verdict, read `task view T-231` again and confirm that C1 and C2 sit on that text. If ids already exist in another order, map by text and say so in the verdict.

What the shipped code says (read before judging; these are the rules, not findings):

- `needsYou` counts only asks, approvals and waiting topics (a topic `waiting for human` with no open ask) whose inbox layer is `now`. Notifications never count, even when a project override places them in Now (`docs/visibility.md`; `hub/src/hub/inbox.ts`, `InboxBoard`). Since T-235 the rows carry their `layer` and `needsYou` is computed from those same placed rows. Placement is also part of the publication signature, so a pin or mute that changes rows without changing the count still publishes (`hub/README.md`, `inbox.list` row).
- The workbench never derives the count. The chip (`nvim/lua/cland/bars.lua`) shows `▲ needs you N`, `✓ needs you 0` or a dim `needs you` while unknown. The panel winbar shows `INBOX` with `N need you` or `nothing needs you`, and the full-width view shows `Inbox · full width · N need you` (0 included). When the count is 0, the inbox body shows ` ✓ nothing needs you`.
- Not-clear verdicts and deaths are warn-level (D17). They stay in Watch even under a Now override, and they never count.
- A pin raises a record to `now`. A mute lowers its default or project layer by one step (now → watch → background → archive). Repeating a choice restores the default, and choosing the other one replaces it (`docs/visibility.md`, "Human pins and mutes"). Topic choices also affect that topic's asks and waiting entries; session choices also affect that session's approvals. The panels show only Now and Watch. Background and Archive rows leave the inbox.

local buf = vim.api.nvim_get_current_buf()
local out, seen, layer = { now = {}, watch = {} }, {}, nil

## Pitfalls

- The scratch hubs, the driver and the workbench must never see the QA shell's `CLAND_*` variables (`noclu`). A command that prints the root project's items or sessions has reached the live hub. When that happens, stop, record BLOCKED for that check, and do not repeat it.
- Write `[visibility]` before `hubstart`. A config edited under a running hub is not read (`docs/visibility.md`).
- Seed the waiting topic before the first `hubstart` of each project. The seed is the only hand edit, and it is made only in scratch projects. Never hand-write item files, `ui.json` or the tracker.
- `<Space>n`, `<Space>s` and `<Space>t` toggle: pressing the active one hides the panel. Use `<Esc><Space>t` before `<Esc><Space>n`, as the test does.
- **Load-sensitive tests: never run the full suite** (`npm test`, `cland verify`/`cland suite`). Do not run these files at all: `nvim/test/shell.test.ts`, `nvim/test/qa.test.ts` (long, shared fixtures), `nvim/test/thread.test.ts`, `nvim/test/plan.test.ts` and `hub/test/request-guard.test.ts` (T-213/T-223 timing). M1's files run one at a time.
- A test reported as `# SKIP` is not a PASS.

## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Run M0, then M1, the cases, M2–M8 (A, B, C in order, each torn down before the next), then M9–M14 and, if chosen, R1. Record each with `qa-record.sh`. At the end, make sure no scratch hub, driver, fake or `nvim` is left: `c hub stop` in each `/tmp/qa-T-231-*` with the wrapper, `ps` for `fake-claude`, `coord.mjs` and `nvim --headless … qa-T-231`. 3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS (R1 counts only if run). Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written, finish from there and never rerun a check under the same run id (the skill, "When a step fails").
6. Criteria by position: **C1 = M1, M2, M3, M4, M5, M6, M7, M8, THREAD-009, THREAD-010**; **C2 = M9, M10, M11, M12, M13, M14** (and R1 if run). M0 gates the run. Write the verdict from the root in QA's own identity (the real QA session: this is the one root write): `node hub/bin/cland.ts task comment T-231 "<text>" --verdict qa --result clear --run <run> --commit <full root dev SHA> --verified C1,C2`, or `--failed "C1=note"` with `--result "not clear"`.
