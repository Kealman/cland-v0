# QA brief: E-1536 — Definition of done (Users and sign-in modes)

This brief is the Definition-of-done demo of epic E-1536 (qa skill, "Epic demos on a named dev commit"). QA runs it in the human's place at a named `dev` commit and records one epic verdict that names, by id, the criteria it verified (C1–C7). Everything the run needs is in this file or in the files it names: whoever runs it cannot ask. Commands are for bash (zsh reads `$B:h` or `$S:q` as modifiers).

**Where it runs.** Every case runs locally, on macOS, from a clean detached worktree at the requested SHA, with `QA_DEMO_EPIC` unset. There is no `cland demo start`, so no lease, deadline, lifetime or cost. Each case names `local macOS` in its `where` column; none names `droplet`, for these reasons: the reused scratch functions use BSD `sed -i ''`; the browser rows use the suite's Chrome Headless Shell from the installed `playwright-core` and its CDP virtual authenticator; the Neovim files need the pinned Neovim; and the named files must run on the same machine and build as the scratch journeys they back. `cland demo status` reads freshness without a lease (skill: "This same check works without a remote lease after a local fallback"). No real browser, no GUI, no real harness and no real messenger: the scratch hubs run the fake `claude`, `codex` and `opencode` of `hub/test/fakes/`, and the remotes run only inside the named files against the loopback fake Bot API (`hub/test/fakes/telegram/`) and the fake Discord gateway and REST (`hub/test/fakes/discord/`).

The run has three parts, framed by the gates E1536D-00 to E1536D-02 and the freshness check E1536D-35:

- **Part T, named files at S** (E1536D-03 to E1536D-08). One row per criterion group: the authority table read from source (C5), then the named files for C1, C2 and C3, C4, C5 and C6, and C7, one file at a time from the build.
- **Part P2, the attribution journey** (E1536D-09 to E1536D-21). Scratch project p2 runs the committed stage-2 scratch functions (`qa/briefs/E-1536-stage-2.md`). A single-mode project switches to users. Its single-mode history moves to the first user, named from git's `user.name`. Users are added and invited from the CLI and from the web. Two users write in General from two web conversations. A Coordinator session (a real spoke) receives the deliveries and raises the asks. The asks and the approvals are answered by different users, first answer wins. An ask is answered with `--as`. The outcomes, the journal, the audit and the web workbench show who acted, and `cland auth reset` returns the project to single mode.
- **Part P3, the sign-in journey** (E1536D-22 to E1536D-34). Scratch project p3 runs the committed stage-3 scratch functions (`qa/briefs/E-1536-stage-3.md`), exactly as the stage-4 full-scope run did. It covers the single-mode link flow, the switch and `cland user add`, invites refused when unknown, revoked, expired or used, a password invite and a passkey invite (CDP virtual authenticator), a password-only invite without WebAuthn, sign-in and sign-out, cookies bound to users, withdrawal by user id with a stored test role refused by name, per-user pairings, the reset and the secret scans. ## Item

E-1536 (`kind: epic`, parent R-1530, labels `epic`, `v0.4`): Users and sign-in modes. A project chooses how the web admits people: `single` (today's one human) or `users` (a user per person, with a passkey or a password, created by invitation), and everything a person does through cland records who did it. Spec: `docs/spec/v0.4.md` §3.8. The demo is the item's `## Definition of done` (`task view E-1536 --json`).

These facts are reference only: E1536D-00 reads them from the tracker and Git at the run.

**Criteria.** Judge each by its text in `task view E-1536 --json` at E1536D-00. At writing:

- C1. `[auth] mode` is `single` by default with today's behaviour unchanged, switching to `users` creates the first user from the current identity, and `cland auth reset` is the only way back.
- C2. Users and the `admin` role live in `hub.db`, and an admin creates a user with `cland user add` or from the web and gets a one-time invite link.
- C3. An invited user registers a passkey or a password and signs in with it, and a used or expired invite is refused.
- C4. Messages, ask answers, approvals, pairings, web sessions and artifacts from a person carry their user, outcomes show who answered, deliveries to agents name the author, and the journal records the user of every human action.
- C5. The web edge's authority table has a user-role column through which every check passes.
- C6. In users mode the CLI acts as the first user and an admin may act `--as` another.
- C7. Each remote pairing belongs to one user, General reaches every paired user, and the first answer to an ask wins with the answerer shown on every copy.

If the ids or the text differ at the run, map by text and say so in the verdict.

### C7: first answer wins between two paired remote users

The DoD's remote sentence ("answers from one remote and reads the other's card fold with the answerer's name") is shown by the named files. `Telegram users answer once and fold every mapped card with the answerer` pairs Alice (chat 101) and Bob (chat 202). Bob presses his copy, and both mapped copies fold with `bob via Telegram` and an empty keyboard. The card closure records Bob's user id. The Discord fan-out cases do the same per channel and also have an unpaired member press first, who is refused natively with no `topic.answer` frame.

What no run can show without new code: **a second paired user pressing a copy of the same card** after or alongside the first. This is T-1650 (open, `needs-triage`, under C-326): "every card test has a stranger press it, then one paired user answers, and a second paired user never presses". The existing doubles cannot drive it from a brief:

- `fakeTelegramFixture(t: TestContext, …)` (`hub/test/fakes/telegram/fake-api.ts`) and `discordFixtureOwner(t: TestContext, …)` (`hub/test/fakes/discord/fake-api.ts`) are fixtures of Node's built-in runner: they take its context `t` and own their native resources through it (`onCleanup(t, close)`), and no standalone entry point starts them.
- The Telegram double's `/control/press` presses only as its fixed `Fixture human` (101) or `Fixture stranger` (202). Its `/control/update` and the Discord double's `interact` accept any paired user, but they are driven only from inside a test file, together with a `TelegramRemote` or Discord remote built in that file and a hub started by the test harness.
- The scratch hubs of this brief have no messenger: the sealed environment sets `CLAND_TELEGRAM_API_ROOT` and `CLAND_DISCORD_API_ROOT` to the sentinel `fixture-loopback-root-required`.

Driving two presses would need a new test file or a new standalone runner around these fixtures. That is a new harness, which this brief does not invent. What the run does show for "first answer wins":

## Probes that mislead

- **Overlays after the seal** (stage-4 run correction a54f9472). `env PATH=… CLAND_…=… cland hub start`, `TMPDIR=… node probe.mjs …` or any `NAME=value command` prefix inside a sealed subshell adds variables `fixtureEnvironment` never filtered.
