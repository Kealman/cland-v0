# QA brief: T-275 Epic: Sessions: stopped sessions, verifiers' items, the queue line

This brief is the Definition-of-done demo of epic T-275. QA runs it on `dev` in the human's place (decisions D16 and D19 of v0.1 §4: epics wait for no human demo). The verifier's item with `+N` and the dimmed pending request, resume with `r` and the fresh-launch offer, archive by hand and by rule, prune, the verify line with its queue view, and the human's `npm test` through the queue are exercised live in **one scratch project**. It has its own hub, its own suite lock path, shortened archive windows, the fake Claude Code and Codex harnesses, four driver spokes (a Coordinator and three verify submitters), six launched fake sessions, a small UI client and one headless workbench. The children's hub and headless tests corroborate, **one file at a time**. Everything the run needs is in this file or in the files it names.

Decisions taken during the build change how the DoD reads. Apply them; they are not findings:

- **`d` on a live session is refused**; only a stopped or exited row archives (decision 1 on T-275).
- **Resume restores the item claim only, never a verifier hold** (decision 2). A resumed verifier retakes its hold.
- **`prune --older-than` counts from the session's stop time** (decision 3).
- **The human's `npm test` waiter queues behind integrated `dev` runs and ahead of ranked item runs** (decision 4, built by T-319).
- **`--force` skips both the hub queue and the compatibility lease**, and the hub journals it (decision 6).
- **No journal backfill of stop times** (decision 7).
- **The column reads `T-b review +1`**: the latest hold with its role, then `+N` (decision 8).
- **"Merged or closed".** The rule starts the item window at the item's merge receipt or, for an item that never merged, at its close (`hub/README.md`, "Stopped or exited crew sessions archive automatically"). A real merge in the scratch project would need a branch, a review verdict and the merge gate. This run therefore **closes** the Reviewer's item (`cland task close`) to start the window. The merge-receipt path is checked by the hub test `a real task merge starts the stopped Implementer item window` (M5).
- **`prune --older-than 1d` in a fresh project.** Every archived record in the scratch project stopped minutes before, so `1d` must prune nothing. The run shows that with `--dry-run`, then prunes with `--older-than 1m`. The journal keeps the launches either way.
- **An ETA needs history.** With no finished run the hub has no median, so the summary reads `next ?` and the waiters' ETAs are `?`. The run first finishes one warm-up verify run of about 60 s, so the three queued runs show real ETAs.
- **An admitted human holder reads `human`.** The hub's holder for an admitted human runner has `kind: "hand run"` and `session: "human"`. Since T-319 the panel, the queue view and `cland verify queue` text label it `human`; any other `hand run` holder still reads `hand run` (`nvim/lua/cland/verification.lua` `holder_name`, `hub/src/cli/suite.ts`). Waiting human entries keep the name `human` too.
- **The 20-row cap of the "more" fold** is not shown live: that needs more than 20 stopped crew sessions inside one stop window. The headless test (M10) checks it on the stub hub. Live, the run checks the fold's header counts and its order (M19).
- **Queue order.** The run's verify submissions are unranked (their report topic is bound to no item), so the order shown live is plain enqueue order. The decided order (integrated `dev`, then human waiters, then ranked item runs) is checked by the hub tests (M6), not here.

**Criterion ids.** The eight checkboxes have no ids in the file, so `task view T-275 --json` shows `"id": null`. That is expected and not a finding. The structured verdict stamps them by position on first touch (`docs/review-and-qa.md`, "Criteria in a verdict"):

- C1: A verifier with several holds shows the latest and `+N`; a pending review or QA request shows dimmed until the hold.
- C2: `r` and "Resume session" relaunch a stopped session through the harness's own resume with its name, role and claim, from the harness session id recorded at launch, and offer a fresh launch with the same brief when resume is impossible.
- C3: `d` archives a session; `A` shows the archive; archived sessions leave every group and the default `session.list`; the journal keeps them.
- C4: Stopped crew sessions archive one hour after their item merged or closed, otherwise after 24 hours; Aides never archive automatically; the "more" fold shows the latest 20 and the archived count.
- C5: `cland session prune --older-than <duration>` deletes the hub's records of archived sessions and never the journal.
- C6: The verify line summarises the queue and opens the queue view with the holder, the waiters in order with their waits and the admission ETA.
- C7: The human's `npm test` waits in the hub's queue while it is busy, and starts at once only with `--force`.
- C8: `hub/README.md`, `nvim/README.md` and the role clauses describe resume, archive, prune and the queue line.

## Pitfalls

- Edit `lock_path`, `budget`, `cache_max_age_minutes` and the `[sessions]` windows **before** the first `hubstart`: the hub reads them only at start. `guard` refuses a hub start without them.
- A command that prints the root's items, sessions, topics or queue has reached the live hub, which means `noclu` was skipped or the command ran in the root. Stop, record BLOCKED for that check, and do not repeat it.
- **Never work around a hub refusal.** A refused send, hold, resume, archive, prune or verify submission is evidence: record its exact text. Do not edit a tracker, `hub.db` or `ui.json` file by hand, or reach the same result another way.
- **Never run `npm test` outside `$P`,** and never in `$P` before `test-entry.mjs` names `$LK` (its grep in "The fixture package"). In the root it would start the package suite and take the machine lock.
- **The release token is consumed by whichever crew run is waiting.** Drop one `release` file at a time, and wait for the matching `end` line in `crew.log` before the next.
- **The stop window is 150 s.** `impl-1` and `cx-1` must be resumed within two minutes of their stops (M15, M16), or they go to the archive first. `rev-1`, `rev-2` and `aide-1` are stopped together in M17 on purpose.
- **Do not commit in `$P` after M21 starts:** a queued verify run is cancelled when the head it was submitted at changes.
- `<Space>s` toggles the sessions panel: the workbench opens with it shown, so the first press hides it. `A` in the sessions panel toggles the archive section; `zR` opens the background fold.
- The fake sessions' `ran: …` replies to the human add rows to the human inbox and raise the needs-you chip. That is expected and not a finding.
- Holds move an item's status to `review` or `qa`, and a hold released at a stop keeps that status. Expected.
- An admitted human holder reads `human` in the panel, the queue view and `cland verify queue` text; the JSON keeps `kind: "hand run"` with `session: "human"` (Item). Only other hand runs read `hand run`.
- Read `hub.log`, `journal.jsonl` or `cland hub journal` only after the `flushLogs` barrier.
- Every launch passes `--harness` and `--model`. A launch without them can reach a real model.
- A targeted test reported as `# SKIP` is not a PASS.

## Procedure

1. Choose a run id, `qa-<date>-<n>`, and set `RUN` and `EV`.
2. Run the checks in this order, and record each with `qa-record.sh`. Captures go under `.cland/qa/T-275/<run>/` of the root.
   1. M0. If it is not PASS, stop: the run is BLOCKED.
   2. M1.
   3. The root test checks M2 to M11, one file at a time, never two at once, under the queue rule. Then M12's two cases.
   4. The scratch checks M13 to M25, in order. M13 gates them: if it is BLOCKED, record M14 to M25 BLOCKED and go to M26. M19 is judged from M17's, M18's and M20's screens.
   5. M26 and M27.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS. Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id (the skill, "When a step fails").
6. Criteria by position:
   - **C1** = M2, M3, M8, M14
   - **C2** = M4, M9, M15, M16

Verify exactly the ids whose checks are all PASS. A failed check puts its criterion under `--failed "Cn=note"` (one nonempty line). A BLOCKED or INCONCLUSIVE check leaves its criterion unverified.
7. Write the verdict from the root in QA's own identity. This is the real QA session, and the verdict is the one root write.    - Through the hub: `send` kind `report` to the requester in the request's topic, `qa clear T-275` or `qa not clear T-275`.
   - Without a hub: print every `runs.jsonl` line, the check table and `verdict: qa`, `result:`, `commit:`, `run:`, `verified:`.
