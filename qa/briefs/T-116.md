# QA brief: T-116 Epic: The task graph

This brief is the Definition-of-done demo of epic T-116, run by QA on `dev` in the human's place (decision D16: epics wait for no human demo). It checks the epic as a whole through the CLI, the hub and a headless workbench. Everything the run needs is in this file or in the files it names.

## Item

T-116: the human sees an epic's children as a graph laid out by their blocking edges, with status, claims and verdicts on each node and the plan's stages as a second grouping; a cursor moves node to node and the graph keeps its place under live updates. The demo is the narrative under `## Definition of done` (`task view T-116`); its eight checkboxes are C1..C8 in order. The epic's parent is the release T-130 (confirm it is `kind: release`). Children T-159..T-163 must all be closed before the run.

Criterion ids: at writing, `task view T-116 --json` showed `criteria: []` (no marks yet, so no stable ids were exposed). Run `task view T-116` first; if ids C1..C8 are shown, map by the checkbox text below and say so in the verdict if the order differs. If no ids are shown, report that as a finding (BLOCKED for the `--verified` step) rather than guessing.

## The scratch tree

Build it first, through the CLI only (never by hand-writing item files). Ids below assume a fresh counter (T-1 first); use the ids `task create` prints and say so if they differ. Titles are short on purpose.

```
task create "R" --kind release --version 0.1.0                  # T-1
task create "E1" --kind epic --parent T-1                       # T-2  (the graph's first parent)
task create "E2" --kind epic --parent T-1                       # T-3  (a second container for p / P)
task create "A" --parent T-2                                    # T-4
task create "B" --parent T-2 --blocked-by T-4                   # T-5
task create "C" --parent T-2 --blocked-by T-4                   # T-6
task create "D" --parent T-2 --blocked-by T-5 --blocked-by T-6  # T-7
task create "F" --parent T-2 --blocked-by T-4 --blocked-by T-7  # T-8  (A -> F is implied by A -> B -> D -> F: a hidden edge)
task create "G" --parent T-2                                    # T-9  (no sibling edge: the tray)
task create "H" --parent T-2                                    # T-10 (no sibling edge, then closed: the folded done tray item)
task create "X" --parent T-2                                    # T-11
task create "Y" --parent T-2 --blocked-by T-11                  # T-12
task link T-11 --blocked-by T-12                                # closes the cycle X <-> Y; if the hub refuses a cycle, record that and prove the cycle layout with M1b instead
task close T-10 --comment "done for the tray"
```

Plan (for M7): save as `/tmp/qa-T-116/plan.yaml` and run `task plan set T-2 --file plan.yaml`:

```yaml
stages:
  - name: base
    qa: { scope: affected, when: after-stage }
    lanes:
      - [T-4]
  - name: middle
    qa: { scope: full, when: per-item }
    lanes:
      - [T-5, T-7]
      - [T-6]
  - name: tail
    qa: { scope: none, when: per-item }
    lanes:
      - [T-8, T-9]
```

Backward edge: at the start of M6 (not before, M1 to M5 expect A on the first layer) run `task link T-4 --blocked-by T-9`. T-9 has no blockers, so no cycle; A (stage `base`) now waits for G (stage `tail`), an edge against the plan that M6 expects to be named.

## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Run every case and manual check above, in order, and record each with `qa-record.sh`.
3. Fix nothing. A failure is a finding: write down the case id, the command and what it showed.
4. Verdict `clear` only when every case and check in scope is PASS; otherwise `not clear`, naming each case that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written, finish from there and never rerun a case under the same run id (the skill, "When a step fails").
6. Criteria: the ids are C1, C2, … in the order of the checkboxes under `## Definition of done` (check with `task view T-116`; if the ids differ from the order below, map by the checkbox text and say so). Verify exactly the ids whose checks are all PASS, as the "Proves" column says: C1 = M1 (and M1b when it ran), C2 = M2, C3 = M3 and M5, C4 = M4, C5 = M6 and M7, C6 = M8 (and GRAPH-001), C7 = M9 and GRAPH-001, C8 = M10. Never use `--verified all` unless every row is PASS.
6a. Since T-196 merged, criteria operations work on epics: write the verdict with the structured flags, `--verified C1,C2,…` for the ids whose checks all passed (or `--verified all` only when every row is PASS, as the verdict is `clear`), and `--failed "C2=note"` for each failed criterion on a `not clear` verdict (repeat the flag; the note is one nonempty line). MCP `task.comment` takes `verified: "C1,C3" | "all"` or `failed: [{ criterion: "C2", note: "…" }]`. A verdict whose criteria sit only in the text does not satisfy the epic close gate (`docs/review-and-qa.md`, "Criteria in a verdict"). Use the full `dev` SHA as `commit`.
6b. Checks that need a human or a real model (the look of the graph, a real terminal, a real session) are BLOCKED, listed as "deferred to the T-117 walkthrough", and do not by themselves fail the verdict. Note the gate in `docs/review-and-qa.md`: a Definition-of-done criterion left unverified keeps the epic open, so a deferred check on a criterion's only proof leaves that criterion unverified; the Coordinator decides then (an `--override` in the human shell, not QA).
7. Through the hub: write it with `task.comment` (`verdict` qa, `result`, `run`, `commit`, and structured verified/failed fields) and `send` it to the coordinator as `qa clear T-116` or `qa not clear T-116`. Without a hub: print every `runs.jsonl` line, the case table and `verdict: qa`, `result:`, `commit:`, `run:`, `verified:`. The epic closes on a clear verdict once its children are closed (decision D16); the Coordinator closes it.
