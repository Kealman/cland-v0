- **Part R, records, read-only.** This repository's own `[verification]` values, the docs, the `cland init` template and the 40-landing selection replay (C2, C4, C5).

**Two stages, one run order.** Stage 1 (T-663 … T-669) had landed at writing; stage 2 (T-670 the droplet's `prepare`, T-671 the docs) had **not**. The brief is written for the full DoD. ## Pitfalls

- **Two worktrees, two jobs.** `$W` is the build and L2's candidate: never switch, edit or commit there. The plant goes only in `X`, on its own `qa/e614-$RUN-sel` branch from `S`. Never push it; L4 deletes it.
- **G3 first.** A live hub started before the newest hub-code commit on `S` resolves commands with older code: record L2 and L3 BLOCKED.
- **`--fresh` on L2.** Without it L2 can be a cache hit on the integrated green at the same tree and show no log of its own.
- **Scratch lock.** The scratch project's `lock_path` is rewritten before `hub start`. If `D2` prints a `lock_path` that is not under the scratch root, stop and record it: the scratch hub would contend for the machine lock.
- **Hub start.** The scratch hub starts fast; D2 retries `hub start` once. A second failure is a finding (record the text) and ends D2–D4.
- **Run order.** D2 empties the scratch root; D3 needs D2's project, D4 needs D3's. Never rerun one alone.
- **Counts, not command lines.** Process checks print counts; no environment or argument vector is printed (T-492).
- **One lease.** Never run `demo start` twice. Record D lines before `demo stop`.
- **Commands on the droplet** are argument vectors: `ds` passes each script as one `sh -c` argument; nothing in it is expanded by QA's shell.
- **Never work around a refusal.** A refused verify, demo control or verdict is evidence: record its exact text.
- `qa-record.sh` takes `E-614`. The verdict goes on `E-614`.
