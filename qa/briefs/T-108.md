# QA brief: T-108 Epic: A quiet Coordinator

This brief is the Definition-of-done demo of epic T-108, run by QA on `dev` in the human's place (decision D16: epics wait for no human demo). It checks the epic through the `cland` CLI against scratch hubs that launch only fake harnesses (Claude Code, Codex and OpenCode from `hub/test/fakes/`), persistent driver spokes standing in for agents, one headless workbench, the real project's hub journal read-only, and committed targeted tests as corroboration. ## Item

T-108: `send` gains `kind` (`progress`, `report`, `question`, `decision`; none is `report`), and `progress` notes start no turn but ride the recipient's next turn-starting delivery in one digest, across a hub restart; sessions `subscribe` / `unsubscribe` / list `subscriptions` over session, item, topic, role and subtree subjects for `session.state`, `task`, `topic`, `usage` and `artifact` events, delivered as one-line hub messages (`event · <event> · <text>`) digested at the next turn (`digest: "turn"`) or steered at once (`digest: "now"`, Codex and OpenCode only); hygiene (coalescing with `×N`, at most 10 event lines and `event · and N more`, final events, lifetimes, the `[hygiene]` keys `event_limit_max` / `event_limit_window_minutes`); `cland hub subscriptions` for the human; the claimant of an item leads it (`lead T-n` in `send.to`, `@lead T-n` in human text); default subscriptions of leads; the item runs its own review loop and the hub's `ready` event is the Coordinator's one delivery. The demo is the narrative under `## Definition of done` (`task view T-108`). The epic's parent is the release T-130 (confirm `kind: release`). Its children T-138, T-139, T-140, T-141, T-142, T-143, T-164, T-189 and T-199 must all be closed before the run (`task list --under T-108`; any other child found there is judged the same way in M0). T-108 is blocked by T-107: record its state in M0 (closed when this brief was written).

**The C8 counter** `$D/count.mjs` (used on the real journal in M1 and on the scratch loop in M15; prototyped against the real journal while this brief was written):

```js
// node count.mjs <journal.jsonl> <item> <lead session> <coordinator> [verifier …]
// Window: the lead's session-launched (or, for a lead the hub did not launch, the item's claim) to the item's
// ready write. Deliveries: event-delivery, send and human-send rows naming the coordinator in `to`. About the
// item: the item or one of its sessions as event subject, the item's topic, or a sender among lead and verifiers.
import { readFileSync } from 'node:fs';
const [file, item, lead, coord, ...verifiers] = process.argv.slice(2);
const rows = readFileSync(file, 'utf8').split('\n').filter(Boolean).map(l => JSON.parse(l));
const start = rows.find(r => r.event === 'session-launched' && r.session === lead)
  ?? rows.find(r => r.event === 'task-written' && r.id === item && r.op === 'claim');
const ready = rows.find(r => r.event === 'task-written' && r.id === item && r.op === 'ready' && start && r.ts >= start.ts);
const merged = rows.find(r => r.event === 'task-merged' && r.id === item);
const topic = rows.find(r => r.event === 'topic-created' && r.item === item)?.topic ?? null;
const people = new Set([lead, ...verifiers]);
const toCoord = r => Array.isArray(r.to) ? r.to.includes(coord) : r.to === coord;
const about = r => Boolean((r.subject && (r.subject.item === item || people.has(r.subject.session))) || (topic && r.topic === topic) || people.has(r.from));
const deliveries = rows.filter(r => ['event-delivery', 'send', 'human-send'].includes(r.event) && toCoord(r));
const line = r => [r.ts, r.event, r.kind ?? '', JSON.stringify(r.subject ?? null), r.from ?? '', r.topic ?? '', r.digest ?? '', (r.outcomes ?? []).join(',')].join(' | ');
console.log(`start ${start ? `${start.event} ${start.ts}` : 'NOT FOUND'} · ready ${ready?.ts ?? 'NOT FOUND'} · merged ${merged?.ts ?? 'none'} · item topic ${topic}`);
const inWindow = deliveries.filter(r => start && ready && r.ts >= start.ts && r.ts <= ready.ts);
console.log(`deliveries to ${coord} from start to ready: ${inWindow.length}; ABOUT ${item}: ${inWindow.filter(about).length}`);
for (const r of inWindow) console.log(`  ${about(r) ? 'ABOUT' : 'other'}  ${line(r)}`);
const after = deliveries.filter(r => ready && r.ts > ready.ts && (!merged || r.ts <= merged.ts) && about(r));
console.log(`after ready up to the merge, ABOUT ${item}: ${after.length}`);
for (const r of after) console.log(`         ${line(r)}`);
const progress = rows.filter(r => r.event === 'send' && r.kind === 'progress' && toCoord(r) && start && ready && r.ts >= start.ts && r.ts <= ready.ts);
console.log(`progress sends to ${coord} in the window: ${progress.length} (${progress.map(r => (r.outcomes ?? []).join(',')).join('; ')})`);
```

The journal fields it reads are the hub's own: `send` logs `to` as the resolved session names and `outcomes` as `<tag>:<outcome>` (`hub/src/hub/core.ts`, the agent `send` path), `event-delivery` logs `subject`, `kind`, `to`, `count` and `digest` (`publishEvent`), `human-send` logs `to`; a send with an empty `to` went to the human only. Read the counter before trusting it; if you change it, record the change.

## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Run M0, M1 and M2 from the root. Build the main project and run M3..M12 in order; the events project and M13, M14; the loop project and M15, M16; then M17 and M18. Record each with `qa-record.sh`. 3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. Verdict `clear` only when every check in scope is PASS (the deferred list and the optional M2 and M16 excepted); otherwise `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written, finish from there and never rerun a check under the same run id (the skill, "When a step fails").
6. Criteria by position (see "Criterion ids"); verify exactly the ids whose checks are all PASS: C1 = M3 (M1 corroborates); C2 = M6, M7, M8, M10; C3 = M7, M9; C4 = M10, M13, M14; C5 = M5, M11, M15; C6 = M4, M6, M12; C7 = M4, M8, M11, M14; C8 = M1, M15 (M2 and M16 corroborate); C9 = M18. M0 gates the run; M17 corroborates C1..C8 and a failure there fails the criterion its file covers. A failed check puts its criterion under `--failed "Cn=note"` (one nonempty line, repeated per criterion); a BLOCKED or INCONCLUSIVE one leaves it unverified. Never use `--verified all` unless every row is PASS.
6a. Write the verdict from the root, in QA's own identity (the real QA session; this is the one root write), with the structured flags: `node hub/bin/cland.ts task comment T-108 "<text>" --verdict qa --result clear --run <run> --commit <full root dev SHA> --verified C1,C2,…` (or `--verified all`), and `--failed "C2=note"` for a `not clear` verdict (`docs/review-and-qa.md`, "Criteria in a verdict" and "Epic closure by QA (D16)"). MCP `task.comment` takes `verified: "C1,C3" | "all"` or `failed: [{ criterion: "C2", note: "…" }]`. A verdict whose criteria sit only in the text does not satisfy the epic close gate. The `commit` must equal the root's `git rev-parse dev` at the time of writing, or the gate refuses it as stale.
6b. Checks that need a human, real time or a real model are BLOCKED, listed as "deferred to v0.1.1", and do not by themselves fail the verdict (D19). A Definition-of-done criterion left unverified keeps the epic open; the Coordinator decides then (an `--override` in the human shell, not QA).
7. Through the hub: write it with `task.comment` (`verdict` qa, `result`, `run`, `commit`, and structured verified/failed fields) and `send` it to the coordinator as `qa clear T-108` or `qa not clear T-108`, naming M1's observation about the post-ready stop and any C9 findings.
