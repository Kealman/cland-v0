# QA brief: E-425 Hub hygiene

This brief is the Definition-of-done demo of epic E-425. QA runs it in the human's place, at a named `dev` commit, partly on a droplet through the demo lease (decisions D16 and D19 of v0.1 §4). It has three parts.

- **Part D, the droplet.** One demo lease at the requested commit. On it: the build identity, a bridge left with no hub (its 60-second exit), a planted orphan bridge beside a live one for `cland doctor` and `cland doctor --fix`, and the criteria's and some children's own test files, one at a time. The doctor runs here because `cland doctor --fix` sweeps every own-user bridge on the machine: on the shared Mac it could end another session's test bridge mid-test. The droplet is the isolated machine the DoD names.
- **Part L, local macOS, a scratch project.** A scratch project under `/private/tmp` with its own hub, running the requested commit's code from a clean detached worktree, with the fake harnesses on its `PATH`. QA plays the human through the `cland` CLI. It covers a fake Claude Code bridge whose project is removed, the hub-start record and `npm run typecheck`. It never touches the live project's tracker, crew or hub.
- **Part R, the live project, read-only.** The cause on T-311, the leftovers report of the latest full suite, the TypeScript 7 comparison table and the docs.

The DoD's suite-input and run-identity part moved to E-579 with T-379 (the human, 2026-10-16, ask 396ec11a). This brief runs none of it: no cache-hit, tracker-commit or cancel checks, and no headless workbench reading of the `verify:` line.

Everything the run needs is in this file or in the files it names: whoever runs it cannot ask.

## Pitfalls

- **Identity.** QA's own commands (`cl`) act as QA on the live hub. Every scratch command (`c`) runs through `noclu`. A scratch command that prints the live project's items, sessions or topics reached the live hub: stop, record that check BLOCKED, and do not repeat it.
- **The DigitalOcean token.** The scratch hub must never see `DIGITALOCEAN_TOKEN`: `guard` checks it before the start. Never print the token or any environment.
- **No doctor on the Mac.** `cland doctor --fix` on the Mac could end another session's test bridge. It runs only in D3.
- **Process reads print counts or pids, never command lines** (`bridges`, `leftovers`, `alive`).
- **No C1 or C2.** The ids jump from the DoD's start to C3. Do not renumber them, and do not mark the removed ones.
- **One lease.** Never run `demo start` twice. Record D lines before `demo stop`.
- **Commands on the droplet** are argument vectors: `sh -c '<script>'`, with `$PWD` and `$T` inside the single quotes so the droplet's shell expands them.
- **Never work around a refusal.** A refused verify, demo control or verdict is evidence: record its exact text.
- `qa-record.sh` takes `E-425`. The verdict goes on `E-425`.

## Procedure

1. Choose a run id, `qa-<date>-<n>`, and set the Environment. Announce START in the request's topic, naming `S`. `dev` is not frozen: D14 decides.
2. Run, in order, recording each with `qa-record.sh` under `.cland/qa/E-425/<run>/` of the root:
   1. G0, G1 and G2. If any is not PASS, stop: the run is BLOCKED.
   2. Part D: D0, then D1–D13 one at a time on the one lease. Part L may run beside D4–D13. Then D14, and D15 last of Part D.
   3. Part L: the scratch setup, then L1–L5 in order. L3 and L5 always run, even after a failure, so nothing is left behind.
   4. Part R: R1–R4.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS. Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id; a D4–D13 rerun is the flaky rule's one rerun, in the same lease, reported beside the first result.
6. Before the verdict, run D14's freshness read again if `dev` moved since D14. Publish the evidence with `artifact.create` (kind `note`: the check table; the lease, executor, commit, lifetime and cost; which checks ran where; the findings) **in the epic's topic where the request was delivered**, and name its id in the verdict text.
7. Write one verdict on E-425 from `$W`: `cl task comment E-425 "<text>" --verdict qa --result clear --run $RUN --commit $S --verified all`. A not-clear verdict carries only `failed` (one `{ criterion, note }` per failed criterion, single-line notes) and names in its text the criteria that passed. The text opens with the check table, then the findings ranked high, medium and low. If the hub refuses the verdict as `qa-stale`, keep the evidence and report BLOCKED. Any other refusal: fix its cause and write only the verdict again with the same run.
8. Release the hold if the verdict did not: `cl task hold E-425 --release`. Remove the build worktree: `git -C $R worktree remove $W`.
9. Report with `send` kind `report` to `lead E-425` in the request's topic: first line `qa clear E-425` or `qa not clear E-425`, then the failed checks, the lease and its cost. Report any find outside the epic as a bug found aside, with its evidence, so the Coordinator files it under Bugs.

## Lessons applied from earlier runs

- E-423 and T-276: every scratch command strips QA's identity; the scratch `origin` is its own territory; `until_` waits on state, never on a flash.
- T-386 and E-423: no full suite; supporting test files one at a time on the droplet; a failure is rerun once and both results are reported.
- T-492: no secret or command line is ever printed; process checks print counts and pids.
- The cover-quiet rule: while the Coordinator holds the verify slot, nothing heavy runs locally.
