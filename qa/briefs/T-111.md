# QA brief: T-111 Epic: The human's own session

This brief is the Definition-of-done demo of epic T-111, run by QA on `dev` in the human's place (decision D16: epics wait for no human demo). It checks the Aide and the launch brief through the CLI, the hub and a headless workbench. Everything the run needs is in this file or in the files it names.

## Item

T-111: the human launches an Aide (`␣A`, a brief) that speaks for them, and any session can be launched with a brief delivered before its first turn. The demo is the narrative under `## Definition of done` (`task view T-111`); its eight checkboxes are C1..C8 in order.

## Build

- Branch: `dev` of the root project `/Users/evgeniyivanov/Projects/cland/v0` (not a task worktree). The build is the tip of `dev` when the run starts.
- Before the first case run `git status --short` and `git rev-parse HEAD` in the root. If tracked source outside `.cland/` is modified, or HEAD is not `dev`, record `BLOCKED` (the build is not a commit). Otherwise `git rev-parse dev` is the build: `qa-record.sh` puts its short form in every line, and the verdict's `commit` is its full SHA. A request that names a commit is honoured when it equals the tip; when it differs, record `BLOCKED` naming both commits (never run another commit silently).
- Run the demo in a scratch project, never in the root's live `.cland/`: `mkdir -p /tmp/qa-T-111 && git -C /tmp/qa-T-111 init && node "$CLAND" init /tmp/qa-T-111`, then `cd` there for `node "$CLAND" …` (set `CLAND=/Users/evgeniyivanov/Projects/cland/v0/hub/bin/cland.ts`, Node from `/Users/evgeniyivanov/.nvm/versions/node/v24.21.0/bin`). Read-only looks at the real tracker (`task view T-111`) stay in the root. Say in each note which project it ran in.
- Headless workbench: one `nvim --headless` process whose rtp includes `nvim/`, started with the scratch project's hub (`cland hub start`); drive keys with `nvim_input`, read the screen with `screenstring()` row by row (or use `cland --headless --qa <case.lua>`, `nvim/README.md` "QA cases"). ## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Run every case and manual check above, in order, and record each with `qa-record.sh`.
3. Fix nothing. A failure is a finding: write down the case id, the command and what it showed.
4. Verdict `clear` only when every case and check in scope is PASS; otherwise `not clear`, naming each case that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written, finish from there and never rerun a case under the same run id (the skill, "When a step fails").
6. Criteria: the ids are C1, C2, … in the order of the checkboxes under `## Definition of done` (check with `task view T-111`; if the ids differ from the order below, map by the checkbox text and say so). Verify with `--verified` exactly the ids whose checks are all PASS, as the "Proves" column says; a failed or BLOCKED check puts its criterion under `--failed "Cn=note"`, or leaves it unverified when BLOCKED. Never use `--verified all` unless every row is PASS.
6a. Until T-196 lands, the hub refuses criteria operations on an epic, so do not pass `verified` or `failed` on this epic's verdict. Write them in the verdict text instead, as two lines: `verified: C1,C3,…` and `failed: C2=note; …`.
6b. A check that needs the human or a real model harness (marked BLOCKED-likely above) is recorded as BLOCKED with its reason. It does not make the verdict not clear on its own: list it under `deferred to the T-117 walkthrough:` in the verdict text. Any other FAIL, BLOCKED or INCONCLUSIVE keeps the verdict not clear.
7. Through the hub: write it with `task.comment` (`verdict` qa, `result`, `run`, `commit`, and the verified/failed lines in the text) and `send` it to the coordinator as `qa clear T-111` or `qa not clear T-111`. Without a hub: print every `runs.jsonl` line, the case table and `verdict: qa`, `result:`, `commit:`, `run:`, `verified:`. The epic closes on a clear verdict once its children are closed (decision D16); the Coordinator closes it.
