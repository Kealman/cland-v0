# QA brief: T-274 Epic: Inbox and the events view

This brief is the Definition-of-done demo of epic T-274, which QA runs on `dev` in the human's place (decisions D16 and D19 of v0.1 §4: epics wait for no human demo). It has its own hub, `[plan] approval = "human"`, its own suite lock path, the fake OpenCode and Claude Code harnesses, five driver spokes (a Coordinator, an Implementer, an Aide, a QA and a bare Reviewer), a small UI client and one headless workbench. **Amended after run qa-2026-10-12-27 (Coordinator, 2026-10-13):** the four clarifications given during that run are now in the text: M12's remote gate accepts the scratch project's own territory as `origin`; drivers named after a role carry `-q` (`aide-q`, `qa-q`) because role names are reserved session names; M20's `archiveToday` is date-aware; M23 expects ×5 and ×4.

```sh
printf 'stages:\n  - name: Build\n    qa: { scope: none, when: after-stage }\n    lanes:\n      - - %s\n' "$K" > $D/plan.yaml
drv coord topic.create "{\"title\":\"Ask topic\",\"item\":\"$IA\"}"      # TA=<topic id>
drv coord topic.create "{\"title\":\"Review request\",\"item\":\"$IR\"}"  # TR=<topic id>
drv coord topic.create '{"title":"QA talk"}'                              # TQ=<topic id>
```

**Keep the rows in separate topics.** A human message in a topic settles every request (`replied`) and message (`answered`) waiting there. The ask lives in TA, the review request in TR, the QA message in TQ and the handover request in General. Never post as the human in a topic except where a step says so.

## Pitfalls

- Edit `lock_path`, `budget` and `[plan] approval` **before** the first `hubstart`: the hub reads them only at start. `guard` refuses a hub start without them. Seed the journal before the first start only.
- A command that prints the root's items, sessions, topics or inbox has reached the live hub, which means `noclu` was skipped or the command ran in the root. Stop, record BLOCKED for that check, and do not repeat it.
- **Never work around a hub refusal.** A refused send, forward, decline or frame is evidence: record its exact text. Do not edit a tracker or `hub.db` file by hand, or reach the same result another way.
- **One human message settles a topic's waiting rows.** Post as the human only where a step says so, and keep the rows in their own topics (see "Items and topics").
- **The last look is set by any opening of the view.** Until M22's screen is taken, never press `␣E`, `e`, Enter on the events line or the palette's Events view.
- `<Space>n` and `<Space>N` toggle: press each once to open and once to close.
- Answer the approval only through `reply.mjs`. Enter on an approval row attaches the harness, which this run never does.
- `doomed` is killed on purpose (M22). Its death is the evidence; do not relaunch it.
- Read `hub.log` or `journal.jsonl` only after the `flushLogs` barrier.
- Every launch passes `--harness`. A launch without it reaches a real OpenCode model.
- A targeted test reported as `# SKIP` is not a PASS.

## Procedure

1. Choose a run id, `qa-<date>-<n>`, and set `RUN` and `EV`.
2. Run the checks in this order, and record each with `qa-record.sh`. Captures go under `.cland/qa/T-274/<run>/` of the root.
   1. M0. If it is not PASS, stop: the run is BLOCKED.
   2. M1.
