# QA brief: E-616 The onboarding skill and the newcomer's first page

This brief is the Definition-of-done demo of epic E-616. The DoD asks for a live run: a real Aide on the favourite harness, QA playing the human in the headless workbench and answering in a language other than English, on an empty scratch project and on a clone of a small public repository. **That live run cannot be made safely by QA** (it needs the human's real harness login, spends real model calls and, for the second project, the human's `gh` login and the network; the standing rule for QA runs is scratch HOME and fake harnesses only). This brief therefore demonstrates every criterion by the closest safe substitutes and says, per criterion, which half is substituted (section "Gaps and substitutes"). The substitutes are accepted under D71 (docs/spec/v0.1.4.md): E-616 is accepted on the fake-harness replay of the Aide's acts plus a check of the skill text, recorded as a Coordinator comment on E-616; a live Aide run is the human's call after the release (section "Grants"). It has three parts.

- **Part D, the droplet.** One demo lease at the requested commit. On it: a fresh scratch project made by `cland init` at `S` holds the `onboarding` skill byte for byte (C1); the children's own test files, one at a time, which exercise the Aide's acts against an in-process hub with fake adapters (C2–C5).
- **Part L, local macOS.** QA plays the Aide's acts itself, on a scratch machine of fake harnesses under a scratch HOME (`hub/test/setup-machine.ts`): the rules, `[plan] approval`, the first release with planned tasks and criteria, the stack's `[verification]` commands and rule, the crew, the welcome note in General, the commit by explicit paths, the push, and the Coordinator's launch with `Work release R-<n>` (C2–C5).
- **Part R, records, read-only.** The skill's five files read against each criterion's wording and diffed against the accepted prototype (C1–C6); the newcomer's first page and the glossary (C7).

Everything the run needs is in this file or in the files it names: whoever runs it cannot ask.

## Pitfalls

- **Scratch only.** `cn`, `mx` and `ax` give the machine's environment and nothing of the real one. The only commands that run bare are `cl` (task, demo, verify queue) and the `node $EV/mkmachine.mjs` build. If an `ax` call prints a path under `/Users/evgeniyivanov` that is not `$W`, stop: the environment leaked.
- **Who runs a command.** `ax` carries the Aide session's identity (`onboarding-aide`, role `aide`); `cn` is the human's shell. A refusal for `ax` that `cn` would not have is a finding on the Aide's grants, recorded with its exact text and escalated to the requester, never repeated as `cn` or another identity and never worked around.
- **Short paths.** The Part L machine lives under `/tmp` because a hub socket path under macOS's default temp folder exceeds the Unix socket limit.
- **No prompts to sessions.** The fake Coordinator is launched and left idle; QA sends it nothing and attaches nowhere.
- **Counts, not command lines.** Process checks print counts; no environment or argument vector is printed (T-492).
- **One lease.** Never run `demo start` twice. Record D lines before `demo stop`.
- **Commands on the droplet** are argument vectors: `ds` passes each script as one `sh -c` argument.
- **Never work around a refusal.** A refused demo control or verdict is evidence: record its exact text.
- `qa-record.sh` takes `E-616`. The verdict goes on `E-616`.

## Procedure

1. Choose a run id, `qa-<date>-<n>`, set the Environment and write the Scripts. Announce START in the request's topic, naming `S` and that C2–C6 are judged by the substitutes. `dev` is not frozen: D14 decides.
2. Run, in order, recording each with `qa-record.sh` under `.cland/qa/E-616/<run>/` of the root:
   1. G0, G1, G2. If any is not PASS, stop: the run is BLOCKED.
   2. Part D: D0, then D1–D4 one at a time on the one lease, D14, and D15 last of Part D.
   3. Part L: L1 (its five blocks in order), then L2 (always, even after a failure).
   4. Part R: R1, R2, R3.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS. Say in the text, per criterion, whether it is verified outright (C1, C7) or **by substitute** (C2–C6), so the Coordinator can record that they are the D71-accepted basis. Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id; a D3 rerun is the flaky rule's one rerun, in the same lease, reported beside the first result.
6. Before the verdict, run D14's freshness read again if `dev` moved since D14. Publish the evidence with `artifact.create` (kind `note`: the check table; the lease, executor, commit, lifetime and cost; which checks ran where; the R1 hunk assignment; the substitutes; the findings) **in the epic's topic where the request was delivered**, and name its id in the verdict text.
7. Write one verdict on E-616 from `$W`: `cl task comment E-616 "<text>" --verdict qa --result clear --run $RUN --commit $S --verified all`. A not-clear verdict carries only `--failed C<n>=<note>` (one per failed criterion, single-line notes) and names in its text the criteria that passed. The text opens with the check table, then the findings ranked high, medium and low. If the hub refuses the verdict as `qa-stale`, keep the evidence and report BLOCKED. Any other refusal: fix its cause and write only the verdict again with the same run.
8. Release the hold if the verdict did not: `cl task hold E-616 --release`. Check L2 and D4 left no scratch folder. Remove the build worktree: `git -C $R worktree remove $W`.
9. Report with `send` kind `report` to `lead E-616` in the request's topic: first line `qa clear E-616` or `qa not clear E-616`, then the failed checks, the substituted criteria, and the lease and its cost. Report any find outside the epic as a bug found aside, with its evidence, so the Coordinator files it under Bugs.
