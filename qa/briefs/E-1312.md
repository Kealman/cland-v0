# QA brief: E-1312 — Definition of done (The Discord remote)

## Item

E-1312, Definition of done C1–C10. Its children are T-1396–T-1415, in five stages: "socket, pairing and one message", "the budget, close codes, REST pacing, the mirror and the commands", "cards and modals", "resume and history catch-up" and "attachments and voice". The request names the full dev SHA under test and the Linux droplet and macOS stage cover logs that closed the last stage. The last stage holds T-1414 (inbound media, landed) and T-1415 (outbound artifacts). If T-1415 has not landed on dev at the SHA named in the request, M11 and M13 are BLOCKED, not passed (see Probes).

The demo runs inside the sealed scratch hubs the tests build (rule 15):
- the fake Discord gateway and REST in `hub/test/fakes/discord/` (loopback only);
- the fake Bot API in `hub/test/fakes/telegram/` where a case mirrors to Telegram;
- fake speech providers (a loopback ElevenLabs stand-in);
- an isolated Chrome Headless Shell for the web checks (rule 18);
- headless Neovim for the workbench check.

Only made-up tokens and keys are used. QA never reads, prints or copies ~/.config/cland/sandbox-remote.secrets.toml. It never uses a real Discord bot, application or server, a real ElevenLabs key or a real token, and never passes a value in argv. The live run with the human on the real bot is not part of this epic.

## Build

Use a clean detached worktree at the full dev SHA named in the request, with `node_modules` and `hub/node_modules` linked from the project root (`ln -sfn`). HEAD must equal that SHA. Build `web/dist` first (`npm run build --workspace web`, or the repository's web build script) so the web checks find the bundle. Every child (T-1396–T-1415) needs a dev landing receipt (an `Item: T-n` trailer). Before the verdict, check freshness with `cland demo status E-1312 --commit <sha> --json`.

## Probes that mislead

- The live hub runs code from its last restart, and no Discord remote is enabled on it. Its behaviour is no evidence. The tests at the build are.
- A `node --test` exit 0 whose name pattern matched nothing is not a pass: confirm the named cases appear in the output. A skipped nvim case (M7) is BLOCKED.
- C2 and C10 have source checks for the parts no test asserts: the intents value (the fake gateway rejects an identify with a different value, so a wrong value shows as a hang or failure, but the number is read from source), the API version, the invite permissions and the TEXT columns. Do not report these as runtime evidence.
- C1 asserts the stop cause and its fix through the doctor row and the stop cause values; no test reads the General notice text itself. Confirm it through the source check in M1, and call it a gap if the text cannot be found.
- The identify count lives in `hub.db`, not in the log. A case that restarts the hub reads it from there; do not look for it elsewhere.
- The history catch-up cases are slow by design. Their allowances (45 s for the full-scale 620 to 500 case, 10 s for the native kill) are owned by R-1278: a run that exceeds one is reported with the measured time, not rerun until it passes.
- The earlier restart cases of `discord-messages.test.ts` once failed on the 5 s identify budget (T-1432, fixed). A new failure in a restart case is a finding.
- A voice note that answers a card answers through its transcript and keeps no audio, while a note that cannot answer goes to General as an ordinary 🎤 message with its audio. This is the human's decision 62b8d32f, not a finding.
- Each artifact goes to a remote once ever; a later message re-attaching it replies with `▣ A-n … (sent above)`. Same decision, not a finding.
- Per-file transcripts for audio albums (T-1433) and batched commits (T-1436) are follow-ups, out of scope.
- If T-1415 is not on dev at the tested SHA, `hub/test/discord-artifacts.test.ts` does not exist there: M11's second half and M13 are BLOCKED. Do not run the file from the branch.
