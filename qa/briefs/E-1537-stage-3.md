## Probes that mislead

- **Doctor's exit code is not the hosts block.** A scratch machine may fail toolchain or harness rows; warnings never change the exit code (VERIFIED in `docs/hub/cland-doctor.md`). Read the `host*` rows from `--json`, never the exit status. The doctor's toolchain probes run whatever harness binaries the sealed PATH resolves, as version and status probes under the scratch HOME (as E-1532 stage 3 ran `doctor --json` in a scratch project, VERIFIED in its brief); no row reads them.
- **`hosts` (one row) versus `host …` rows.** `hosts: no host pool` appears only without any pool; with pools there is no `hosts` row. `host logins`, `host reachability` and `host spend` without a pool name appear only with `hub not running`.
- **Free-login rows follow placed roles, not logins.** `freeLogins` lists only harnesses of roles whose launch pool is that configured pool; with no placed role there is no `logins` row at all, and `0 free` appears only after `cland role launch … --pool <pool>`. The admission `capacity` field is not a count.
- **An outage is reachable before it is `unreachable`.** Within the three-minute grace a host stays `ready` but already carries `outageSince`; doctor then reads `ready; outage since <t>` with `cland host destroy <id>`. The `stop` fix is for other non-ready states without an observed outage.
- **The control's root is the project root** (carried). Pass `$Q/p1`; `$Q/fh` links to it. A refusal naming `owned fake host root` is a setup fault, not a product failure.
- **The fake DigitalOcean API logs only authorized requests.** Its server answers 401 without logging a request whose bearer is not its own, and the hub has no token at all: `DigitalOceanApi`'s request path throws `DIGITALOCEAN_TOKEN is required` before any `fetch` (VERIFIED in `hub/src/executor/droplet/api.ts`). Zero in E1537S3-86 is therefore expected for two independent reasons; the stronger proof that doctor itself sends nothing is E1537S3-40's `presence=true` expansion, where the hub holds a working sentinel and the log still stays empty.
- **`host.providers` with and without the filter.** Unfiltered lists only configured providers (`{providers:[]}` with no pool); `provider: "digitalocean"` lists that provider even unconfigured. Neither constructs a provider.
- **`roleLogins` is opt-in.** A plain `host.status` reply never has it; the opt-in map skips roles launching on `local`, so it is `{}` until a role is placed on a nonlocal pool. An older hub without it means unknown, so setup stays `open`.
- **Setup's untouched/partial split reads only `[hosts.agents]`.** The `qa` and `do` pools do not count. With a pool and no placed role the fix lists only the placement and reload; with placed roles but no readiness it is `cland setup in a terminal`; a `digitalocean` `agents` pool without the hub token is `open` naming `DIGITALOCEAN_TOKEN` before anything else.
- **`cland setup --json` is always without a terminal**, whatever the shell (VERIFIED: `interactive = !json && …` in `hub/src/cli/setup.ts`).
- **The token sentinels are never written down.** E1537S3-90 reads them from the test sources and prints only their lengths; a brief, record or artifact that contains one is itself a finding.
- **Generated names cannot be certified by `qa lint`.** The loop titles (`C1/C6 doctor reads hub token presence=<present> without provider calls`, `C3 doctor counts actual <kind> logins only for placed harnesses`, `Discord setup checks application before enabling and pairs through native /cland pair (repair=<repair>)`) are expanded in `expect.json` and checked by `tap.mjs` against the TAP at the build.
- **A configured pool changes setup's shape (T-1831).** With an `agents` pool and a placed role, setup asks no `Set up agent hosts?`: in a terminal it prints `ok agent hosts` and goes straight to the image and login offers; without a terminal it prints `open` and the same rows `open` with their commands. `--yes` takes each offer's default No, so in a terminal the rows are `skip`, but without a terminal they stay `open` (T-1831 C5, reviewer-required): `--yes` is `skip` only for an untouched project (T-1830 C2's test). Only a current image plus eligible logins is the quiet one-row `ok`.
- **`agents: prepared` versus `agents: current`.** The image row's `done` detail is the hub receipt's state: `prepared` after a build, `current` when the hub found the key unchanged; a current local record before the offer prints `ok` `agents: current` and asks nothing.
- **A sign-in failure's fix depends on admission.** Before the hub admits a name, the fix stays `cland login add <h> --pool agents`; after admission it is `cland login signin <name>`. Neither is a pass for C2.
- **The terminal SSH of E1537S3-88 is not the hub's SSH.** The hub reaches fake hosts through `CLAND_SSH_BIN` with its own `CLAND_FAKE_HOSTS`; the CLI terminal sign-in spawns `ssh` from `PATH`. `sd.mjs` puts `$Q/bin88` first on that child's `PATH` only, with a wrapper copied from `login-add.test.ts`'s; the hub, the PRE gate and every other row still see `$Q/bin/ssh`.
