Commands are for bash (start `bash` first; zsh reads `$S:q`, `$B:h` or `${B}:hub` as modifiers; always brace a variable before `:`).

**Where it runs.** Two places, framed by gates and a freshness check:

### What the scratch hub cannot drive, and what carries it

- **OpenCode on the created host (E1533D-45): a relay stands in for sshd's TCP forwarding.** The named tests patch `Host.spawn` (to set `FAKE_OPENCODE_SOCKET`) and `freePort` in process; a CLI-started hub cannot, and no environment path exists: the hub's environment never crosses to a host (`hostCommandEnvironment` passes only explicit additions, `hub/src/host/command-environment.ts`), and the fake `ssh` builds the host agent's environment with `fixtureEnvironment(host.directory, …)`, which drops every inherited `FAKE_*` name. So the host's fake OpenCode listens on TCP `127.0.0.1:<port>` as real OpenCode does, while the fake `ssh` forwards a host loopback port only to a Unix path named in `<host directory>/ports.json`. Stage 3's kit mapped every port to `session.sock`, where nothing listened (E1533S3-56: `opencode serve did not answer within 30000 ms`). This brief maps every port `p` to `relay/<p>.sock` and runs `relay.mjs` beside the host: for each port the fake OpenCode records in its `serve-ports.jsonl`, it listens on `<home>/relay/<p>.sock` and pipes each connection to `127.0.0.1:<p>`. That is sshd's direct-tcpip, which the fake `ssh` lacks; no hub code is patched. **Validated by a scratch trial at `093f851b`** (2026-11-07, on the stage-3 kit): `host create agents` ready, the launch answered `ok:true`, the relay served the chosen port, `srow oc` read `status=running` on the host, then `host destroy` gave `status=exited`, two `host-destroy` reads and the row `destroyed`. If the launch still fails, E1533D-45 is BLOCKED (not FAIL) with the reply text, E1533D-46's session line reads `no row`, and "runs a session" rests on E1533D-17.
- **The fake DigitalOcean API.** It lives inside the named test files (scripted machine, FakeClock, synthetic credential). The DoD's 429, split-DELETE and tag-reap sentences are those files' tests (E1533D-12); no scratch row talks to it.

## Probes that mislead

- **Generated names cannot be certified by `qa lint`.** Contract registrations (`fake: …`, `digitalocean: …`) and loop titles (`<arch> base …`, `pool prepare invalidates <part> …`, `digitalocean <status> pauses …`, `429 carries retry time … (<mode>)`, `project provision runs as root before runner prepare, failure=<bool>`, `destroy requires confirming reads: <outcome>`, `C1/C2/C3 destroy settles native session …; tunnel down=<bool>`) are expanded in `expect.json` and checked by `tap.mjs` at the run.
- **The fake DigitalOcean API is the only DigitalOcean here.** Its loopback listener and synthetic credential live inside the named files. A real DigitalOcean variable on either side is a BLOCKED gate (S0, E1533D-03); no row creates, lists or deletes a real droplet, key, volume or image. The demo droplet is the hub's lease, not a DigitalOcean provider operation.
- **`cland demo exec` has no stdin** and returns output when the command ends, capped at 8 MiB: the probes travel as single argument strings and the named files run one per exec.
- **A refused create naming E-1534 is the pass** (E1533D-47, E1533D-16). A refusal naming `cland host prepare` for a `digitalocean` pool would mean the admission order regressed.
- **Destroyed hosts stay listed** with `state` `destroyed`; their confirming reads are hub-log events, not CLI output (E1533D-46).
- **The relay is a probe, not product.** It stands in for sshd's direct-tcpip, which the fake `ssh` lacks; the fake OpenCode listens on host loopback TCP exactly as real OpenCode does on a real host. A launch that works only because of the relay proves the hub's launch, forward and readiness path, not the fake transport.
- **The created host is a fake machine**: a directory, local processes, and a `gone` marker on release. Nothing about a real droplet's boot time follows; the DoD's 60 to 90 seconds are not a criterion.
- **C2's `idle_stop` and `host status` are E-1534's** (see "Item"); this run proves the provider deadline and the declared price, and the verdict says so.
- **The snapshot key, not a rebuild, proves "the new snapshot"** (E1533D-30): a key whose `provision` digest equals the hook at `S` and whose `recipe` digest equals `provision.sh` at `S`, used by a green droplet run at `S`'s tree. Successful prepare and reuse lines are in the run's `delivery.log`, not the suite log.
- **Plain `node --test` is not the suite runner.** It enforces no duration allowance and no resource tripwire preload: a slow pass is not a finding and a fast one proves no budget.
- Process cleanup probes use the fixture-owned pid census (`$Q/pids`) and the scratch-root census; a machine-wide `pgrep` counts other sessions too.
- File-change probes use isolation; mtime alone is confounded by live sessions rewriting the same file.
- Speed criteria use measured wall times, never projections; this epic's criteria have none.
- Slots due or queued before the build count even when their results arrive later.
- "No skip" names platform-only cases: on Linux the named files of this brief skip nothing at writing; `executor-droplet`'s macOS idle-sleep case is not run here.
- Re-check helper and function names with grep at the tested build; renames happen. The kits are pinned by blob; a different blob is a setup BLOCKED.
