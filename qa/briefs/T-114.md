# QA brief: T-114 Epic: The epic plan

This brief is the Definition-of-done demo of epic T-114, run by QA on `dev` in the human's place (decision D16: epics wait for no human demo). It checks the epic as a whole through the `cland` CLI against a scratch hub that launches only the fake Claude Code, one headless workbench on that hub, and the committed targeted tests as corroboration. Everything the run needs is in this file or in the files it names.

## Item

T-114: every epic is worked from a plan, ordered stages of parallel lanes with a QA policy per stage, kept as a validated YAML block under `## Plan` in the epic's file, drafted by the `plan-epic` skill, approved per `[plan] approval`, read by the merge gate, and shown in the plan view (`gp`). The demo is the narrative under `## Definition of done` (`task view T-114`). The epic's parent is the release T-130 (confirm it is `kind: release`). Its children T-183, T-184, T-185, T-186, T-187 and T-188 must all be closed before the run. T-114 lists T-113 under `blocked_by`; record T-113's state in M0 (it is not a reason to block this run, but name it in the verdict if it is still open).

Criterion ids: the eight checkboxes under `## Definition of done` have no ids in the file (`- [ ] The hub parses…`), so `task view T-114 --json` may show `id: null`. That is expected and not a finding. Legacy criteria receive stable ids positionally on first touch (`docs/review-and-qa.md`, "Criteria in a verdict"): the first criterion operation, including the structured verdict's `--verified`, stamps them C1..C8 in list order, first checkbox C1. This brief maps them by position:

- C1: the hub parses and validates `## Plan`; a broken plan is refused and the previous one stays; `task.plan` and `cland task plan` set, show and approve.
- C2: the gate takes each item's QA policy from its plan or `[plan] qa_default`; `qa-required` is retired; `ready` agrees with the gate.
- C3: after-stage QA: the stage's items merge on review, one QA verdict on the stage closes it, and a not-clear stage verdict keeps it open.
- C4: criteria the plan marks for QA need a QA verification before the merge.
- C5: `plan-epic` writes a valid plan; `approval = "human"` holds the epic's launches until the human or an Aide approves.
- C6: `gp` opens the plan view before the start and mid-way as §3.13 describes; the items panel shows the stage tags.
- C7: a plan change is journalled, leaves merged items alone, and stays marked for the human until they open the view.
- C8: `docs/review-and-qa.md`, the `merge` and `qa` skills, the role clauses and `nvim/README.md` describe the plan and its view.

After the verdict, read `task view T-114` again and confirm the stamped ids sit on the checkbox text above. If ids are already shown and their order differs, map by the checkbox text and say so in the verdict.

## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Build the scratch project, the tree and the sessions, start the workbench, then run every check in order and record each with `qa-record.sh`. At the end stop the scratch workbench (`:qa!` through the driver, or kill its pid), the scratch hub (`c hub stop`, never without the wrapper) and any fake left (`PATH="$FAKE:$PATH" FAKE_CLAUDE_HOME=/tmp/qa-T-114-fake claude stop` for each), then remove `/tmp/qa-T-114*` after the captures are under `.cland/qa/T-114/<run>/`.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. Verdict `clear` only when every check in scope is PASS (the deferred list excepted); otherwise `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written, finish from there and never rerun a check under the same run id (the skill, "When a step fails").
6. Criteria by position (see "Criterion ids"); verify exactly the ids whose checks are all PASS: C1 = M2, M3, M4, M5 (M11, M15, M17 corroborate approve; M19 task-plan); C2 = M6, M7, M18 (T-6 half); C3 = M12, M13; C4 = M18 (T-7 half); C5 = M1, M5, M8, M11, M17; C6 = M9, M10, M14, M16; C7 = M15, M16; C8 = M20. M0 gates the run; M19 corroborates C1..C7 and a failure there fails the criterion its file covers. A failed check puts its criterion under `--failed "Cn=note"` (one nonempty line, repeated per criterion); a BLOCKED or INCONCLUSIVE one leaves it unverified. Never use `--verified all` unless every row is PASS.
6a. Write the verdict from the root, in QA's own identity (the real QA session; this is the one root write), with the structured flags: `node hub/bin/cland.ts task comment T-114 "<text>" --verdict qa --result clear --run <run> --commit <full root dev SHA> --verified C1,C2,…` (or `--verified all`), and `--failed "C2=note"` for a `not clear` verdict (`docs/review-and-qa.md`, "Criteria in a verdict" and "Epic closure by QA (D16)"). MCP `task.comment` takes `verified: "C1,C3" | "all"` or `failed: [{ criterion: "C2", note: "…" }]`. A verdict whose criteria sit only in the text does not satisfy the epic close gate. The `commit` must equal the root's `git rev-parse dev` at the time of writing, or the gate refuses it as stale.
6b. Checks that need a human or a real model are BLOCKED, listed as "deferred to v0.1.1", and do not by themselves fail the verdict (D19). A Definition-of-done criterion left unverified keeps the epic open; the Coordinator decides then (an `--override` in the human shell, not QA).
7. Through the hub: write it with `task.comment` (`verdict` qa, `result`, `run`, `commit`, and structured verified/failed fields) and `send` it to the coordinator as `qa clear T-114` or `qa not clear T-114`. Without a hub: print every `runs.jsonl` line, the check table and `verdict: qa`, `result:`, `commit:`, `run:`, `verified:`. The epic closes on a clear verdict once its children are closed (decision D16); the Coordinator closes it.
