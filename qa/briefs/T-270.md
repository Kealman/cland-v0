# QA brief: T-270 Status, fields and instrumentation

This brief is the Definition-of-done demo of epic T-270. QA runs it on `dev` in the human's place (decisions D16 and D19 of v0.1 §4: epics wait for no human demo). It has two parts.

- **Part A, a scratch project with its own hub, running `dev`'s code.** Every write the DoD asks for happens here: the two-stage plan and its `planned` moves, the landings through `cland merge`, the epic's close, the size and `regression_of` refusals and fields, the review scope with and without `--scope`, three fake harness sessions launched without a model, and their usage records read back from `cland hub journal --json`. One driver spoke, one reviewer spoke, one UI client and one headless workbench at release scope.
- **Part B, the live tracker, read-only.** Root reads of `cland task list --under T-228 --json` and the plans of closed epics, then a headless workbench on a mirror root attached to the live hub as a UI client, reading the release scope of R-228. Part B writes nothing to the live tracker, the live hub or the live `ui.json`.

The children's hub and Neovim tests corroborate, **one file at a time**. No harness session is launched anywhere except the three fake ones inside the scratch hub. Everything the run needs is in this file or in the files it names.

Decisions taken during the build change how the DoD reads. Apply them; they are not findings (the Coordinator's 12 decisions on E-270, 2026-10-13 14:04Z, its stand-in adjustment and D24):

- **The size is refused at the request layer** (decision 1). `cland task create` and MCP `task.create` refuse a task without one. `cland task import-github` and hub-internal creates stay sizeless, and existing unsized files stay readable.
- **The demo's `--regression-of` names a landed task** (decision 2), not the open T-254. In the scratch project it names a task landed there by `cland merge`.
- **Clause bytes** (decision 3). The Coordinator's clause sits just under its 512-byte headroom; T-331 and T-332 cut what they added. M7 runs the guard; QA judges no clause wording beyond the rules named in M7 and M14.
- **`planned` moves each task once per stage entry, recorded in `tracker_meta`** (decision 4). Nothing moves until a plan is approved. The scratch project keeps the default `[plan] approval = "none"`, so a set plan is accepted at once; pending approval is covered by M2.
- **A closed epic's stages read as closed, and nothing is written** (decision 5).
- **The closing-time backfill** takes the receipt's `merged_at`, then the journal, then the receipt commit's git time (decision 6). Items with no source stay unresolved.
- **`verified` counts only marks current at the branch tip** (decision 7), beside `stale` and `failed`. A landed task uses its receipt's tip.
- **The tracker reads the verify jobs through a function the dispatcher passes at startup** (decision 8). Existing wiring, not a seam; not judged.
- **The layer views stay as they are** (decision 9). Only the `board`, `work` and `done` filters narrow to the release; `gn`, `gw`, `gb`, `gA` list layers across every container.
- **Sub-agent models are recorded where a harness gives a signal** (decision 10). Claude Code's `SubagentStart` without a model journals `"unknown"`.
- **Usage is charged to the session's launch item** (decision 11), not to a later claim or hold.
- **Role sessions relaunch after T-331 and T-332** (decision 12). The live hub at the time of the run may predate T-332 (its restart may be pending). So every write check runs in the scratch project, whose hub runs `dev`'s code, and the root is only read.
- **The live backfills already ran** (stand-in adjustment). The closed and size backfills ran on the live tracker at b4a7018 (2026-10-13): 269 closing times, and size `M` for T-332 and T-340. 39 early closed items have no closing-time source (M-1, Q-2 to Q-5, T-6, Q-7 to Q-18, T-21 to T-41) and 15 open tasks were unsized then. A task with no `closed` because it predates the journal, or a task with no size, is **not** a finding. The check is that the fields are present where a source exists.
- **No verification is submitted in this run.** `verify` is judged on the live tracker, where the children's own `cland verify` jobs are, and by M5's hub tests. In the scratch project every task carries `verify: null`.
- **The scratch epic is closed with the human's `--override`**, because its demo epic has no QA run. The override is the human shell's documented path (`cland task close <id> --override <reason>`), and it journals `epic-close-overridden`.
- **The verdict's scope is read back from the journal as event text.** The scope lives in the verdict header and the index. The journal carries it in the `event-announced` record whose text reads `<id> verdict posted review clear · <scope> · <run>`.
- **Root `task view` in text mode can crash against an older hub** (T-339). Every root read uses `--json`.

## Pitfalls

- **Never launch a session in the root, and never one in the scratch project before `gates` prints the three fake versions.** These launches carry no `--model`; a real harness would pick a real model.
- A command that prints the root's items, sessions or topics from a scratch helper reached the live hub: `noclu` was skipped or the cwd was wrong. Stop, record BLOCKED for that check, and do not repeat it.
- **Use the printed ids.** M16's creates normally print `R-1` to `T-14`; the refusals before them consume no number. If they differ, carry the printed ids through every later check and say so; that is not a finding.
- **Keep the item set as M16 builds it.** M25's exact count line assumes one open category with one open item and two loose tasks. Every later create (`TQ`, `TR`) has a parent.
- **Never work around a refusal.** A refused create, edit, link, comment, close or launch is evidence: record its exact text. Never edit an item file, `hub.db` or `ui.json` by hand. The epic's `--override` (M20) is the human's own documented path, not a workaround.
- `TA1`'s review carries `verified: "all"`: the merge gate refuses a task with unverified criteria. `TA2` has no criteria, so its review carries none.
- `c task claim` is the human's claim; its worktree lives under `$P/.cland/worktrees/`. Commit only there, never in `$P`'s own checkout.
- Stop the three fake sessions (M24) before the workbench starts (M25).
- The fake sessions' `pong` replies raise the human inbox and the needs-you chip in the scratch workbench. Expected.
- **Part B presses only the listed keys.** In the items panel never press `K`, `J` or `T` (rank writes), `e` or `E` (scope), or `d`. Press Enter only on the count line. Never focus the composer, never press Enter in the sessions panel or `gs`, and never type into a thread. `:qa!` ends the workbench.
- **One workbench at a time.** Part A's workbench and drivers stop before `nvlive`.
- `<Space>i` toggles the items panel. Filters are `1` board, `2` work, `3` needs you, `4` done, `5` map, `6` all. `zR` opens every fold, the categories' included (T-269 amendment 4).
- `qa-record.sh` takes `T-270`, never `E-270`.
- Read `hub.log` or `journal.jsonl` of a running scratch hub only after the `flushLogs` barrier (`jr`).
- Root reads use `--json` (T-339).

4. The verdict is `clear` only when every check in scope is PASS. Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id (the skill, "When a step fails").

   - **C1** = M2, M17, M18
