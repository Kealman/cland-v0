# QA brief: T-113 Epic: Leads and the crew

This brief is the Definition-of-done demo of epic T-113, run by QA on `dev` in the human's place (decision D16: epics wait for no human demo). It checks the epic as a whole through the `cland` CLI, a scratch hub that launches the fake Claude Code, the committed protocol tests for the spoke-only tools, and a headless workbench for the crew summary. ## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Build the scratch tree and sessions, then run every check in order, and record each with `qa-record.sh`. Stop the scratch hub and the fake sessions at the end (`cland hub stop`, `claude stop` for any left in `FAKE_CLAUDE_HOME`) and remove `/tmp/qa-T-113*`.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. Verdict `clear` only when every case and check in scope is PASS (the deferred list excepted); otherwise `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written, finish from there and never rerun a case under the same run id (the skill, "When a step fails").
6. Criteria: the ids are C1, C2, … in the order of the checkboxes under `## Definition of done` (check with `task view T-113`; if the ids differ from the order below, map by the checkbox text and say so). Verify with `--verified` exactly the ids whose checks are all PASS, as the "Proves" column says: C1 = M1, M2, M3, M4; C2 = M5, M6 (M23 corroborates); C3 = M12, M13; C4 = M7, M8, M9; C5 = M10, M11; C6 = M14, M15, M16; C7 = M19, M20, M21; C8 = M17, M18; C9 = M22. M0 gates the whole run. A failed check puts its criterion under `--failed "Cn=note"` (one nonempty line, repeated per criterion); a BLOCKED or INCONCLUSIVE one leaves it unverified. Never use `--verified all` unless every row is PASS.
6a. Write the verdict with the structured flags: `task comment T-113 "<text>" --verdict qa --result clear --run <run> --commit <full dev SHA> --verified C1,C2,…` (or `--verified all`), and `--failed "C2=note"` for a `not clear` verdict (`docs/review-and-qa.md`, "Criteria in a verdict"). MCP `task.comment` takes `verified: "C1,C3" | "all"` or `failed: [{ criterion: "C2", note: "…" }]`. A verdict whose criteria sit only in the text does not satisfy the epic close gate. The `commit` must equal `git rev-parse dev` at the time of writing, or the gate refuses it as stale.
6b. Checks that need a human or a real model are BLOCKED, listed as "deferred to v0.1.1", and do not by themselves fail the verdict (D19). A Definition-of-done criterion left unverified keeps the epic open; the Coordinator decides then (an `--override` in the human shell, not QA).
7. Through the hub: write it with `task.comment` (`verdict` qa, `result`, `run`, `commit`, and structured verified/failed fields) and `send` it to the coordinator as `qa clear T-113` or `qa not clear T-113`. Without a hub: print every `runs.jsonl` line, the case table and `verdict: qa`, `result:`, `commit:`, `run:`, `verified:`. The epic closes on a clear verdict once its children are closed (decision D16); the Coordinator closes it.
