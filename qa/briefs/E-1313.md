# QA brief: E-1313 — Definition of done (Setup, doctor, onboarding and the workbenches)

## Item

E-1313, Definition of done C1–C9. Its children are T-1361–T-1372, in four stages: "doctor, Remotes row, pairing rows and Telegram setup" (T-1361–T-1366), "tour and documentation" (T-1367, T-1368), "speech key and Telegram marks" (T-1369, T-1370) and "Discord" (T-1371, T-1372). The request names the full dev SHA under test and the Linux droplet and macOS stage cover logs that closed the last stage. The last stage holds T-1371 (setup's Discord step, landed) and T-1372 (Discord's stopped causes reach doctor, the Discord workbench rows and the doctor guide). If T-1372 has not landed on dev at the SHA named in the request, the cases marked (T-1372) in M5, M7, M9 and M13, and M15, are BLOCKED, not passed (see Probes).

The demo runs inside the sealed scratch hubs and fixtures the tests build (rule 15):
- the fake Telegram Bot API in `hub/test/fakes/telegram/` and the fake Discord gateway and REST in `hub/test/fakes/discord/` (loopback only);
- fake speech providers (a loopback ElevenLabs stand-in);
- scripted prompters and sealed scratch machines for setup (`fixtureEnvironment`, no real HOME);
- an isolated Chrome Headless Shell for the web checks (rule 18);
- headless Neovim for the workbench checks.

Only made-up tokens and keys are used. QA never reads, prints or copies ~/.config/cland/sandbox-remote.secrets.toml. It never uses a real Telegram or Discord bot, application or server, a real ElevenLabs key or a real token, and never passes a value in argv. The live run with the human on the real bots is not part of this epic.

## Probes that mislead

- The live hub runs code from its last restart, and its remotes are not the fakes. Its behaviour is no evidence. The tests at the build are.
- A `node --test` exit 0 whose name pattern matched nothing is not a pass. A skipped Neovim case (M8, M9, M10, M11) is BLOCKED.
- C4's "no platform or paid call" is shown by tests that assert no fake-API request: the unchanged request list of the fake Bot API (M5, Telegram), the unchanged request list of the fake Discord (M5, T-1372), zero TCP connections and no `fetch`, and the fake speech provider's empty request list. The absence of errors in doctor's output is not that evidence. The source check in M14 supports it but does not replace it.
- C4's Discord token row (presence and fingerprint) has no runtime assertion: "doctor reports ${source} token fingerprint ..." uses a Telegram token only, and the Discord rows asserted are enabled, connection, pairing and the stop. Treat the Discord token row as a source check (M14) and call it that. If the row text cannot be found in the source, it is a gap.
- C5's red "at once" and recovery are asserted on the Telegram row on dev and on the Discord row only by the (T-1372) cases (M7, M9). With T-1372 not landed, the Discord half of C5 and of C7's voice mark is BLOCKED, not passed from the Telegram cases.
- C6's "the web's row points to the terminal or Neovim without an approve action" is asserted by a count of buttons and by the absence of mutation frames, not by the wording alone. The Neovim approval needs Neovim (M8): a skip is BLOCKED.
- The three web pairing allowances (the cases of `web/test/pairing.test.ts`) are owned by R-1278: a run that exceeds one is reported with the measured time, not rerun until it passes.
- C1 asserts guidance through printed text (`@BotFather`, `/newbot`, Install Link and the Discord application field names), the hidden prompt through the scripted prompter's `secret` question and `setup-prompter.test.ts`, and the speech data-use line through its position before the hidden question. No test drives a real terminal's echo; "no echo" rests on the prompter file. A real human read of the wording is out of scope.
- C2's "a second run reports `ok`" is asserted for Telegram through the `--json` rerun in M2, for Discord through the `again` run in the `(repair=...)` cases and for speech in M1. The scenario in M4 re-offers declined remotes (`skip`); it does not assert `ok`.
- The tour's commands "match the build" through `commandProblems`, which compares them with the generated usage, config keys and secret names. A tour sentence that names a command without backticks is not checked: the manual read in M12 covers it.
- T-1438 (sealed fixtures fail closed to real remote endpoints) and T-1439 (the Discord test clock) are separate 0.3 bug items. A failure in a fixture or a clock that matches either item is reported with its identity, not rerun until it passes, and does not change a criterion's verdict by itself. The resumable-stop old-copy wait is T-1439's; the sealed-fixture endpoint guard is T-1438's.
- T-1372's workbench cases use `hub/test/discord-workbench-fixture.ts` (new in T-1372). If the file is missing at the tested build, T-1372 has not landed: BLOCKED, do not run it from the branch.
- The Discord application checks of C3 are asserted against the fake application (`bot_public`, `flags`, `interactions_endpoint_url`). The fake validates the values setup reads; whether the real developer portal shows the same fields is not tested here.
- Ambient `CLAND_*` variables or a real `~/.cland` state must not leak into setup cases: the cases use `fixtureEnvironment` and a scratch HOME. If a case reads a real HOME, it is a finding.
