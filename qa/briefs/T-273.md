# QA brief: T-273 Release v0.1.2 from the item

This brief is the Definition-of-done demo of epic E-273, up to the dry run. QA runs it on `dev` in the human's place (D16 and D19 of v0.1 §4: epics wait for no human demo). The epic closes on QA's clear verdict. After that the Coordinator releases from its own shell (the `release` skill). QA's post-release check of the tag is a **separate request on R-228** (Appendix P1). It is not part of this verdict. The brief has four parts:

- **Part A, root reads and targeted tests.** The two children's test files, **one file at a time**, plus doc greps. Nothing is written in the root.
- **Part B, scratch project `P` (T-254).** Its own hub, its own suite lock and a tiny package whose "suite" QA controls with flag files. It runs green → cancelled → request (a cache hit naming the green run), three ways, and green → failed → request (a fresh run).
- **Part C, scratch project `P2` (T-253).** Its own hub, run in the foreground with the tracker write gate. A tracker write is held past its deadline while the hub serves. The hub exits non-zero naming the operation and the item, no later mutation reaches disk, and the README's restart path brings it back.
- **Part D, the release tree, read-only.** R-228's open descendants, the other epics' closing QA verdicts, R-228's `## Notes`, the Coordinator's dry run (plus a scratch reproduction of its notes), and the Coordinator's macOS release cover log.

**Safety in one line.** No scratch command reaches the live hub, the live tracker or `/tmp/cland-suite.lock*`. QA never runs `cland release`, `merge`, `push`, `sync`, `verify` or `npm test` in the root. Everything the run needs is in this file or in the files it names.

## Pitfalls

- **Never run `cland release` in the root, not even `--dry-run`.** QA's role is refused (`hub/src/hub/dispatch.ts`: release belongs to the human or the Coordinator from its own shell). A dry run also takes the territory lock, fetches GitHub and journals `release-preview`. Running it with `noclu` would impersonate the human; that is routing around a refusal. The root dry run is the Coordinator's. QA reads it (M14b) and reproduces the notes in scratch (M14d).
- A scratch command that prints the root's items, sessions or topics reached the live hub: stop, record BLOCKED for that check, and do not repeat it.
- **Order matters in Part B.** M5–M8 build on each other (G1 is the green evidence until M8 replaces it with G2). Never rerun an earlier check under the same run id. If a step's state does not land, record INCONCLUSIVE, not FAIL.
- Every cancelled or failed attempt in M5–M8 uses `--fresh`, because without it the request would be a cache hit and never become an attempt. Every probe after it uses no `--fresh`.
- `mkdir $LK` / `rmdir $LK` act only on the **scratch** lock. Check `echo $LK` first.
- In Part C, the CLI calls queued behind the held write may hang until the hub exits. Read their outputs only after `serve.exit` exists. If the hub never exits within 60 s, record M10 FAIL, then `kill <hub pid>` (scratch only), touch `$G/release`, and record M11 and M12 as far as they go.
- Never hand-edit an item file, `hub.db` or `ui.json`, in scratch or live.
- `qa-record.sh` takes `T-273` (and `T-228` in P1), never `E-273`/`R-228`. Root reads use `--json`.

4. `clear` only when every check is PASS; otherwise `not clear`, naming each FAIL, BLOCKED or INCONCLUSIVE check.
5. If a step fails, keep what is written and finish from there; never rerun a check under the same run id.
