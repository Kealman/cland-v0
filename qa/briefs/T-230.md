This brief is the Definition-of-done demo of epic T-230, which QA runs on `dev` in the human's place (decision D16: epics wait for no human demo). The scheduler, the cache, the queue view and cancellation are exercised live in **one scratch project**. It has its own hub, its own compatibility lock path, Coordinator and Implementer driver spokes, one fake Claude Code session and one headless workbench. Sharding, the two load-sensitive tests and the compile cache are checked by the manifest lint, targeted test runs and read-only evidence. Everything the run needs is in this file or in the files it names.

## Machine-wide lock: what keeps the scratch run off it

The live crew's full suites hold `/tmp/cland-suite.lock` and `/tmp/cland-suite-nvim.lock`, with their `.owner`, `.queue/`, `.runs/`, `.machine` and `.reaper` siblings. A scratch run must never create, wait on, sweep or take over any of them. The code supports this:

- **The scratch hub uses its own lock.** The hub reads `[verification] lock_path` from `.cland/config.toml` **at start** (`hub/src/init/config.ts`; the path must be absolute). It passes `[lock_path, lock_path + "-nvim"]` to the scheduler and to every worker (`hub/src/hub/daemon.ts`). Every probe, ticket, recovery record and stale sweep is keyed by those paths (`hub/src/suite-lock.ts`). The protocol tests do exactly this (`hub/test/suite.test.ts` `fixture`: `lock_path = <root>/suite.lock`).
- **The default is the machine lock.** A scratch hub started before `lock_path` is edited would inspect the live lock. Its stale-owner recovery could also remove a lock it judges dead (`inspectLocks`). Edit the config before the first `hubstart`, and prove the hub read it (M3) before the first submission.
- **The worker never runs cland's runner.** The scratch package's `test` script is a tiny `suite.mjs`, so a worker never calls `hub/test/run-suite.ts` with its defaults.
- **The hand run names its locks.** It calls `runSuite(…, { lockDirs: [$LK, $LK-nvim] })` explicitly. Without `lockDirs`, `runSuite` defaults to `/tmp/cland-suite.lock`, so `hand.mjs` refuses any path outside the scratch lock directory.
- **Nothing borrows the QA shell's lease.** `noclu` strips `CLAND_SUITE_LEASE`, `CLAND_SUITE_SELECTION` and `CLAND_TEST_SKIP_LOCK` along with every other `CLAND_*` variable.
- **Targeted tests use private locks, with one exception.** The test files use private temp roots and lock paths. The exception is `hub/test/suite-runner.test.ts`, "package shard lint refuses a free test with …" (3 cases). It calls `runPackageSuite('all', [], { cwd })` **without lock paths** and expects the lint to reject before any lock is taken. If the lint regressed, it would queue on the live lock. Run those three cases only with `CLAND_TEST_SKIP_LOCK=1` (M16b), and the rest of the file without them.
- **Shared and harmless:** worker temp roots `/private/tmp/cland-suite-<random token>` (unique per run), and the termination registry `/tmp/cland-termination-<uid>` that `session stop` uses.

M1 and M21 snapshot the live lock read-only (`ls` and `cat`, never `rm`, `mkdir` or `touch`). If any scratch output names `/tmp/cland-suite.lock` or `/tmp/cland-suite-nvim.lock`:

1. Stop all scratch work.
2. Record BLOCKED for that check.
3. Tell the requester.

## Pitfalls

- Edit `lock_path` and `budget` **before** the first `hubstart`: the hub reads `[verification]` only at start. `guard` refuses a hub start without them. Never start a scratch hub with the default config.
- A command that prints the root's items, sessions or suites has reached the live hub, which means `noclu` was skipped. Stop, record BLOCKED for that check, and do not repeat it.
- Each session identity can have one active request. A second submission from a session that already has one queued or running is refused with `this session already has a suite queued or running`. Wait for the result before submitting again.
- After M7, every request at a tree that is already green is a cache hit. A hit completes without entering the queue, even while a lock is held. Use `--fresh` wherever a check needs a real run or a queued request.
- Untracked files outside `.cland/tasks` make the tree dirty. A dirty request bypasses the cache and cannot seed it. Keep the flag files in `.gitignore`, and check `git status --porcelain` before M7.
- `release.flag` lets every run finish at once. Remove it before any check that needs a holder that stays running.
- `<Space>s` toggles the sessions panel: press it once.
- A targeted test reported as `# SKIP` is not a PASS.

## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Run the checks in this order, and record each with `qa-record.sh`. Captures go under `.cland/qa/T-230/<run>/` of the root.
   1. M0. If it is not PASS, stop: the run is BLOCKED.
   2. M1.
   3. The root test checks M2, M9, M12, M14, M16, M17 and M18. Run one file at a time, never two at once.
   4. The scratch checks M3–M8, M10, M11, M13 and M15.
   5. M19, M20 and M21.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS. Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id (the skill, "When a step fails").
6. Criteria by position:
   - **C1** = M2, M3, M4, M5, M6
   - **C2** = M2, M7, M8, M9
   - **C3** = M2, M5, M10, M11, M12
   - **C4** = M2, M13
   - **C5** = M14, M15, M16, M17, M18
   - **C6** = M19

   M0, M1, M20 and M21 gate the run. A safety failure (scratch output naming the machine lock) leaves every criterion it touched unverified. M2 counts toward a criterion only through the tests its row maps there. Verify exactly the ids whose checks are all PASS. A failed check puts its criterion under `--failed "Cn=note"` (one nonempty line). A BLOCKED or INCONCLUSIVE check leaves its criterion unverified.
7. Write the verdict from the root in QA's own identity. This is the real QA session, and the verdict is the one root write. Use `node hub/bin/cland.ts task comment T-230 "<text>" --verdict qa --result clear --run <run> --commit <full root dev SHA> --verified C1,C2,C3,C4,C5,C6`, or `--failed "C5=note"` with `--result "not clear"`. The text opens with the check table, then the findings ranked high, medium and low. `commit` must equal `git rev-parse dev` at the time of writing.
8. Report the result:
   - Through the hub: `send` kind `report` to the requester in the request's topic, `qa clear T-230` or `qa not clear T-230`.
