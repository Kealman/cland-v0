# QA brief: E-613 Setup: the guided step ending in the workbench

This brief is the Definition-of-done demo of epic E-613. QA runs it in the human's place, at a named `dev` commit, partly on a droplet through the demo lease (decisions D16 and D19 of v0.1 §4) and mainly on this Mac, where the DoD asks for it. It has three parts.

- **Part D, the droplet.** One demo lease at the requested commit. On it: the setup scenario (`hub/test/scenarios/setup.test.ts`, a scratch machine with fake harnesses driven through a real pseudo-terminal), the children's own rule-level test files one at a time, the doctor test files, and the Neovim side of "the Aide in the centre" (`nvim/test/launcher-component.test.ts`, a headless Neovim against a stub hub) (C1–C7).
- **Part L, local macOS.** QA plays the human in a terminal of its own. Five scratch machines are built from the repository's own setup fixtures (`hub/test/setup-machine.ts`): fake harnesses on a scratch PATH, a scratch HOME, no real account. On them: the report without a terminal (C1, C6), a full interactive run with its answers and every file it writes (C1–C5), the second run (C1), the remembered decline and `--install` (C2), the accounts question answered Yes (C3), the flags (C6), the doctor's strictness (C7). Then one `--no-aide` run with this Mac's real harness binaries under a scratch HOME and scratch profile folders, every login and install question answered No, no hub and no Aide, so no onboarding brief reaches a real harness (C4). The scenario file runs once more on this Mac (BSD `script`).
- **Part R, records, read-only.** The children's closure and merge commits (G1).

Everything the run needs is in this file or in the files it names: whoever runs it cannot ask.

## Changes since the last run

- Commands: `"$S:qa/..."` is now `"${S}:qa/..."` (zsh reads `$S:q` as a modifier); the brief tells QA to run its blocks with bash.

- `dt` keeps each test file's complete output locally (`$EV/<id>.log`, never overwritten, copied before the next test and before the lease stops) and its exit code (`$EV/<id>.exit`); the `ℹ` summary lines are no longer relied on (Node may emit TAP when piped). D2-D5 and L9 are judged by the exit code.
- Build: same-SHA prerequisite and the INT_LOG_LINUX / INT_LOG_MAC statement (QA submits no verify).
- Local fallback: if `demo start` is refused for slot or budget the refusal text is recorded and D1-D5 run locally and are judged normally.
- Scratch contract: the builder's fixture-owned roots /private/tmp/cland-init-machine-* and /tmp/cland-setup-* (outside Q) are explicitly allowed and recorded.
- D1: Neovim is resolved with `node nvim/bin/nvim-path.ts` and its `--version` is compared with `nvim/NVIM_VERSION`, not `command -v nvim`.
- L1 (machine M1) expectations: M1's roles template is Claude-only, so the unused missing Codex is `skip` (not `open`), there is no Codex login row before Codex is installed, and the report has ten step rows (not eleven or twelve). Substitute 2 now names L8 (it named L6).
- L4/L5/L6: the machines are built with `--decline opencode` (as the repository scenario does) so the interactive drivers meet no unanswered OpenCode install question.
- L10: `ALL` is a bash array (`for m in "${ALL[@]}"`): zsh does not word-split `$ALL`.
- L8/L10 cleanup: the paths are printed and inspected first, `rm -r` is non-force and guarded by a pattern check and `[ -d ]`; the literal `/tmp/qa-e613` is removed by name. If the harness blocks a computed `rm` target, print the recorded path and run `rm -r` on that literal path.
- L8 runs `cland setup --no-aide`: real setup without it would auto-send the onboarding brief to a real harness session (hub/src/setup/steps/aide.ts), which breaks the no-real-prompt rule; the session and launcher expectations are revised, trust (C4) stays covered.

**Criteria.** Judge each by its text in `task view E-613 --json` at START. At writing:

- C1. `cland setup` runs its eight steps in order, one line each, and a second run reports `ok` for every step already done.
- C2. A missing harness is installed on yes and detected again, a declined install is remembered until `--install`, and every harness a template role uses is checked for a login and signed in on yes.
- C3. The accounts step appends to `~/.config/cland/accounts.toml` only on a yes, the default No, and the favourite harness lands in `[aide.launch]`.
- C4. Trust is granted for every installed harness without a question and reported in one line, for the fake harnesses and for this Mac's real ones.
- C5. Setup starts the hub, launches `aide-1` with the onboarding brief and opens the workbench with the Aide in the centre, `--attach` runs the harness's attach instead, and one closing line follows.
- C6. Without a terminal setup prints each open step with its command and exits 1, and `--json`, `--yes`, `--install`, `--harness`, `--no-accounts`, `--no-aide` and `--attach` do what the spec says.
- C7. `cland doctor` requires a harness only when a role uses it and `gh` only with a `github` remote, shows versions without a verdict, and does not count OpenCode environment keys as credentials.

If the ids or the text differ at START, map by text and say so in the verdict.

**Eight steps, twelve lines.** The spec's eight steps print up to twelve lines named `project`, `claude-code`, `codex`, `opencode` (the harnesses step, one line per harness), `claude-code login`, `codex login`, `opencode login` (the logins step, one line per harness a role uses), `accounts`, `favourite`, `trust`, `hub`, `aide`. A line is `<verdict>  <name>  <detail>[ — <fix>]`, verdict `ok`, `done`, `skip`, `open` or `fail`; a summary line `N ok, N done, N skip, N open, N fail` follows. A login line exists only for a harness a role uses, so a Claude-only roles template (a machine whose Codex is not installed yet) prints ten lines, not eleven or twelve, and an unused missing harness is `skip`, not `open`. The `opencode login` line is absent while OpenCode is declined or unused. "The eight steps in order" is judged on the order of the groups.

// node drive.cjs <env.json> <cwd> <rules.json> [cland setup args…]
// Runs `cland setup` in a pseudo-terminal (script), answers only questions a rule matches, prints the transcript,
// the rule counts and SETUP_EXIT:<code>. A question no rule matches is left unanswered and the run times out.
const { spawn } = require('child_process');
const fs = require('fs');
const [envFile, cwd, rulesFile, ...args] = process.argv.slice(2);
const env = { ...JSON.parse(fs.readFileSync(envFile, 'utf8')), ...JSON.parse(process.env.QA_EXTRA || '{}') };
const rules = JSON.parse(fs.readFileSync(rulesFile, 'utf8')).map(r => ({ ...r, used: 0, re: r.regex ? new RegExp(r.match) : null }));

const command = [process.execPath, clandEntry, 'setup', ...args].map(q).join(' ') + '; status=$?; printf "\\nSETUP_EXIT:%s\\n" "$status"; exit "$status"';
const argv = process.platform === 'darwin' ? ['-q', '/dev/null', 'sh', '-c', command] : ['-qefc', command, '/dev/null'];
const pipe = 'while IFS= read -r line; do printf "%s\\n" "$line"; done | ';
const child = spawn('sh', ['-c', pipe + ['script', ...argv].map(q).join(' ')], { cwd, env, stdio: ['pipe', 'pipe', 'pipe'], detached: true });
let output = '', fresh = '', timedOut = false;
child.stdin.on('error', () => {});
const consume = chunk => {
  const text = String(chunk).replaceAll('\r', '');
  output += text; fresh += text;
  if (output.includes('SETUP_EXIT:')) child.stdin.end();

    if (r.max !== undefined && r.used >= r.max) continue;
    if (r.re ? r.re.test(fresh) : fresh.includes(r.match)) { r.used++; fresh = ''; child.stdin.write(r.reply + '\n'); break; }
  }
};
child.stdout.on('data', consume);
child.stderr.on('data', consume);
const timer = setTimeout(() => { timedOut = true; try { process.kill(-child.pid, 'SIGKILL'); } catch {} }, Number(process.env.QA_TIMEOUT_S || 90) * 1000);
child.on('close', () => {
  clearTimeout(timer);
  process.stdout.write(output);
  process.stdout.write('\nDRIVER rules: ' + JSON.stringify(rules.map(r => [r.match.slice(0, 40), r.used])) + (timedOut ? ' TIMED-OUT' : '') + '\n');
  const m = /SETUP_EXIT:(\d+)/.exec(output);

});
EOF

## Pitfalls

- **Scratch HOME everywhere.** `cn`, `mx` and `dr` give the machine's environment and nothing of the real one. The only commands that run bare are `cl` (task, demo, verify queue) and the `node $EV/mkmachine.mjs` build. If a `cn` call prints a path under `/Users/evgeniyivanov` that is not `$W`, stop: the environment leaked.
- **Short paths.** Machines live under `/tmp` because a hub socket path under macOS's default temp folder exceeds the Unix socket limit. Do not move `$Q`.
- **`use` empties the launcher log.** Call it once per machine; L3 keeps L2's line.
- **One interface per question.** A driver timeout (exit `98`) is a finding: the prompt that was not answered is the last line of the transcript.
- **Real processes in L8.** Only the three real binaries run (version and login probes), under the scratch HOME, signed out, with no hub and no Aide. QA never answers a login or install question with Yes.
- **Counts, not command lines.** Process checks print counts; no environment or argument vector is printed (T-492).
- **One lease.** Never run `demo start` twice. Record D lines before `demo stop`.
- **Commands on the droplet** are argument vectors: `sh -c '<script>'`.
- **Never work around a refusal.** A refused verify, demo control or verdict is evidence: record its exact text.
- `qa-record.sh` takes `E-613`. The verdict goes on `E-613`.

## Procedure

1. Choose a run id, `qa-<date>-<n>`, set the Environment and write the Scripts. Announce START in the request's topic, naming `S`. `dev` is not frozen: D14 decides.
2. Run, in order, recording each with `qa-record.sh` under `.cland/qa/E-613/<run>/` of the root:
   1. G0, G1, G2, G3. If G0, G1 or G2 is not PASS, stop: the run is BLOCKED.
   2. Part D: D0, then D1–D5 one at a time on the one lease, D14, and D15 last of Part D.
   3. Part L: L1, L2, L3, L4, L5, L6, L7, L8, L9, then L10 (always, even after a failure).
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS (the two substitutes are PASS when their halves pass, and named as substitutes in the text). Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id; a D2–D5 or L9 rerun is the flaky rule's one rerun, reported beside the first result.
6. Before the verdict, run D14's freshness read again if `dev` moved since D14. Publish the evidence with `artifact.create` (kind `note`: the check table; the lease, executor, commit, lifetime and cost; which checks ran where; the transcripts of L2, L6 and L8; the substitutes; the findings) **in the epic's topic where the request was delivered**, and name its id in the verdict text.
7. Write one verdict on E-613 from `$W`: `cl task comment E-613 "<text>" --verdict qa --result clear --run $RUN --commit $S --verified all`. A not-clear verdict carries only `--failed C<n>=<note>` (one per failed criterion, single-line notes) and names in its text the criteria that passed. The text opens with the check table, then the findings ranked high, medium and low. If the hub refuses the verdict as `qa-stale`, keep the evidence and report BLOCKED. Any other refusal: fix its cause and write only the verdict again with the same run.
8. Release the hold if the verdict did not: `cl task hold E-613 --release`. Check L10 left no scratch folder. Remove the build worktree: `git -C $R worktree remove $W`.
9. Report with `send` kind `report` to `lead E-613` in the request's topic: first line `qa clear E-613` or `qa not clear E-613`, then the failed checks, the substitutes, and the lease and its cost. Report any find outside the epic as a bug found aside, with its evidence, so the Coordinator files it under Bugs.
