# QA brief: T-229 Epic: Session lifecycle

This brief is the Definition-of-done demo of epic T-229, which QA runs on `dev` in the human's place (decision D16: epics wait for no human demo). Stops, role routing, restart, pooled handoff, reopen after merge, nameless spokes, a hung tracker write and OpenCode approvals are exercised live in **one scratch project**. It has its own hub, its own suite lock path, the three fake harnesses (Claude Code, Codex, OpenCode), two driver spokes (a Coordinator and a bare Reviewer), a small UI client and one headless workbench. The children's protocol and CLI tests corroborate, **one file at a time**. Everything the run needs is in this file or in the files it names.

## Pitfalls

- Write `lock_path` and `budget` **before** the first `hubstart`: the hub reads `[verification]` only at start, and its stale-lock recovery acts on that path. `guard` refuses a hub start without them.
- A command that prints the root's items, sessions or topics has reached the live hub, which means `noclu` was skipped. Stop, record BLOCKED for that check, and do not repeat it. Never stop, launch or message a root session.
- **Never work around a hub refusal.** A refused stop, launch, merge, push or edit is evidence: record its exact text. Do not kill a process the hub refused to stop, edit a tracker file by hand, or reach the same result another way. The gate directory `$G` and the scratch `config.toml` are the only hand edits, and they are made only in the scratch project.
- `hub/test/termination-ownership.test.ts`'s first case runs `cland doctor --fix` without the test's orphan scope. Like production, it ends any hub on this machine whose project directory no longer exists. Before M5, list `/tmp/cland-suite.lock` read-only: if it exists, a crew suite is running and its temporary projects come and go. Wait until it is gone (read-only polling, never touching it), then run M5 and say so in the note.
- The Implementer pool cap counts every running Implementer. Stop `cb1` (M14) before M18, and reset the crew (M18 g) before launching `ocw` (M19).
- `<Space>s` toggles the sessions panel. Use the key sequence PANELS-010 uses and do not press it again.

## Procedure

1. Choose a run id, `qa-<date>-<n>`.
2. Run the checks in this order, and record each with `qa-record.sh`. Captures go under `.cland/qa/T-229/<run>/` of the root.
   1. M0. If it is not PASS, stop: the run is BLOCKED.
   2. M1.
   3. The root test checks M2–M9, one file at a time, never two at once. Then the case PANELS-010.
   4. The scratch checks M10–M21, in order.
   5. M22 and M23.
3. Fix nothing. A failure is a finding: write down the check id, the command and what it showed.
4. The verdict is `clear` only when every check in scope is PASS. Otherwise it is `not clear`, naming each check that was FAIL, BLOCKED or INCONCLUSIVE.
5. If a step fails, keep what is already written and finish from there. Never rerun a check under the same run id (the skill, "When a step fails").
6. Criteria by position:
   - **C1** = M2, M11, M12, M13
   - **C2** = M3, M15
   - **C3** = M4, M5, M6, M18, M20
   - **C4** = M7, M16, M17
   - **C5** = M8, M19, M21, PANELS-010
   - **C6** = M22

   M0, M1, M10 and M23 gate the run. M9 and M14 (T-249, a child no checkbox names) verify no criterion, but they are in scope: a failure makes the verdict `not clear`. A safety failure (scratch output naming the machine lock, or a command reaching the root hub) leaves every criterion it touched unverified. Verify exactly the ids whose checks are all PASS.
